# DATA_MODEL — Модель данных и память Aven

> **Статус:** проектная документация. Конкретная схема БД не проектируется до утверждения стека ([DECISIONS.md](DECISIONS.md), ADR-102, статус `Proposed`).
> **Последнее обновление:** 2026-09-29

---

## 1. Память Aven — контролируемая

Память **не является бесконтрольной AI-памятью**. Aven не сохраняет бесконтрольно каждую произнесённую фразу как постоянную память.

Существует интерфейс **«Память Aven»**, в котором пользователь может **просматривать, редактировать и удалять** сохранённую постоянную информацию ([ADR-008](DECISIONS.md)).

Временный контекст — не постоянная память; правила его жизни (границы, сброс) детализируются в [COMMAND_ENGINE.md](COMMAND_ENGINE.md).

Пользователь управляет памятью в том числе через настройки: просмотр/добавление/редактирование/удаление, категории памяти, управление тем, что разрешено сохранять, очистка контекста диалога ([PROJECT_PLAN.md](PROJECT_PLAN.md), раздел «Настройки Aven», категория «Память»).

## 3. Сущности и связи

### 3.1. Связи данных

Сущности должны иметь возможность **связываться**. Пример цепочки:

```
BMW → Ремонт → Расход 25 000 ₽ → Чек → Автосервис → Дата
```

Правило: **не дублировать одни и те же данные в разных модулях без необходимости** — связь вместо копии.

### 3.2. Универсальные пользовательские сущности (будущее)

Пользователь сможет создавать собственные разделы/типы сущностей, например:

- Аквариум;
- Мотоцикл;
- Домашнее животное;
- Сервер;
- Коллекция.

Типы полей:

- text;
- long text;
- number;
- money;
- date;
- datetime;
- boolean;
- file;
- image;
- URL;
- select;
- relation;
- и расширяемые типы.

## 4. Задачи, события и напоминания (данные)

**Прототипное состояние 2026-09-27 (не финальная схема БД):** `tasks` и `events` в `/prototype` приведены к общей модели для UI/Text/Voice→Action:

- `task`: `title`, `description`, ISO `date`, `time`, `deadline`, `priority`, `tags`, `completed/status`, `archived`, `reminder` metadata; для совместимости прототип пока хранит также старые алиасы `desc`, `dueDate`, `dueTime`, `prio`, `done`.
- `event`: `title`, ISO `date`, `startTime`, `endTime`, `allDay`, `place`, `description`, `category/color`, `importance`, `repeat`, `reminder` metadata; для совместимости остаются алиасы `time`, `end`, `desc`.
- Reminder metadata — это данные для будущего уведомителя, а не гарантия доставки в web-прототипе при закрытом браузере. Фоновые уведомления требуют отдельного механизма/platform support.

Типы (полное описание — [FEATURES.md](FEATURES.md), раздел 4):

- по точному времени;
- через определённый интервал;
- повторяющиеся;
- за N времени до события;
- по достижению значения;
- будущие: по геопозиции; по событию устройства; по внешнему интернет-событию.

Градация важности: обычное; важное; критическое/будильник-подобное (насколько позволяет платформа).

### 4.1. Suggestions: вычисляемое представление и реакция пользователя

Suggestion не является второй копией задачи/события. Оно вычисляется из исходных сущностей и содержит
stable `id`, тип, приоритет, заголовок/текст/причину, дату и контекст, actions и source references.
В постоянном состоянии прототипа хранится только `suggestionState[id]` (`dismissed`, `snoozeUntilISO`).
Если исходное условие исчезло, suggestion исчезает без отдельного статуса `resolved`; если snooze истёк,
правило снова может его показать. Мутации исходных сущностей выполняет Common Action Layer.
Это прототипный контракт, не утверждённая схема production БД.

### 4.2. Дневные сценарии (утро/вечер): только маркер прохождения

Утренний обзор и вечернее планирование не хранят собственных сущностей и не сохраняют копию сводки.
В постоянном состоянии прототипа есть только минимальный маркер:

```
dailyState: {
  morning: { dateISO: 'YYYY-MM-DD' },   // сценарий пройден в этот день
  evening: { dateISO: 'YYYY-MM-DD' }
}
```

Всё остальное вычисляется на лету из задач, событий, уведомлений и предложений. Настройки
`settings.daily.morning/evening` управляют только подсказкой на «Главной», а границы «утро/день/вечер/ночь»
берутся из уже существующих `settings.behavior`. Перенос задачи на завтра — обычное обновление полей
`date`/`deadline` через Common Action Layer, поэтому Undo возвращает исходную дату.
Это прототипный контракт, не утверждённая схема production БД.

### 4.3. Инварианты целостности данных (Data Integrity, 2026-09-29)

Прототипный контракт общего слоя действий (Common Action Layer). Схема хранения **не менялась** —
это ужесточение проверки значений перед записью, а не новая версия данных и не миграция.

**Календарная дата.** Поле даты хранится строкой `YYYY-MM-DD`, но форма — это ещё не дата.
Единая детерминированная проверка (`AvenActions.dates.isValid`) требует одновременно:

1. точной формы `YYYY-MM-DD` (ровно 4-2-2 цифры);
2. месяца 01–12;
3. дня 01 … фактической длины месяца;
4. правила високосного года: год делится на 4, кроме столетий, кроме делящихся на 400
   (`2000-02-29` — есть, `1900-02-29` и `2100-02-29` — нет, `2028-02-29` — есть);
5. round-trip: дата, собранная обратно из разобранных компонентов, совпадает с исходной строкой
   символ в символ.

Проверка **не использует `new Date()`**: JS молча нормализует невозможные даты
(`new Date('2026-02-30')` → 2 марта), поэтому отсутствие `NaN` ничего не доказывает.

**Диапазон года не ограничен продуктовым правилом.** Модель данных такого диапазона не определяет,
и вводить его молча нельзя, поэтому ограничены только реальные месяц и день: `0001-01-01` и
`9999-12-31` контракт принимает. Если владелец захочет продуктовый диапазон лет (например,
1900–2100), это отдельное решение и отдельный ADR — см. «Открытые вопросы» ниже.

**Деньги.** Денежные величины хранятся как JS `Number` в целых минимальных единицах валюты
(копейки/центы, масштаб 100). Точная целочисленная арифметика существует только внутри безопасного
диапазона, поэтому инвариант:

- `Number.isSafeInteger(minorUnits(amount)) === true` для любой сохраняемой суммы;
- `Number.isSafeInteger(minorUnits(balance)) === true` для любого сохраняемого баланса счёта;
- `Number.isSafeInteger(minorUnits(balance) + minorUnits(delta)) === true` — будущий баланс
  проверяется **до** мутации, а не после.

Граница не выписана константой: она вычисляется из `Number.MAX_SAFE_INTEGER` и масштаба валюты
(`maxAmount = Number.MAX_SAFE_INTEGER / 100`). Продуктового «лимита суммы» вроде «не больше
миллиона» в модели нет и он не вводится — ограничение только техническое и объясняется пользователю
как «слишком большая сумма не сохраняется, чтобы расчёты остались точными».

**Предел различимости копеек (проверено на ревью 2026-09-29).** Инвариант выше гарантирует, что
арифметика остаётся точной, но он **не** означает, что на любой принятой величине различимы соседние
копейки. Суммы и балансы хранятся в основных единицах (`minorUnits / 100`) как JS `Number`, поэтому
примерно с 3,5 × 10¹³ основных единиц шаг представления double превышает 0,01, и пара соседних
«копеечных» значений может отобразиться на одно и то же хранимое число. Измерено: расхождение
не превышает **1 минимальной единицы**, возникает только при первом преобразовании и **не
накапливается** (значение сразу становится неподвижной точкой). Это свойство существовавшего до
ужесточения способа хранения (`minorUnits(v) / 100`), а не следствие новой проверки: до ужесточения
та же арифметика принимала `10²²` и ошибалась на порядки. Реальные бытовые суммы этого порога не
достигают. Если когда-нибудь понадобится точность копейки на таких величинах, это смена схемы
хранения (хранить минимальные единицы целыми) и отдельное решение, а не правка валидации.

**Где проверка живёт.** Проверка принадлежит общему слою действий и является окончательной для всех
входов: UI-форма, текстовая команда и прямой вызов действия. Разбор текстовой команды может иметь
собственную синтаксическую проверку, но source of truth один — Common Action Layer. Отклонённое
значение не меняет сущности, не двигает баланс, не пишет «Историю» и не попадает в сохраняемое
состояние.

**Ограничение контракта.** Проверка работает на границе действий. Значения, попавшие в состояние
**до** ужесточения (или подложенные напрямую в localStorage), не мигрируются: read-only показ
остаётся живым (формат не падает и не «чинит» невозможную дату молчаливой нормализацией), но
автоматической починки старых данных нет. Импорта/восстановления произвольного состояния в
прототипе нет — когда он появится, он обязан проходить эти же инварианты.

## 5. Статусы записей и действий

Честные статусы ([ADR-010](DECISIONS.md)): успешно; ожидает синхронизации; запланировано; требует подтверждения; ошибка; недоступно офлайн; платформа не поддерживает.

## 6. Разделение данных

- Данные строго разделяются по пользователям ([SECURITY.md](SECURITY.md)).
- Все связанные данные автомобиля связываются с конкретным автомобилем ([FEATURES.md](FEATURES.md), раздел 6).
- Финансовые записи связываются с сущностями (авто, дом, покупка, поездка, проект) через связи, а не дублирование.
- Семья/общие пространства — будущая модель совместного доступа ([FUTURE.md](FUTURE.md)).

## 7. Файлы

Файлы (чеки, фото, документы) — через объектное хранилище с S3-compatible абстракцией ([DECISIONS.md](DECISIONS.md), ADR-108); метаданные — в БД; квоты и лимиты — [ADMIN.md](ADMIN.md), раздел Storage.

## 8. Офлайн-данные

Локальные копии/очереди изменений, pending sync, конфликты — [OFFLINE_SYNC.md](OFFLINE_SYNC.md).

## 9. Открытые вопросы

1. Конкретная схема БД и миграции — после утверждения ADR-102.
2. Механизм универсальных пользовательских типов (EAV / JSONB / гибрид) — будущий ADR.
3. Правила хранения временного диалогового контекста (объём, TTL, приватность).
4. Модель совместного доступа (семья/общие пространства).
5. Версионирование фактов памяти (история изменений памяти пользователя).
6. **Продуктовый диапазон лет для дат** (§4.3). Сейчас ограничены только реальные месяц и день,
   год не ограничен. Нужен ли продуктовый диапазон (например, 1900–2100) — решение владельца,
   молча он не вводился.
7. **Импорт/восстановление произвольного состояния** (§4.3). Такого пути в прототипе нет; когда он
   появится, нужно решить, проверяются ли импортируемые данные теми же инвариантами или
   требуется отдельный слой миграции.
