## 1. Суть проекта

**Aven** — персональный цифровой помощник и центр управления личными данными, делами, инструментами и автоматизациями пользователя.

Это **не** чат-бот. Основной сценарий: пользователь регистрируется и получает персонального помощника Aven, которому можно сказать или написать, что необходимо **сделать, записать, найти, посчитать, запланировать или выполнить**.

### Примеры запросов

- «Напомни завтра в 10 позвонить Сергею.»
- «Через час мне нужно быть у стоматолога.»
- «Запиши расход 850 рублей на продукты.»
- «Я заправился на 3200 рублей, 42 литра.»
- «Покажи расходы на BMW за сентябрь.»
- «Когда я последний раз менял масло?»
- «Запомни, что зимние колёса лежат в гараже.»
- «Что у меня завтра?»
- «Покажи покупки, у которых ещё действует гарантия.»

### Ключевые принципы продукта

1. Пользователь может взаимодействовать **голосом и текстом**.
2. **Текстовый ввод всегда доступен** (микрофон не обязателен).
3. Ответы могут одновременно **показываться текстом и озвучиваться**.
4. Основные возможности **не зависят от платного AI**; AI — дополнительный слой, а не ядро системы.
5. Система должна иметь возможность **работать частично без интернета**.
6. В будущем появятся **мобильные приложения**; позже возможен **desktop-agent**.
7. Функциональность **расширяется модулями**.
8. Пользователь **контролирует** свою память, данные, команды и автоматизации.
9. **Опасные действия требуют подтверждения.**
10. **Приватность и безопасность** учитываются с самого начала.

### Цель

Пользователь регистрируется и получает персонального помощника Aven, которому можно сказать или написать, что необходимо сделать, записать, найти, посчитать, запланировать или выполнить.

## 2. Ключевая архитектурная идея (кратко)

Полные детали — в [ARCHITECTURE.md](ARCHITECTURE.md), [COMMAND_ENGINE.md](COMMAND_ENGINE.md), [VOICE.md](VOICE.md).

```
Микрофон → Speech-to-Text → текст ↘
                                    Command Engine → Action → Result → текстовый ответ → Text-to-Speech
UI / текстовый ввод ———————————————— ↗
```

- **Command Engine** работает на intents/actions **без генеративного AI**: нормализация, определение намерения, извлечение параметров, entity resolution, confidence, уточнения, подтверждения.
- **Action Core**: любой источник команды (UI, текст, голос, Automation, API, в будущем AI) превращается в стандартное действие; бизнес-логика не дублируется для голоса и UI.
- **Голосовой слой заменяем** (STT/TTS — провайдеры и движки могут меняться).
- **AI — опциональный слой** в будущем: `Human input → AI Router (опционально) → строго определённый Action + parameters → permission validation → execution`. Без AI и интернета основные функции продолжают работать.
- **Automation Canvas** (node-based визуальные автоматизации) — ключевая будущая возможность, см. [AUTOMATION.md](AUTOMATION.md).
- **Offline-first / local-first** учитывается в долгосрочной архитектуре, см. [OFFLINE_SYNC.md](OFFLINE_SYNC.md).

## 4. Этапы развития (карта-roadmap)

> Этапы — ориентир, а не жёсткое расписание. Состав этапов уточняется по мере утверждения решений.

### Этап 0 — Документационная основа ✅ (текущий)

- Создана документационная структура, зафиксирована концепция.
- Зафиксированы продуктовые принципы (`Product Principle`) и решения в статусах `Proposed`/`Under Discussion` (см. [DECISIONS.md](DECISIONS.md)). Окончательные архитектурные решения **не** утверждены; ничто не является необратимым.
- Код приложения **не** пишется, зависимости **не** устанавливаются.

### Этап 1 — Утверждение архитектуры (ADR)

- Ответить на открытые вопросы раздела 8.
- Зафиксировать в [DECISIONS.md](DECISIONS.md): backend-стек, БД, web-фреймворк, очередь задач, кэш, объектное хранилище, стратегию синхронизации, модель доверия Command Engine (пороги confidence).
- Определить состав и границы MVP (черновик — раздел 5) и **утвердить** его.

### Этап 2 — MVP (состав — черновик, см. раздел 5)

- Реализация утверждённого состава MVP на утверждённом стеке.
- Вертикальный срез: регистрация → главная Aven → текстовая команда → Command Engine → действие → шаблонный ответ.

### Этап 3 — Расширение MVP

- Углубление модулей (авто, финансы, память), пользовательские команды и словарь, готовые автоматизации.
- Решение по Automation Canvas: либо поздняя часть MVP (этап 2–3), либо следующий этап — **вопрос открыт**.

### Этап 4 — Мобильные приложения и офлайн

- PWA → Android/iOS (кандидат: Flutter/Dart, локальная БД SQLite).
- Системные TTS/STT, системные уведомления, локальная БД, синхронизация.

### Этап 5 — Desktop-agent и расширенные интеграции

- Desktop-agent (кандидат: Rust + Tauri): только с явного согласия, контролируемые permissions.
- Примеры будущих команд: «Открой Steam.», «Покажи свободное место.», «Открой папку проекта.», «Передай файл на компьютер.»

### Горизонт

- AI-слой (опциональный router/парсер), гео-напоминания, события устройств, внешние интернет-события, семейные/общие пространства, универсальные пользовательские сущности — см. [FUTURE.md](FUTURE.md).

**Не считать функции этапов 4–5 частью первого MVP.**

## 8. Открытые вопросы

> Вопросы, которые **нужно решить отдельно** до/во время этапа 1. Найденные противоречия также фиксируются здесь.

1. **Automation Canvas в MVP или после?** Спецификация явно допускает оба варианта («либо поздней частью MVP, либо следующим этапом»). Нужно решение.
2. **Пороги confidence** Command Engine — принцип уровней утверждён (высокая/средняя/низкая/опасное действие), конкретные числовые пороги **не утверждены**.
3. **Background jobs** — production-ready система очередей/воркеров не выбрана.
4. **Кэширование** — Redis «если обосновано»; обоснование не подготовлено.
5. **Backend/Web/Mobile/Desktop стеки** — кандидаты перечислены, ADR нет.
6. **Стратегия разрешения конфликтов офлайн-синхронизации** не выбрана (last-write-wins / CRDT / ручное разрешение — TBD).
7. **STT/TTS провайдеры** не выбраны; поддержка браузерами (Web Speech API) не гарантирована — нужен план fallback и матрица поддержки.
8. **Состав и приоритеты MVP** — список в разделе 5 помечен как «вероятный», требуется утверждение.
9. **Значения по умолчанию для «утро/вечер/после работы»** — концепция требует пользовательских настроек, конкретные дефолты не определены.
10. **Языковой охват Command Engine на старте** — концепция написана на русском; мультиязычность движка и приоритетные языки не зафиксированы (в профиле есть поле «язык», в голосовых настройках — «язык»).
11. **Порядок выхода платформ** (Web → PWA → Android → iOS → desktop-agent) — логичный, но не утверждён.
12. **Хранилище офлайн-данных в вебе** (IndexedDB / OPFS / SQLite-WASM и т.п.) не выбрано.
13. **AI Router будущего** — провайдер/модель/условия включения не определены (сам принцип «AI опционален» утверждён).
14. **Механизм защиты критического audit trail** от незаметного удаления обычным администратором — требование зафиксировано, механизм (append-only, WORM, мультиподпись и т.п.) не выбран.
15. **Модель квот и лимитов** (storage, voice, automation) упомянута в админке — детали не определены.
16. **Email-провайдер / SMTP** и шаблоны писем — не выбраны.
17. **Каналы уведомлений в MVP** (in-app / email / web push) — web push имеет ограничения, точный состав не утверждён.
18. **Push/фоновое произнесение**: честно зафиксировано ограничение (закрытый браузер не может произносить голосовые сообщения), ожидания пользователей нужно оформить в UX-текстах. Решение о том, что именно обещать в каждом клиенте, не принято.
19. **Перечень «чувствительных настроек»**, требующих подтверждения и/или повторной аутентификации при изменении командой — не определён.
20. **Охват настроек, изменяемых текстовой/голосовой командой** («подходящие настройки»), и полный набор `settings.*` actions — не определены (зафиксированы только примеры).
21. **Механизм повторной аутентификации** для чувствительных действий (и окно доверия после неё) — не спроектирован.
22. **«Звук перед голосом», «поведение при подключённых наушниках», управление диагностическими данными** — техническая реализуемость на целевых платформах требует исследования.
23. **Состав настроек MVP** — какие категории настроек входят в первый выпуск — не определён.
24. **Support impersonation** — нужен ли и в каком виде; при появлении — отдельный ADR (требования зафиксированы в PROJECT_PLAN, раздел 12).
25. **Настройки главной** (карточки, порядок, блоки) и **Доступности** (accessibility) — минимальный состав для MVP не определён.
26. **Экспериментальные функции** — механизм индивидуального включения будущих возможностей (в связке с feature flags админки) не спроектирован.

## 9. Статус архитектуры

Зафиксировано владельцем проекта:

- архитектура пока **проектируется**;
- окончательный **production stack не утверждён**;

- **Automation Canvas** остаётся предметом планирования;

- **offline/sync architecture** остаётся предметом дальнейшего проектирования;
- **AI** остаётся **необязательным** направлением;
- **документация будет развиваться вместе с концепцией**.

Правило изменяемости архитектуры зафиксировано в [DECISIONS.md](DECISIONS.md): до начала production-разработки любое `Proposed`/`Under Discussion` решение может быть изменено владельцем без требований обратной совместимости; ADR не является запретом на изменение архитектуры.

## 10. Настройки Aven

Будущие категории пользовательских настроек (интерфейс `/settings`). Категории и состав зафиксированы владельцем как **планируемая структура**; состав MVP настроек определяется отдельно (открытый вопрос №23).

### Профиль

имя; обращение; язык; регион; часовой пояс; валюта; формат даты; формат времени; начало недели.

### Голос

выбор доступного голоса; скорость; высота; громкость; автоматическая озвучка; повтор последнего ответа; голосовой ввод; тест голоса; fallback при недоступности STT/TTS.

### Поведение Aven

краткие/подробные ответы; уровень подтверждений; пользовательское определение «утро»; «день»; «вечер»; «ночь»; «после работы»; другие временные понятия в будущем.

### Голосовые события/уведомления

разрешение голосового произнесения; тихие часы; уровни важности; повтор; звук перед голосом; поведение при подключённых наушниках; правила произнесения приватной информации; ограничения платформ должны отображаться честно.

### Команды

системные команды; пользовательские команды; альтернативные фразы; шаблоны; параметры; включение/отключение; тестирование распознавания; конфликты.

### Персональный словарь

пользовательские слова; словосочетания; aliases сущностей; просмотр конфликтов; приоритет персонального словаря.

### Память

просмотр постоянной памяти; добавление; редактирование; удаление; категории памяти; управление тем, что разрешено сохранять; очистка контекста диалога.

### Автоматизации

список workflows; включение/отключение; история запусков; ошибки; permissions; переход в Automation Canvas.

### Модули

включение/отключение ненужных пользователю модулей; настройка порядка; будущая поддержка пользовательских модулей.

### Главная

карточки; порядок; быстрые действия; отображаемые блоки; вид следующего события.

### Приватность

экспорт; удаление данных; диагностические данные; история действий; управление постоянной памятью; локальные/private данные в будущем.

### Файлы

### Доступность

## 11. Управление настройками через Aven

Пользователь должен иметь возможность менять **подходящие настройки не только через UI, но и текстовой/голосовой командой** ([ADR-011](DECISIONS.md)).

Примеры:

- «Говори медленнее.»
- «Не разговаривай после 23:00.»
- «Вечер для меня начинается в 18:30.»
- «Называй BMW бэхой.»
- «Отключи голосовые ответы.»
- «Всегда спрашивай перед удалением.»

Такие команды должны преобразовываться в **стандартные Actions**, например:

```
settings.voice.rate.set
settings.quiet_hours.set
settings.day_period.set
dictionary.alias.create
settings.voice.enabled.set
settings.confirmation_policy.set
```

Безопасность:

- **Не разрешать** голосовой команде обходить security requirements.
- Для **чувствительных настроек** использовать подтверждение и/или **повторную аутентификацию**.

Перечни «подходящих» и «чувствительных» настроек — открытые вопросы (№19, №20).

## 12. Разделение User Settings и Admin

Явно зафиксировано ([ADR-012](DECISIONS.md)):

- **`/settings`** — настройки **конкретного пользователя** (раздел 10).
- **`/admin`** — управление **системой Aven** ([ADMIN.md](ADMIN.md)).

Правила:

- Администратор **не должен автоматически получать возможность действовать от имени пользователя**.
- Если в будущем появится **support impersonation**, функция должна:
  - проектироваться **отдельно** (отдельный ADR);
  - иметь **строгие permissions**;
  - быть **явно заметной** (режим виден пользователю/в интерфейсе);
  - **журналироваться**;
  - иметь **причину входа** (reason);
  - по возможности **ограничивать доступ к чувствительным данным**.

## 13. Правила изменения плана

- План — живой документ, но изменения фиксируются: обновляется этот файл и, при необходимости, [CHANGELOG.md](CHANGELOG.md) / [WORK_LOG.md](WORK_LOG.md).
- **Приоритет источников требований** — см. [AGENT_GUIDE.md](AGENT_GUIDE.md): последнее прямое решение владельца > PROJECT_PLAN > действующие Product Principles > действующие ADR > остальная документация > предположения агента. При конфликте нового прямого решения владельца со старым ADR приоритет у решения владельца; конфликт документируется.
- Архитектура изменяема (правило — [DECISIONS.md](DECISIONS.md)): изменение решения фиксируется **новым ADR** с причиной и последствиями; старое решение отмечается `Superseded`/`Rejected`, а не удаляется.
- Незавершённое не помечается как выполненное.
