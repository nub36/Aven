## 1. Суть проекта

**Aven** — персональный цифровой помощник и центр управления личными данными, делами, инструментами и автоматизациями пользователя.

Это **не** чат-бот. Основной сценарий: пользователь регистрируется и получает персонального помощника Aven, которому можно сказать или написать, что необходимо **сделать, записать, найти, посчитать, запланировать или выполнить**.

### Примеры запросов

- «Напомни завтра в 10 позвонить Сергею.»
- «Через час мне нужно быть у стоматолога.»
- «Запиши расход 850 рублей на продукты.»
- «Я заправился на 3200 рублей, 42 литра.»
- «Покажи расходы на BMW за сентябрь.»
- «Когда я последний раз менял масло?»
- «Запомни, что зимние колёса лежат в гараже.»
- «Что у меня завтра?»
- «Покажи покупки, у которых ещё действует гарантия.»

### Ключевые принципы продукта

1. Пользователь может взаимодействовать **голосом и текстом**.
2. **Текстовый ввод всегда доступен** (микрофон не обязателен).
3. Ответы могут одновременно **показываться текстом и озвучиваться**.
4. Основные возможности **не зависят от платного AI**; AI — дополнительный слой, а не ядро системы.
5. Система должна иметь возможность **работать частично без интернета**.
6. В будущем появятся **мобильные приложения**; позже возможен **desktop-agent**.
7. Функциональность **расширяется модулями**.
8. Пользователь **контролирует** свою память, данные, команды и автоматизации.
9. **Опасные действия требуют подтверждения.**
10. **Приватность и безопасность** учитываются с самого начала.

Текущее продуктовое направление — **Web-first**: первая полноценная реализация — самостоятельный полезный веб-сайт (см. раздел 6 и [ADR-013](DECISIONS.md)).

## 2. Ключевая архитектурная идея (кратко)

Полные детали — в [ARCHITECTURE.md](ARCHITECTURE.md), [COMMAND_ENGINE.md](COMMAND_ENGINE.md), [VOICE.md](VOICE.md).

```
UI / Forms
        \
Text command → Action Core → Business Logic → Data
        /
Voice → STT → Text command

Result → UI
       → Text response
       → TTS (если включено)
```

- **UI/формы** — первоклассный способ пользования сайтом: основные функции полноценно доступны мышью, клавиатурой, обычными формами и навигацией. Голос и текстовые команды — **дополнительные способы управления уже существующими функциями**.
- **Отдельная бизнес-логика для UI, текста и голоса не создаётся** — все источники ведут к одному Action/Use Case ([ADR-013](DECISIONS.md), [ADR-004](DECISIONS.md) — Proposed).
- **Command Engine** (Stage 2) работает на intents/actions **без генеративного AI**: нормализация, определение намерения, извлечение параметров, entity resolution, confidence, уточнения, подтверждения ([COMMAND_ENGINE.md](COMMAND_ENGINE.md)).
- **Голосовой слой заменяем** и является слоем поверх текстового Command Engine (Stage 3); Business Logic не связывается напрямую с Speech Recognition ([VOICE.md](VOICE.md)).
- **AI — опциональный слой** в будущем: `Human input → AI Router (опционально) → строго определённый Action + parameters → permission validation → execution`. Без AI и интернета основные функции продолжают работать.
- **Automation Canvas** — Stage 4; сложность Canvas не должна задерживать создание полезного сайта ([AUTOMATION.md](AUTOMATION.md)).
- **Offline/local-first** — желаемое будущее свойство; сложная offline-синхронизация **не** является обязательным условием запуска web-версии ([OFFLINE_SYNC.md](OFFLINE_SYNC.md), [ADR-007](DECISIONS.md)).

## 4. Порядок развития (Stage) — Web-first

> Зафиксировано владельцем 2026-09-25 ([ADR-013](DECISIONS.md)). Это **продуктовый приоритет**, а не обязательная архитектурная последовательность: компоненты могут реализоваться с перекрытием. **Все Stage могут пересматриваться владельцем.**

### Stage 0 — Документационная основа ✅ (выполнено)

- Создана документационная структура, зафиксирована концепция.
- Зафиксированы продуктовые принципы и решения в статусах `Product Principle`/`Product Direction`/`Proposed`/`Under Discussion`.
- Код приложения не пишется, зависимости не устанавливаются.

### Stage 1 — Полезный самостоятельный веб-сайт (текущий приоритет)

- Первая полноценная реализация Aven — **самостоятельный полезный веб-сайт** ([ADR-013](DECISIONS.md)): основные функции полноценно доступны мышью, клавиатурой, обычными формами, навигацией.
- Разделы сайта — раздел 6 (структура предварительно проектируется; не все обязаны войти в MVP).
- Перед кодом — утверждение стека и способов реализации (ADR из `Proposed` → `Accepted`).
- Голос и текстовые команды на этом этапе не являются обязательными.

### Stage 2 — Command Engine

- Управление функциями сайта естественными **текстовыми командами** ([COMMAND_ENGINE.md](COMMAND_ENGINE.md)).
- Те же действия остаются доступными через обычный UI.

### Stage 3 — Голос

- **Голосовой ввод и голосовые ответы** поверх Command Engine: `audio → STT → text → Command Engine`; ответ `result → response text → optional TTS` ([VOICE.md](VOICE.md)).
- Сайт обязан оставаться полноценно полезным без голоса (раздел 6.2).

### Stage 4 — Автоматизации

- Расширение автоматизаций и **Automation Canvas** ([AUTOMATION.md](AUTOMATION.md)).
- На раннем этапе могут существовать готовые автоматизации, простые правила, расписания; полноценный node-based Canvas — после стабилизации базовых данных и Action Core. Срок Canvas не утверждён.

### Stage 5 — Оценка мобильного переноса

- После появления полезного и проверенного веб-продукта — определить, какие функции **действительно необходимо** переносить в мобильные приложения (по реальному использованию).

### Stage 6 — Android/iOS и другие клиенты

- Отдельное **будущее** направление ([FUTURE.md](FUTURE.md)).

**Не считать функции Stage 5–6 частью первого MVP.**

## 6. Web-first: принцип и состав Web Aven

### 6.1. Основной принцип

Первая полноценная реализация Aven — **самостоятельный полезный веб-сайт** ([ADR-013](DECISIONS.md)).

**Не** проектировать первую версию как:

- оболочку будущего мобильного приложения;
- только голосового ассистента;
- только чат;
- пустой dashboard;
- демонстрацию технологий.

Пользователь должен иметь возможность полноценно пользоваться основными функциями сайта:

- мышью;
- клавиатурой;
- обычными формами;
- навигацией.

Голос и текстовые команды являются **дополнительными** способами управления уже существующими функциями. Отдельная бизнес-логика для UI, текста и голоса **не создаётся** (диаграмма — раздел 2).

### 6.2. Обязательное UX-правило: веб-сайт полезен без голоса

**Ни одна базовая функция Aven не должна становиться недоступной только потому, что:**

- нет микрофона;
- пользователь запретил доступ к микрофону;
- STT не поддерживается браузером;
- пользователь не хочет разговаривать;
- TTS отключён.

Для базовых функций должен существовать **обычный UI**.

### 6.3. Предварительная структура Web Aven

> Считать **проектируемой структурой, которую можно менять**. Не все разделы обязательно войдут в первый MVP. Полный состав разделов — [FEATURES.md](FEATURES.md).

1. Главная
2. День
3. Календарь
4. Задачи
5. Заметки
6. Финансы
7. Авто
8. Покупки / Имущество
9. Инструменты
10. Aven Assistant
11. Автоматизации
12. Настройки

### 6.4. Краткое описание разделов

- **Главная** — персональный центр: приветствие, дата, ближайшее событие, краткий сегодняшний план, задачи, быстрые действия, последние действия, расходы/пользовательские показатели, настраиваемые карточки, строка «Что сделать?», кнопка микрофона (когда voice доступен), Suggestions, переходы в разделы. **Не должна превращаться в перегруженную панель.**
- **День** — текущее время пользователя: вчера/сегодня/завтра, timeline, события, задачи, напоминания, выполненные действия, быстрое создание записи, утренний обзор, вечернее планирование.
- **Календарь** — обычный полноценный UI: месяц/неделя/день, события (создание/изменение/удаление), повторения, важность, связанные сущности. **Календарём можно пользоваться без ассистента.**
- **Задачи** — задачи, списки, проекты, сроки, приоритет, подзадачи, повторение, статусы, выполненные, архив, связи с сущностями.
- **Заметки** — самостоятельный раздел: текстовые заметки, папки/коллекции, теги, поиск, закрепление, архив, списки, ссылки, будущие attachments, связи с объектами.
- **Финансы** — расходы, доходы, категории, счета, история, фильтры, статистика, графики, связи. **Функции работают через обычные формы независимо от Command Engine.** Расширенные банковские возможности — не часть первоначальной реализации.
- **Авто** — самостоятельный функциональный раздел (несколько автомобилей, карточка, пробег, заправки, ремонты, обслуживание, документы, страховки, история, статистика). Все пути (UI / текст / голос) ведут к **одному** Action/Use Case — пример в [FEATURES.md](FEATURES.md).
- **Покупки / Имущество** — предмет, категория, цена, дата покупки, магазин, гарантия, серийный номер, чек, фото/файлы (будущее), ремонт, обслуживание, продажа, статус собственности.
- **Инструменты** — полезные функции, доступные сразу, даже если персональные данные почти не заполнены (QR-коды, генератор паролей, конвертеры, калькуляторы, текстовые/JSON/Base64/UUID/timestamp-утилиты и др.). При возможности обработка приватных файлов — локально в браузере. Набор первого релиза определяется отдельно.
- **Aven Assistant** — отдельный режим/страница ассистента с более свободным интерфейсом (история общения, большое поле команды, микрофон, ответы, Suggestions, уточнения, подтверждения). **Не заменяет обычные страницы сайта.**
- **Автоматизации** — Stage 4 (Canvas); на раннем этапе возможны готовые автоматизации, простые правила, расписания.
- **Настройки** — раздел 11.

### 6.5. Автоматизации на раннем этапе

Automation Canvas остаётся важным будущим направлением, но **сложность Canvas не должна задерживать создание полезного сайта**. На раннем этапе могут существовать: готовые автоматизации; простые правила; расписания. Полноценный node-based Canvas — после стабилизации базовых данных и Action Core ([AUTOMATION.md](AUTOMATION.md)). Срок Canvas **не считать окончательно утверждённым**.

### 6.6. Mobile и Desktop — FUTURE

- **Принцип переноса в mobile:** сначала создать полезный Aven Web; наблюдать, какие функции действительно используются; после этого определить набор функций Android/iOS (Stage 5–6).
- Сейчас **не требуется** реализовывать: Android; iOS; mobile offline database; background mobile voice; постоянное прослушивание; сложную device synchronization.
- Desktop-agent: в FUTURE; сейчас не реализовывать запуск программ, управление ОС, файловую систему пользователя, shutdown, desktop monitoring.
- При этом **не создавать искусственных архитектурных препятствий** будущим клиентам: Backend/API и Business Logic проектируются так, чтобы позже их могли использовать другие доверенные клиенты ([ARCHITECTURE.md](ARCHITECTURE.md)).

### 6.7. Offline — текущая трактовка

Offline/local-first остаётся **желаемым будущим свойством** Aven (особенно для мобильных приложений), но **сложная offline-синхронизация не является обязательным условием запуска первой web-версии**. Для Web можно использовать локальные возможности браузера там, где это даёт практическую пользу, но без построения сложной распределённой sync-системы без подтверждённой необходимости. [OFFLINE_SYNC.md](OFFLINE_SYNC.md) сохранён; части документа имеют статус Future / Under Design.

### 6.8. Web-first ≠ Web-only

**Aven сейчас Web-first. Это НЕ означает, что Aven навсегда останется только сайтом.** Архитектура должна позволять дальнейшее развитие в: PWA; Android; iOS; desktop; integrations. Но эти платформы **не являются текущей целью разработки**.

## 9. Открытые вопросы

> Вопросы, которые **нужно решить отдельно**. Найденные противоречия также фиксируются здесь.

1. **Automation Canvas в MVP или после?** Направление Web-first относит Canvas к Stage 4, но границы раннего этапа (готовые автоматизации/простые правила/расписания) нужно определить.
2. **Пороги confidence** Command Engine — принцип уровней зафиксирован, конкретные числовые пороги **не утверждены**.
3. **Background jobs** — кандидаты предложены и сравнены ([STACK_RESEARCH.md](STACK_RESEARCH.md) §6.2, [ADR-106](DECISIONS.md): pg-boss vs BullMQ vs Temporal vs cron); **решение за владельцем**.

## 11. Настройки Aven

Будущие категории пользовательских настроек (интерфейс `/settings`). Категории и состав зафиксированы владельцем как **планируемая структура**; состав MVP настроек определяется отдельно (открытый вопрос №23). Настройки должны **работать через UI**; в будущем подходящие настройки можно менять командами (раздел 12).

### Профиль

имя; обращение; язык; регион; часовой пояс; валюта; формат даты; формат времени; начало недели.

### Голос

выбор доступного голоса; скорость; высота; громкость; автоматическая озвучка; повтор последнего ответа; голосовой ввод; тест голоса; fallback при недоступности STT/TTS.

### Поведение Aven

краткие/подробные ответы; уровень подтверждений; пользовательское определение «утро»; «день»; «вечер»; «ночь»; «после работы»; другие временные понятия в будущем.

### Голосовые события/уведомления

разрешение голосового произнесения; тихие часы; уровни важности; повтор; звук перед голосом; поведение при подключённых наушниках; правила произнесения приватной информации; ограничения платформ должны отображаться честно.

### Команды

системные команды; пользовательские команды; альтернативные фразы; шаблоны; параметры; включение/отключение; тестирование распознавания; конфликты.

### Персональный словарь

пользовательские слова; словосочетания; aliases сущностей; просмотр конфликтов; приоритет персонального словаря.

### Память

просмотр постоянной памяти; добавление; редактирование; удаление; категории памяти; управление тем, что разрешено сохранять; очистка контекста диалога.

### Автоматизации

список workflows; включение/отключение; история запусков; ошибки; permissions; переход в Automation Canvas.

### Модули

включение/отключение ненужных пользователю модулей; настройка порядка; будущая поддержка пользовательских модулей.

### Главная

карточки; порядок; быстрые действия; отображаемые блоки; вид следующего события.

### Приватность

экспорт; удаление данных; диагностические данные; история действий; управление постоянной памятью; локальные/private данные в будущем.

### Безопасность

пароль; 2FA; активные сессии; доверенные устройства; завершение других сессий; security history.

### Интеграции

подключённые сервисы; permissions; отключение; статус; дата последней синхронизации.

### Синхронизация

устройства; sync status; pending operations; offline storage; настройки локального хранения.

### Файлы

занятое пространство; квота; настройки хранения; backup/export.

### Доступность

размер текста; контрастность; reduced motion; управление клавиатурой; другие accessibility-настройки.

### Экспериментальные функции

возможность отдельно включать будущие возможности Aven.

Связанные документы: [UI_UX.md](UI_UX.md) (структура в интерфейсе), [VOICE.md](VOICE.md) (голос/уведомления), [COMMAND_ENGINE.md](COMMAND_ENGINE.md) (команды/словарь), [DATA_MODEL.md](DATA_MODEL.md) (память/профиль), [SECURITY.md](SECURITY.md) (безопасность/приватность).

## 12. Управление настройками через Aven

Пользователь должен иметь возможность менять **подходящие настройки не только через UI, но и текстовой/голосовой командой** ([ADR-011](DECISIONS.md)). Приоритет — UI: командное управление подключается вместе с Command Engine (Stage 2+).

Примеры:

- «Говори медленнее.»
- «Не разговаривай после 23:00.»
- «Вечер для меня начинается в 18:30.»
- «Называй BMW бэхой.»
- «Отключи голосовые ответы.»
- «Всегда спрашивай перед удалением.»

Такие команды должны преобразовываться в **стандартные Actions**, например:

```
settings.voice.rate.set
settings.quiet_hours.set
settings.day_period.set
dictionary.alias.create
settings.voice.enabled.set
settings.confirmation_policy.set
```

Безопасность:

- **Не разрешать** голосовой команде обходить security requirements.
- Для **чувствительных настроек** использовать подтверждение и/или **повторную аутентификацию**.

Перечни «подходящих» и «чувствительных» настроек — открытые вопросы (№19, №20).

## 13. Разделение User Settings и Admin

Явно зафиксировано ([ADR-012](DECISIONS.md)):

- **`/settings`** — настройки **конкретного пользователя** (раздел 11).
- **`/admin`** — управление **системой Aven** ([ADMIN.md](ADMIN.md)); админка остаётся частью web ecosystem, но не смешивается с `/settings`.

Правила:

- Администратор **не должен автоматически получать возможность действовать от имени пользователя**.
- Если в будущем появится **support impersonation**, функция должна:
  - проектироваться **отдельно** (отдельный ADR);
  - иметь **строгие permissions**;
  - быть **явно заметной** (режим виден пользователю/в интерфейсе);
  - **журналироваться**;
  - иметь **причину входа** (reason);
  - по возможности **ограничивать доступ к чувствительным данным**.

Ранее определённые требования безопасности и audit log сохраняются ([ADMIN.md](ADMIN.md), [SECURITY.md](SECURITY.md)).
