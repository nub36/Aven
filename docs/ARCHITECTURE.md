# ARCHITECTURE — Архитектура Aven

> **Статус:** проектная документация (design). Production-архитектура в стадии проектирования; `/prototype` — UX-прототип, не production-реализация. Стек — см. [DECISIONS.md](DECISIONS.md) (все технологические кандидаты — `Proposed`; `Under Discussion` на 2026-09-26 нет) и [PROJECT_PLAN.md](PROJECT_PLAN.md), раздел «Статус архитектуры»; материалы для решения по стеку — [STACK_RESEARCH.md](STACK_RESEARCH.md). ADR не является запретом на изменение архитектуры.
> **Текущее направление:** Web-first ([ADR-013](DECISIONS.md), Product Direction) — первая полноценная реализация: самостоятельный полезный веб-сайт.
> **Последнее обновление:** 2026-09-28 (первая итерация Text Command Engine в прототипе)

## 1. Что такое Aven с точки зрения системы

Aven — персональный цифровой помощник и центр управления личными данными, делами, инструментами и автоматизациями. Не чат-бот: основная ценность — превращение естественных фраз (голос/текст) в **надёжные действия** над персональными данными при полном контроле пользователя.

Три опоры архитектуры:

1. **Command Engine** — детерминированное понимание команд без генеративного AI ([COMMAND_ENGINE.md](COMMAND_ENGINE.md)).
2. **Action Core** — единый контракт действий для всех источников команд (этот документ, раздел 4).
3. **Модульные данные и автоматизации** — расширяемые сущности и связи ([DATA_MODEL.md](DATA_MODEL.md)), визуальные автоматизации ([AUTOMATION.md](AUTOMATION.md)).

## 2. Основные принципы

- **Web-first** ([ADR-013](DECISIONS.md)): первая полноценная реализация — самостоятельный полезный веб-сайт. Основные функции полноценно доступны мышью, клавиатурой, обычными формами, навигацией. Не оболочка мобильного приложения, не только голосовой ассистент, не только чат, не пустой dashboard, не демонстрация технологий.
- **Голос и текстовые команды — дополнительные способы управления уже существующими функциями.** Пользователь взаимодействует голосом **и** текстом; текстовый ввод всегда доступен; микрофон не обязателен.
- Ответ может одновременно показываться текстом и озвучиваться.
- Основные возможности не зависят от платного AI; AI — дополнительный слой, а не ядро.
- Частичная работа без интернета — желаемое будущее свойство; сложная offline-синхронизация не является условием запуска web-версии ([OFFLINE_SYNC.md](OFFLINE_SYNC.md), [ADR-007](DECISIONS.md)).
- Расширение модулями; пользовательские типы сущностей ([DATA_MODEL.md](DATA_MODEL.md)).
- Пользователь контролирует память, данные, команды и автоматизации ([DATA_MODEL.md](DATA_MODEL.md), [SECURITY.md](SECURITY.md)).
- Опасные действия требуют подтверждения ([COMMAND_ENGINE.md](COMMAND_ENGINE.md), раздел 6).
- Приватность и безопасность с самого начала ([SECURITY.md](SECURITY.md)).
- В будущем (Stage 5–6): мобильные приложения и desktop-agent ([FUTURE.md](FUTURE.md)).

## 3. Общая схема (верхний уровень)

```
Источники команд                         Ядро                            Данные и исполнение
┌──────────────────────┐    ┌───────────────────────────────┐    ┌─────────────────────────────┐
│ Web UI (текст/голос) │    │ Command Engine                │    │ Модули (день, задачи, авто, │
│ Mobile (будущее)     │ →  │ нормализация → intent →       │ →  │ финансы, память, ...)       │
│ Automation           │    │ параметры → entities →        │    │ Action Core → выполнение    │
│ API                  │    │ confidence → уточнения →      │    │ Хранилища (БД, файлы, кэш)  │
│ Desktop-agent (буд.) │    │ подтверждение → Action        │    │ Уведомления                 │
│ AI Router (будущее,  │    └───────────────────────────────┘    │ Синхронизация (офлайн)      │
│ опционально)         │                                         └─────────────────────────────┘
└──────────────────────┘
```

### 3.1. Единый путь действия (Web-first, [ADR-013](DECISIONS.md))

```
UI / Forms
        \
Text command → Action Core → Business Logic → Data
        /
Voice → STT → Text command

Result → UI
       → Text response
       → TTS (если включено)
```

Отдельная бизнес-логика для UI, текста и голоса **не создаётся**: все пути ведут к одному Action/Use Case (пример — [FEATURES.md](FEATURES.md), раздел 2.7).

Подробная декомпозиция Command Engine — [COMMAND_ENGINE.md](COMMAND_ENGINE.md); голосовой путь — [VOICE.md](VOICE.md).

### 3.2. Help и Guided Tutorial (прототипное направление, не ADR)

В `/prototype` добавлен отдельный reusable слой обучения:

```
Help Center / Contextual Help
        ↓
Tutorial Engine → declarative tutorial definitions → overlay/highlight/progress
        ↓                                      ↓
обычный UI path / Common Actions          optional existing TTS narration
```

Правила этого слоя:

- обучение не создаёт отдельные task/event copies и не дублирует business logic;
- если tutorial взаимодействует с сущностями, он ведёт пользователя через существующий UI и Common Action Layer;
- голосовое сопровождение — optional adapter к существующему frontend TTS (`AvenVoice`/`AvenTTS`), а не новая voice infrastructure;
- текст инструкции всегда остаётся основным, narration не заменяет доступный UI/screen-reader text.

Это фиксирует направление UX-подсистемы прототипа, но не утверждает production framework.

### 3.3. Suggestions (прототипное направление, не ADR)

`AvenSuggestions` — тонкий DOM-free read/decision слой над общим состоянием: `state + date context →
ordered explainable suggestions`. Вычисляемая карточка не копируется в данные; сохраняется только реакция
пользователя (`suggestionState[id]`: dismiss/snooze). Stable ID строится из правила, исходной сущности и
даты контекста, поэтому повторный render не создаёт дубль. Мутация реальной сущности делегируется Action
Core, а suppression записывается в общий History/Undo. Home, Day, Assistant и Morning/Evening
используют один контракт. Notification сообщает о факте/сроке; Suggestion предлагает действие — read/unread
модель уведомлений в Suggestions не переносится. Правила локальные, детерминированные и не требуют AI.

### 3.4. Daily Summary (утро/вечер; прототипное направление, не ADR)

`AvenDaily` — тонкий DOM-free агрегатор над уже существующими слоями: `getMorning(context)` и
`getEvening(context)` читают общий state через Common Actions (`tasks/events/dates`), движок уведомлений
(`AvenNotify`) и `AvenSuggestions`, и возвращают структурированную сводку
(`summary`, списки сущностей, `nextEvent`, `tomorrow`, `empty`, `errors`). Контракт:

- **read-only:** получение сводки не мутирует состояние и не создаёт новых сущностей;
- **shared entities:** возвращаются те же задачи/события/уведомления/предложения, что и в разделах;
- **deterministic:** все даты берутся из общего demo clock (`AvenActions.dates`), поэтому «сегодня»/«завтра»
  совпадают с «Днём», «Задачами», «Календарём», «Уведомлениями» и Suggestions;
- **error resilience:** сбой одного источника попадает в `errors[]` и не ломает остальную сводку;
- **мутации отдельно:** `rescheduleToTomorrow` и `planTomorrowTask` — тонкие обёртки над `task.update` /
  `task.create` Action Core, поэтому History/Undo работает без отдельного механизма;
- **минимальное состояние сценария:** `dailyState.{morning|evening} = { dateISO }` — только маркер
  прохождения; копия сводки не сохраняется и вторым источником данных не становится;
- **готовность к Assistant:** `summaryText(kind)` отдаёт готовый текст для будущих команд «Что у меня
  сегодня?»/«Как прошёл день?»/«Что завтра?» без нового parser/NLP.

Morning/Evening — guided-слой поверх этих данных; «День» остаётся рабочим центром выбранной даты.


### 3.5. Text Command Engine (прототип Stage 2, первая итерация; не production ADR)

В `/prototype` появился слой между текстом и Action Core — `AvenCommand` (`prototype/js/command.js`):

```
text → normalize → parse → structured intent
                         → execute → Common Actions / Common Queries
                         → structured result → respond → человеческий ответ
```

Границы слоя (проверяются тестами `command-engine-check.js`):

- **DOM-free ядро:** в `command.js` нет `document`, `innerHTML`, обработчиков событий; экран
  помощника — отдельный адаптер. Это же позволит Stage 3 подать распознанный текст в тот же вход,
  без `voiceCreateTask()`-подобных дублей;
- **parse без side effects:** разбор не меняет состояние и не пишет историю; `execute` вызывается
  только после успешного разбора и проверки;
- **нет второго слоя записи:** все мутации идут через `AvenActions.tasks/events`, поэтому
  «История»/Undo, проверка ввода и бизнес-правила остаются в одном месте;
- **нет второй копии запросов:** обзор дня, просроченное, предложения, финансы и авто читаются
  теми же запросами, что и разделы;
- **общие часы:** «сегодня/завтра/пятница» берутся из `AvenActions.dates`, а не из `Date.now()`;
- **безопасность вместо догадок:** несколько подходящих сущностей → структурированная
  неоднозначность без мутации; разрушительные команды в первую итерацию не включены
  ([ADR-005](DECISIONS.md), [COMMAND_ENGINE.md](COMMAND_ENGINE.md) §6, §9.4);
- **ответ отделён от результата:** структурированный результат остаётся внутри API (tests/debug),
  пользователю показывается только обычный текст.

Фактический охват первой итерации — [COMMAND_ENGINE.md](COMMAND_ENGINE.md) §9. Это прототипное
направление, а не утверждённая production-архитектура.

### 3.6. Transient Command Session (Stage 2, итерация 2)

`AvenCommandSession` — DOM-free слой оркестрации между Assistant и `AvenCommand`:

```
Assistant → CommandSession (pending clarification/confirmation only)
          → AvenCommand resolve/execute → Common Actions → state/history
```

Он хранит только минимальный сериализуемый pending intent, фиксированный контекст общих часов и
references кандидатов/цели. Это interaction state, не business state: слой не импортирует `AvenState`,
не пишет History, не содержит Task/Event/Finance logic и не сохраняется в localStorage. Assistant —
единственный UI; Home передаёт текст в него. Сброс происходит после success/cancel/refusal/stale,
при новой распознанной команде и уходе с route. Перед конечной мутацией цель перечитывается через
Common Query; pending очищается до execute для защиты от двойного подтверждения.

`parse()` остаётся чистым; Entity Resolver возвращает дискретные `EXACT / INFERRED / AMBIGUOUS /
UNSUPPORTED`, без числовых confidence. Подробный contract и policy — [COMMAND_ENGINE.md](COMMAND_ENGINE.md)
§6, §10. Это развитие прототипного слоя, а не перевод ADR-004 или stack ADR в `Accepted`.

## 4. Action Core

Независимо от источника команда превращается в **стандартное действие**.

Источники:

- UI (формы/навигация — первоклассный источник при Web-first);
- текст (командная строка «Что сделать?», Assistant; Stage 2);
- голос (Stage 3, поверх Command Engine);
- Automation;
- API;
- в будущем — AI.

Примеры стандартных действий:

```
ADD_EXPENSE
ADD_FUEL
CREATE_REMINDER
CREATE_NOTE
GET_DAY_PLAN
SEARCH_DATA
UPDATE_MILEAGE
RUN_AUTOMATION
SPEAK
```

Правила:

- Бизнес-логика **не дублируется** отдельно для голоса и обычного UI.
- Каждое действие имеет: параметры (с типами), требуемые permissions, класс опасности (требует ли подтверждения), результат со статусом.
- Внутренние идентификаторы intents/actions — на английском (`expense.add`, `ADD_EXPENSE`); формулировки для пользователя — на языке пользователя через шаблоны ответов.
- Через Action Core идут и **команды изменения настроек** (`settings.voice.rate.set`, `settings.quiet_hours.set`, `settings.day_period.set`, `dictionary.alias.create`, `settings.voice.enabled.set`, `settings.confirmation_policy.set` — [ADR-011](DECISIONS.md), [PROJECT_PLAN.md](PROJECT_PLAN.md), раздел 12); они не обходят security requirements — для чувствительных настроек требуются подтверждение и/или повторная аутентификация.

**Прототипное направление (2026-09-27, не production ADR):** в `/prototype/js/actions.js` появился тонкий Common Action Layer. Изначально он покрывал задачи и события; к 2026-09-27 (Stage 1.1–1.3) контракт расширен на **все обязательные пользовательские сущности прототипа**: `tasks`, `events`, `profile`, `settings`, `notes`, `finance`, `auto`, `shopping`, `reminders` плюс общие справочники и форматирование (`options`, `format`, `dates`, `money`). Форма контракта не менялась: `action(params) → { ok, action, entity | code, message }`, проверка ввода и бизнес-правила живут в слое, каждое изменение пишет запись истории с обратной операцией (`value | remove | fields | restore | batch`). Он подтверждает продуктовый путь `UI / Text Command / Voice→STT → Common Action Layer`: UI вызывает эти actions, Assistant demo-flow использует `createEvent(...)` и общие запросы, а будущий Command Engine сможет вызвать те же операции без второго пути записи. Это не фиксирует окончательный backend/API/framework; это проверка границы «параметры → изменение state → structured result/history» в UX-прототипе.

Пример преобразования фразы:

```
«Потратил сегодня 1250 рублей на бензин»
→ intent = expense.add
  amount = 1250
  currency = RUB
  category = fuel
  date = today
```

## 5. Command Engine (сводка)

Подробно — [COMMAND_ENGINE.md](COMMAND_ENGINE.md). Состав компонентов: нормализация текста; определение намерения; извлечение параметров; разбор дат, времени, денежных значений, чисел; Entity Resolver; контекст; confidence score; запрос недостающих параметров; подтверждение; выполнение Action; генерация шаблонного ответа.

Если информации недостаточно — Aven задаёт уточнение («Напомни завтра позвонить» → «В какое время?» → «В десять» → создание напоминания завершено). Потенциально опасные или существенные данные не угадываются.

## 6. AI — OPTIONAL, NOT REQUIRED

Первая архитектура **не требует** платного LLM API для базовой работы.

В будущем AI может использоваться как:

- более свободный language parser;
- intent router;
- помощник по сложным запросам;
- дополнительный интерфейс.

Предпочтительная схема:

```
Human input
→ AI Router (опционально)
→ строго определённый Action + parameters
→ permission validation
→ execution
```

Ограничения:

- AI **не имеет неконтролируемого прямого доступа** к базе или системным операциям.
- При отсутствии AI или интернета основные функции продолжают работать.

## 7. Голосовой слой

Голос — **слой поверх текстового Command Engine** (Stage 3): Business Logic не связывается непосредственно с Speech Recognition (`audio → STT → text → Command Engine`). Заменяемый слой STT/TTS, изолированный за интерфейсами. Для веб-версии рассматриваются системные браузерные возможности (Speech Synthesis API — TTS; Web Speech API — STT там, где доступно); поддержка браузерами **не считается гарантированной**, предусмотрен fallback на текст; ни одна базовая функция не зависит от микрофона/STT/TTS ([PROJECT_PLAN.md](PROJECT_PLAN.md), раздел 6.2). Полная спецификация — [VOICE.md](VOICE.md).

## 8. Память и данные

Память Aven — контролируемая, разделена на профиль, объекты, факты, структурированную историю, временный контекст диалога, пользовательский словарь и команды, сценарии/автоматизации, предпочтения поведения. Есть интерфейс «Память Aven» для просмотра/редактирования/удаления. Aven не сохраняет бесконтрольно каждую фразу как постоянную память. Сущности связываются между собой без дублирования данных. Подробно — [DATA_MODEL.md](DATA_MODEL.md).

## 9. Автоматизации

Automation Canvas — node-based редактор (класс n8n, собственная реализация и UX), **Stage 4**: реализуется после стабилизации базовых данных и Action Core и не должен задерживать создание полезного сайта. На раннем этапе возможны готовые автоматизации, простые правила, расписания. Workflow сохраняются и выполняются независимо от открытого редактора, если их характер это предполагает. Запрет произвольного пользовательского JS на сервере; каждый серверный блок — зарегистрированная операция (входы, выходы, permissions, validation, resource limits). Подробно — [AUTOMATION.md](AUTOMATION.md).

## 10. Offline (перспектива)

Offline/local-first — желаемое будущее свойство (особенно для мобильных приложений); **не** обязательное условие запуска первой web-версии. Для Web допустимы локальные возможности браузера там, где это даёт практическую пользу, без сложной распределённой sync-системы до подтверждённой необходимости. Части [OFFLINE_SYNC.md](OFFLINE_SYNC.md) — статус Future/Under Design.

## 11. Честность статусов

Aven не должен делать вид, что действие выполнено, если оно не выполнено. Различаются:

- успешно;
- ожидает синхронизации;
- запланировано;
- требует подтверждения;
- ошибка;
- недоступно офлайн;
- платформа не поддерживает.

Это особенно важно для voice, notifications, integrations и desktop/mobile операций.

## 12. Безопасность и приватность

Security by design: хеширование паролей современным алгоритмом, безопасные сессии/tokens, CSRF/XSS/SQLi-защиты, валидация, authorization на каждом объекте, rate limiting, шифрование secrets, разделение данных пользователей, аудит админ-действий, управление устройствами/сессиями, 2FA, backup + restore testing, export/delete account, least privilege, явные permissions для device-агентов и интеграций, подтверждение разрушительных действий. Подробно — [SECURITY.md](SECURITY.md) и [ADMIN.md](ADMIN.md).

## 13. Кроссплатформенность (перспектива, Stage 5–6)

**Web-first ≠ Web-only** ([ADR-013](DECISIONS.md)): архитектура должна позволять дальнейшее развитие в PWA, Android, iOS, desktop, integrations — но эти платформы не являются текущей целью разработки. Не создавать искусственных архитектурных препятствий будущим клиентам: **Backend/API и Business Logic проектируются так, чтобы позже их могли использовать другие доверенные клиенты**. Сначала — полезный и проверенный веб-продукт; затем по реальному использованию определяется набор функций мобильных приложений. Desktop-agent — только с явного согласия, контролируемые permissions. Подробно — [FUTURE.md](FUTURE.md).

Архитектурные следствия, которые документ фиксирует как **предложения** (не решения):

- **Один Action Core важнее удобства веб-фреймворка**: доменная логика живёт в backend-модулях (`packages/core`),
  а не в UI-слое — иначе Stage 2 (текст), Stage 3 (голос) и Stage 5–6 (мобильные/desktop-клиенты) получат
  вторую реализацию той же логики, что запрещено разделом 4 этого документа.
- **Модульный монолит, а не микросервисы** на Stage 1: одна транзакционность для Undo/аудита/подтверждений
  ([ADR-005](DECISIONS.md), [ADR-010](DECISIONS.md)); границы модулей соблюдаются так, чтобы вынос был возможен позже.
- **Минимум инфраструктурных компонентов**: очередь задач в PostgreSQL ([ADR-106](DECISIONS.md)), отдельный
  кэш-сервер не вводится до измеренной необходимости ([ADR-107](DECISIONS.md)), файлы — за абстракцией
  `StorageProvider` ([ADR-108](DECISIONS.md)).
- **Автоматизации без произвольного JS** ([ADR-006](DECISIONS.md)): движок автоматизаций — данные/ограниченный
  DSL, что влияет на выбор очереди и хранение определений (DATA_MODEL §2.7), но не требует внешнего движка правил.
- Новые ADR-предложения: [ADR-109](DECISIONS.md) (доступ к данным), [ADR-110](DECISIONS.md) (аутентификация),
  [ADR-111](DECISIONS.md) (контракт API), [ADR-112](DECISIONS.md) (тестирование), [ADR-113](DECISIONS.md) (деплой).
  Все — `Proposed`, реализация до `Accepted` запрещена.
