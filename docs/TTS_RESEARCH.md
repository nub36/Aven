## 1. Задача и критерии

Сейчас Aven говорит браузерным `speechSynthesis` — на многих устройствах это звучит роботизированно.
Нужен естественный русский женский голос: молодая взрослая женщина, спокойная, дружелюбная, уверенная;
не диктор новостей, не ребёнок, не мультяшный, не робот; правильные ударения, интонация, паузы;
корректное произношение времени, дат, денег, автомобильных данных, чисел, уведомлений.

Ограничения: без AI/LLM, без платных API и подписок, без карт/триалов; неясная лицензия → не использовать;
личные данные не отправлять во внешние TTS; честно показывать Local / Cloud.

Целевая задержка до начала звука: идеал < 1 с, приемлемо 1–2 с, 5–10 с — плохо.

## 2. Методика

- **Одинаковые фразы для всех движков** — `research/tts/phrases.json` (T1–T10 из задачи + короткая
  фраза «Готово.» для замера задержки коротких ответов). Тексты подаются уже в «речевом» виде
  (числа словами), чтобы сравнивать голоса, а не чужие нормализаторы. Aven → «Авен» (см. §9, вопрос 1).
- **Где запускалось.** В песочнице агента скачивание весов с Hugging Face / silero.ai / alphacephei
  заблокировано, поэтому генерация идёт в **GitHub Actions** (`.github/workflows/tts-research.yml`,
  в пределах бесплатной квоты минут Actions; без карт и платных сервисов): обычный CPU-раннер **AMD EPYC 7763, 4 vCPU, 16 ГБ RAM, без GPU**.
  RHVoice собран из исходников и запущен в песочнице (Intel Xeon 2,6 ГГц, **2 vCPU**, 3,8 ГБ, без GPU).
- **Метрики** (`research/tts/results/*.json`): время синтеза каждой фразы (первый «холодный» вызов
  отдельно), длительность аудио, RTF = синтез / длительность (< 1 — быстрее реального времени),
  время загрузки модели, медианная частота основного тона F0 (грубая проверка «женский голос»).
- **Разборчивость (объективно):** ASR round-trip — образец распознаётся Whisper small (faster-whisper,
  CPU), цифры в распознанном тексте переводятся в слова тем же нормализатором, что в прототипе,
  считается WER относительно исходного текста (`research/tts/asr_eval.py`, `results/asr.json`).
  WER ловит проглоченные/искажённые слова и числа, **но не измеряет естественность** — её оценивает владелец на слух.
- **Честно:** агент не может слушать аудио. Оценки «натуральности» ниже — это репутация модели
  и объективные метрики, а не субъективный вердикт. Решение — только после прослушивания.
- **Прослушивание:** `prototype/voice-lab.html` — образцы по фразам, слепой режим (A/B/C без названий,
  случайный порядок), оценки ★ (хранятся локально, копируются текстом), для сравнения — текущий системный голос.
  MP3-образцы: `prototype/assets/voice-samples/<engine>/<voice>/tNN.mp3`.
- **Компактный набор в git (вариант Б, решение владельца):** 193 MP3 ≈ 5,2 МБ вместо 425 MP3 ≈ 11 МБ.
  Полный набор T1–T10: Supertonic F1–F5, Qwen3 (Serena, Vivian, клон дизайн-голоса), Chatterbox (default, клон),
  RHVoice Elena / Dasha. Silero CIS MIT — 17 женских голосов × T1, T3, T4, T6. Каталог T1: Qwen3 Ono_Anna, Sohee,
  эталон VoiceDesign. eSpeak — T1 и T3 (эталон «робота»).
  В git **не хранятся** аудио: Silero v5_5_ru (NC), Piper Irina и Vosk (неясная лицензия), RHVoice Anna / Irina
  (лицензия не указана), Silero `__nostress`, мужские/низкие голоса, `ru_igor` (мужское имя). Их метрики и
  разборчивость остаются в `research/tts/results/*.json`, а аудио воспроизводится скриптами.
  Состав задаётся в `research/tts/candidates.json` → `publish`; `collect.py` удаляет всё, что в него не входит,
  и строит `manifest.js` только по реально существующим файлам.
- **Повторить:** Actions → «TTS Research» → Run workflow (**только вручную**, при push не запускается;
  поле `engines` или список по умолчанию в `research/tts/ENGINES`). Полные WAV — в артефактах запуска (14 дней),
  в git попадают только метрики и компактный набор MP3. Локально: `pip install …` + `python research/tts/gen_<engine>.py`,
  затем `python research/tts/collect.py research/tts/out`.

## 3. Классы решений

|---|---|---|
| **A** — браузер / ОС | `speechSynthesis`, голоса ОС | Текущий путь. ## 6. Shortlist для прослушивания (3–5), без выбора за владельца

1. **Silero v5 CIS base (MIT)** — единственный найденный вариант «нейросетевой русский голос +
   чистая разрешительная лицензия + мгновенно на дешёвом CPU (≈0,25 с на фразу, 0,07 с на «Готово.»)».
   Риск — акцент дикторов (носители языков СНГ): слушать 17 женских голосов, выбрать 1–3 лучших.
   Поднимается на любом VPS/домашнем ПК без GPU. Нужен PyTorch на сервере.
2. **Supertonic 3 (OpenRAIL-M)** — может работать **прямо в браузере** пользователя (максимальная приватность,
   без сервера). На CPU ≈ 2 с на фразу при 8 шагах (можно уменьшить шаги ценой качества). Риски:
   архивированный репозиторий, мультиязычные (не русские) голоса, use-based ограничения OpenRAIL-M.
3. **Qwen3-TTS (Apache-2.0)** — лучший потенциал «живого» голоса и единственный с Voice Design

   Имеет смысл только с GPU-сервером (стоимость — решение владельца).
4. **Chatterbox Multilingual (MIT)** — клонирование тембра по референсу (нужна запись диктора с согласием
   или голос с лицензией, допускающей клонирование). На CPU ≈20–25 с на фразу — только с GPU. Результаты — §5.
5. **RHVoice Elena (GPL-3.0) / Dasha (CC BY-SA)** — запасной «лёгкий офлайн» вариант: мгновенно, крошечный,
   но звучит синтетично. Заметно лучше eSpeak, но не решает задачу «естественного» голоса.

### 11.2. Произношение «Aven / Авен» — главный открытый вопрос

Экранный текст **не меняется** нигде: пользователь всегда видит «Aven». Меняется только то, что мы
отдаём в TTS (нормализация для речи, `prototype/js/tts/normalize.js`, словарь `Aven → Авен`).
Проверены 4 варианта на одной и той же фразе «Aven слушает вас.»:

| id | Что подано в TTS | Аудио, с | Что услышал Whisper small | WER | Оценка |
|---|---|---|---|---|---|
| x17 | `Aven слушает вас.` (латиница, **без** нормализации) | 1,12 | «**Ай, вен** слушит вас!» | 100% | ❌ То самое «Эйвен»: **нормализация обязательна** |
| x18 | `Авен слушает вас.` (текущий словарь) | 2,24 | «А вен слушает вас.» | 67% | ⚠️ Лучший из четырёх, но первый слог распознался как отдельное «А» — похоже на редукцию/ударение на второй слог |
| x19 | `А́вен слушает вас.` (знак ударения на А) | 2,56 | «**Айф**, слушает вас.» | 50% | ❌ Знак ударения модель не понимает и ломает произношение |
| x20 | `Авэн слушает вас.` (через «э») | 1,20 | «А **вон** слушает вас.» | 67% | ❌ «э» даёт неожиданный гласный, хуже, чем «Авен» |

Дополнительно: в этапе 1 сохранённый клип T1 (тот же голос, та же фраза «Здравствуйте. Я Авен…»)
Whisper расслышал как «Я **Аван**» — то есть проблема не в конкретной генерации, а в том,
как модель читает слово «Авен» целиком.

**Вывод (честно):** ни один из четырёх вариантов не даёт эталонного «А́вен» по данным ASR.
ASR — не ухо, но сигнал устойчивый и повторяется на разных фразах. Вариант **x18 (текущий словарь
«Авен») — лучший из проверенных**; знак ударения и подмена «е» на «э» делают только хуже.
Окончательное решение — за владельцем: нужно послушать x17–x20 на странице теста
(там есть кнопка «Проиграть 4 варианта»).

> ⚠️ **Поправка этапа 2.1 (2026-09-25, §16.1).** Формулировка «ни один вариант не даёт эталонного «Авен»»
> оказалась следствием **словесного** WER: Whisper пишет «А вен» двумя токенами, и метрика наказывает
> за разбиение, а не за звук. Побуквенная метрика `name_lwer` (§16.1) показывает: **x18 — точное «авен» (0%)**,
> тогда как x17 — «айвен», x19 — «айф», x20 — «авон». То есть текущий словарь «Авен» по данным ASR корректен;
> открытый вопрос сузился до **ударения и паузы** (их ASR не измеряет — только ухо владельца).
> Таблица ниже сохранена как историческая; актуальные данные — §16.2.

**Если x18 не устроит — рабочие способы (проверить отдельным мини-прогоном, пока не делали):**

1. **Обучение произношению через in-context learning.** 0.6B/1.7B-**Base** принимает
   `create_voice_clone_prompt(ref_audio, ref_text)`: в `ref_text` включаем имя, и модель повторяет
   услышанное произношение. Это самый контролируемый путь — но требует эталонного клипа, где «Авен»
   сказано правильно (синтезировать/записать и прослушать).
2. **Подсказка в промпте описания голоса** (для VoiceDesign) или в `instruct` (CustomVoice) —
   например, явно указать произношение. Ненадёжно: промпт влияет и на тембр, придётся переслушивать голос.
3. **Перебор орфографии** («А́вен» уже проверен — не работает; остаются «А́вэн», «Авен» с двумя «н»,
   разбиение «А-вен» и т. п.). Дёшево, но каждый вариант надо слушать.
4. **Готовый образец для имени**: самые частые реплики с названием («Я Авен, ваш помощник»)
   записать один раз и переиспользовать (вариант D §13) — мгновенно и 100% предсказуемо.

Все четыре пункта в этом прогоне не проверялись → **проверены в этапе 2.1 (§16)**: способы 1–3
 прогоном на CPU-раннере, способ 4 остаётся механизмом продукта (генерации не требует).

### 12.2. Опубликованные данные разработчика (не наши измерения)

Qwen3-TTS Technical Report ([arXiv:2601.15621](https://arxiv.org/html/2601.15621v1), таблица 2) —
потоковая эффективность; измерено **на внутреннем vLLM-движке (vLLM V0)** с `torch.compile` и CUDA Graph,
модель GPU в отчёте не указана:

| Модель | Конкуренция | LM TTFP | Декод токенайзера | First-packet latency | LM TPP | RTF |
|---|---|---|---|---|---|---|
| Qwen3-TTS-12Hz-1.7B | 1 | 97 мс | 4 мс | **101 мс** | 21 мс | 0,313 |
| Qwen3-TTS-12Hz-1.7B | 3 | 190 мс | 5 мс | 195 мс | 24 мс | 0,363 |
| Qwen3-TTS-12Hz-1.7B | 6 | 328 мс | 5 мс | 333 мс | 32 мс | 0,463 |
| Qwen3-TTS-12Hz-0.6B | 1 | 93 мс | 4 мс | **97 мс** | 19 мс | 0,288 |
| Qwen3-TTS-12Hz-0.6B | 3 | 174 мс | 5 мс | 179 мс | 22 мс | 0,338 |
| Qwen3-TTS-12Hz-0.6B | 6 | 294 мс | 5 мс | 299 мс | 30 мс | 0,434 |

Как это читать:

- **97–101 мс** — время до **первого пакета** звука при потоковой выдаче (не вся фраза). Это «теоретический
  оптимум» разработчика на их стенде; в реальности добавятся сеть, очередь, прогрев и плеер.
- **RTF 0,29–0,46** — генерация быстрее реального времени: фраза длительностью 3 с «собирается» примерно
  за 0,9–1,4 с, при потоковой выдаче воспроизведение начинается почти сразу и не догоняет генерацию.
- При 6 одновременных запросах first-packet latency остаётся < 350 мс — то есть один GPU держит
  несколько одновременных разговоров.
- **Наша оценка-гипотеза (не измерение):** при self-hosted GPU и потоковой выдаче «Готово.»/«Слушаю.»
  зазвучит через ≈ 0,2–0,5 с, обычная фраза — ≈ 0,3–0,8 с до первых звуков. Проверить на целевом железе.

### 12.3. VRAM и класс GPU

Размеры весов — из карточек моделей Hugging Face (BF16):

| Модель | Веса модели | Токенайзер 12 Гц | Итого на диске | Практическая оценка VRAM | Разумный класс GPU |
|---|---|---|---|---|---|
| Qwen3-TTS-12Hz-**1.7B** (VoiceDesign / Base / CustomVoice) | 3,83 ГБ (1,92 млрд параметров BF16) | 0,68 ГБ | **4,5 ГБ** | **≥ 8 ГБ, комфортно 12 ГБ** (веса + KV-кэш + CUDA Graph) | RTX 4070 Ti / 4080 / 3090 / 4090, L40S, A100 |

### 12.4. Держать ли модель загруженной

Да, обязательно: это убирает из пути запроса загрузку весов (у нас на CPU — 22,7 с; на GPU — чтение
4,5 ГБ с диска + инициализация CUDA, оценивается секундами, измерить на целевом железе) и прогревы
компиляции/CUDA Graph. Практически — долгоживущий процесс:

- `vllm serve Qwen/Qwen3-TTS-12Hz-1.7B-VoiceDesign --omni --port 8091` (vLLM-Omni, см. §12.5);
- либо свой процесс с `qwen_tts.Qwen3TTSModel`, загруженным один раз, и HTTP-обёрткой
  (так устроен исследовательский `research/tts/server.py`);
- после старта — 1–2 «холостых» запроса на прогрев, чтобы первый реальный пользователь не получил
  холодный старт;
- модель в режиме kept-alive ест VRAM постоянно, поэтому один сервер = одна задача (CustomVoice /
  VoiceDesign / Base — vLLM-Omni поднимает один чекпоинт за раз).

## 13. Как подключать Qwen3 к Web Aven (варианты, без утверждения)

```
Aven Web (браузер)
   → POST /api/tts  (текст ответа, уже нормализованный для речи; экранный текст не меняется)
      → Aven TTS API (свой сервер; текст не уходит третьим лицам)
         → Qwen3-TTS (GPU, модель загружена постоянно)
            → audio/wav или PCM-поток
               → браузер: HTMLAudioElement / MediaSource / Web Audio (AudioWorklet)
                  → воспроизведение

Fallback (обязателен): сервер недоступен/таймаут/нет GPU
   → SystemTTSProvider (speechSynthesis) + честный статус для пользователя
```

| Вариант | Ожидаемая latency | Приватность | Стоимость (ориентир) | Сложность | Комментарий |
|---|---|---|---|---|---|
| **A. Свой GPU-сервер** (vLLM-Omni, self-hosted) | до первого звука ≈ 0,1–0,5 с (streaming), фраза целиком ≈ 0,3–1,5 с | **полная**: текст и аудио не покидают ваш контур | CAPEX на GPU (см. §12.3) + электричество/размещение; без платных подписок | средняя/высокая: CUDA-драйверы, vLLM, мониторинг, обновления | Целевой путь при утверждении голоса. Тот же сервер пригодится для будущего 3D (§14). |
| **B. GPU cloud / on-demand** | то же, что A (зависит от железа) | текст уходит на арендованный инстанс (ваш, но чужой ЦОД) | published rates (сен. 2026, страницы провайдеров): RTX 4090 ≈ $0,34–0,74/ч, L40S ≈ $0,79–1,09/ч, A100 ≈ $1,59/ч, H100 ≈ $2,89/ч → 24/7 на 4090 ≈ $250–540/мес | средняя: те же CUDA/vLLM + управление жизненным циклом инстанса | Хорош как **пилот без CAPEX** и как serverless с масштабированием в ноль; постоянно включённый инстанс дороже своего сервера уже через несколько месяцев. |

Плюс не у всех включён WebGPU. |
| **D. Готовые образцы + кэш** | мгновенно | локально | бесплатно | низкая | Работает только для фиксированных реплик. Уже используется в прототипе; оставить как «уровень 0». |

Практические заметки к будущей интеграции (если владелец утвердит голос):

- Нормализация выполняется **в браузере до отправки** (`prototype/js/tts/normalize.js`): на сервер уходит
  уже «речевой» текст, экранный текст Aven не меняется. Персональные данные (суммы, адреса, имена)
  не должны логироваться на TTS-сервере — в исследовательском `server.py` логирование текста уже отключено,
  сохранить это правило.
- Кэш: короткие реплики и часто повторяемые фразы — в памяти/на диске сервера (по хешу нормализованного
  текста), чтобы «Готово.» звучало мгновенно. Фразы с персональными числами — не кэшировать.
- Chunking по предложениям — обязателен для длинных ответов (x16): играем первое предложение, пока
  генерируется второе.
- Fallback-политика: таймаут (например, 2–3 с до первого аудио) → System TTS + честный статус
  («натуральный голос недоступен, говорю системным»). Пользователь не должен ждать молча.
- Очередь и лимиты: один GPU держит ~3–6 параллельных генераций (см. таблицу §12.2), дальше — очередь.
- **Какая модель стоит на сервере — отдельный вопрос (этап 2.1, §16).** `1.7B-VoiceDesign` пересоздаёт голос
  на каждый вызов (по промпту описания), поэтому официально рекомендуемый пайплайн — спроектировать голос
  **один раз**, сохранить эталонный клип и дальше генерировать **Base-клоном** (`create_voice_clone_prompt`
  по эталону: 0,4 с один раз, затем переиспользуется). Наши данные: клон 0.6B-Base устойчивее на коротких
  репликах («Слушаю.» — 0% против провала x03 у VoiceDesign) и точно произносит «Авен» в развёрнутой фразе,
  но его **тембр на слух не сравнивался** с ★5-эталоном, а клон 1.7B-Base по имени оказался хуже («Авент»,
  «Овен»). Выбор «VoiceDesign vs Base-клон» — за владельцем после прослушивания (§15, вопросы 2–3).
- **Готовые образцы имени и коротких реплик** (вариант D) — не «костыль», а основной способ гарантировать
  произношение «Авен»: приветствие/представление генерируется один раз и переиспользуется (§16.4, п. 5).

## 14. Lip-sync / viseme timing для будущего 3D Female Aven

**Отдаёт ли Qwen3-TTS тайминги напрямую? НЕТ.** Проверено по исходникам `qwen-tts` 0.1.1:
`generate_voice_design/generate_custom_voice/generate_voice_clone` возвращают `(List[np.ndarray], int)`
— только аудио и частоту; в публичном API нет ни `align`, ни `phoneme`, ни `duration`, ни `timestamp`
(поиск по пакету это подтверждает). В vLLM-Omni `/v1/audio/speech` тоже отдаёт только байты аудио.
То есть цепочку «TTS → фонемы» придётся строить самим.

Рабочая схема:

```
текст ответа ──→ TTS (Qwen3) ──→ audio.wav
                                    │
                (A) forced alignment по тексту + аудио → фонемы/слова с таймингами
                                    │
                (B) маппинг фонема → висима (набор форм рта) → кривые для блендшейпов
                                    │
                                 → 3D-лицо (Three.js / Ready Player Me / свой риг)
```

Варианты (все — «на будущее», ничего не реализовано):

| Инструмент | Что даёт | Лицензия | Русский | Комментарий |
|---|---|---|---|---|
| **Уровень 0: амплитуда** (Web Audio `AnalyserNode` → RMS) | только «открыто/закрыто» рта, без артикуляции | — | да | 30 строк без зависимостей. Для первой демо-анимации достаточно; фонем нет. |
| **Rhubarb Lip Sync** | готовые `mouthCues` (9 форм рта A–H + X) с таймингами по аудио; вход — WAV + (опционально) текст | **MIT** (и deps MIT/BSD) | фонетический режим **не зависит от языка** (PocketSphinx-режим — только английский) | Самый быстрый путь к качественным виземам. Есть [WASM-порт (MIT)](https://github.com/danieloquelis/rhubarb-lip-sync-wasm) → можно считать и в Node/браузере. |
| **Montreal Forced Aligner (MFA)** | посекундные фонемы и слова (Praat TextGrid) | **MIT** | да: русский G2P (точность 96,4%) и русские акустические модели | Точнее Rhubarb по границам (медиана отклонения ~12,5 мс), но тяжелее в эксплуатации (Kaldi, 16 кГц моно, словарь). |
| **WhisperX** | word-level тайминги (есть русский wav2vec2-aligner), опция char-level | BSD-2 | да | Уже используется у нас для ASR-проверки образцов → можно переиспользовать стенд. |
| **NeMo Forced Aligner** | token/word/segment-выравнивание | Apache-2.0 | через русские CTC-модели NeMo | Тяжеловесный стек (NVIDIA NeMo). |
| **torchaudio `MMS_FA`** | char-level выравнивание | код BSD-2, **веса `facebook/mms-1b-fl102` — CC BY-NC 4.0** | да | Для коммерческого продукта **под вопросом** из-за NC-лицензии весов. |
| **Oculus OVRLipSync / NVIDIA Audio2Face / Azure viseme events** | готовые визимы (у Azure — 22 визимы, событие `visemeReceived`) | проприетарные SDK / облако | частично | Облачные — текст уходит третьему лицу; на текущих правилах приватности не подходят. |

Предварительный план (когда дойдём до 3D, не сейчас):

1. Сначала — уровень 0 (амплитуда) для проверки рига и таймингов плеера.
2. Затем — Rhubarb (WASM, MIT) по готовому аудио + тексту: быстро, без серверных зависимостей,
   языконезависимый фонетический режим.
3. Если понадобится точность фонем — MFA на сервере (MIT, русский G2P) с маппингом фонем в 9–15 визим.
4. Маппинг «висима → блендшейп» держать в отдельном модуле, чтобы менять движок lip-sync независимо от TTS.

## 15. Статус после этапа 2 и обновлённые вопросы владельцу

**Что зафиксировано:**

- `qwen3/vd17-design` (Qwen3-TTS-12Hz-1.7B-VoiceDesign, один и тот же промпт описания голоса) —
  **фаворит владельца (★5, предварительно)** и главный кандидат.
- Это **не** утверждённая TTS-архитектура. Системный `speechSynthesis` остаётся движком по умолчанию
  и рабочим fallback; Qwen3 не является обязательной зависимостью Aven.
- Без GPU Qwen3 для диалога непригоден (§12.1). Любое внедрение = GPU-сервер (§13).
- Тайминги для lip-sync Qwen3 не отдаёт — нужен отдельный шаг (§14).

### 16.1. Новая метрика `name_lwer` (и поправка к выводу этапа 2)

Словесный WER непригоден для одного слова: Whisper пишет «А вен» двумя токенами, и метрика даёт 67%
ошибок там, где буквы сказаны верно. Поэтому в `asr_eval.py` добавлены производные метрики, которые
считаются **из уже сохранённых гипотез** (повторное распознавание не нужно: `python asr_eval.py --derive`;
посчитаны для всех 464 клипов в `results/asr.json`):

| Метрика | Что измеряет | Референс |
|---|---|---|
| `wer` | словесный WER — прежний смысл, сравнимость с этапом 1/2 сохранена | поданный в TTS текст (`speech`) |
| `twer` | словесный WER против **желаемого** звучания (у вариантов имени `speech` ≠ `target`) | `target` |
| `lwer` | то же побуквенно (пробелы/пунктуация убираются, ё→е) — не наказывает за «Авен» → «А вен» | `target` |
| **`name.letters` / `name.lwer`** | **что именно сказано вместо имени**: буквы имени вырезаются из гипотезы по якорям `name_prev`/`name_after` и сравниваются с «авен» | `name_target` |

Якоря ищутся нестрого (`difflib` + окно с минимальным расстоянием Левенштейна, допуск 3 буквы) — Whisper
сам пишет с ошибками. Если якорь не найден, пишется `name.error`, а не «0%». Вырезанные буквы сохраняются
в `results/asr.json`, поэтому каждую оценку можно проверить глазами по сырой гипотезе.
Ошибок выделения нет: метрика посчитана на **91 клипе** с якорями (79 прежних + 12 новых), `name.error` — 0.

**Поправка к §11.2:** по `name_lwer` вариант **x18 («Авен») — точное «авен», 0%**; «А вен» в гипотезе —
артефакт разбиения, а не другая буква. Вывод этапа 2 «ни один из четырёх вариантов не даёт эталонного
«Авен»» в этой части **снят**. Что метрика **не** показывает: ударение, паузу между «А» и «вен»,
естественность — это слышно только ухом (§16.5).

### 16.5. Ограничения прогона

- **ASR ≠ ухо.** `name_lwer` ловит замену букв, но не ударение, паузу, естественность. Все «0%» —
  повод послушать, а не вердикт. Модель распознавания — Whisper small; другая модель могла бы слышать иначе.
- **CPU, а не целевая среда.** RTF 6,4–12,0; у коротких реплик (1–2 с) RTF выше, потому что постоянные
  накладные расходы не амортизируются. Для диалога нужен GPU (§12) — выводы о скорости отсюда не переносятся.
- **Тембр клонов на слух не сравнивался.** n10–n13 и n20–n25 — это клон эталона n00, а не сам VoiceDesign:
  похож ли он на ★5-голос, решает только прослушивание (в этом прогоне не проверялось).
  1.7B-Base участвовал в нашем наборе впервые.
- **По одной генерации на вариант.** Устойчивость подтверждается только совпадением n01 и x18
  (два разных прогона, разные CPU) и n11 с t01 этапа 1. Полная проверка стабильности — отдельный прогон.
- **`first_call` у n01/n06** — артефакт группировки генератора (§16.2); исправлено в `gen_qwen3_name.py`,
  метрики прогона задним числом не правились.
- **Подсказка в промпте (n06/n07) не может стать «бесплатной правкой»:** если владелец выберет её,
  голос придётся переслушать целиком и, возможно, пересобрать эталон для клона.
- Голос **не внедрён**: `speechSynthesis` остаётся движком по умолчанию и fallback, ADR не создавался.

### 19.1 server.py 0.4.0 — production-like режим

Поверх исследовательского 0.3.0 добавлено (env-переменные, код один и тот же для research и VPS):

| Механизм | Поведение |
|---|---|
| `AVEN_TTS_HEALTH=minimal` | health = `{ok, status, server, version, max_chars, default_voice}` — без engines/voices/uptime, ничего лишнего о сервере |
| `AVEN_TTS_DEFAULT_VOICE` | `health.default_voice` — фронт предвыбирает голос сервера |
| `AVEN_TTS_RATE_N` / `_WINDOW_S` | rate limit по IP на `/api/tts/synthesize` (12/60 c), до чтения тела → `429` + `Retry-After`; 0 — выключен |
| `AVEN_TTS_BUSY_TIMEOUT_S` | ожидание лока движка (1 CPU, сериализация) → `503` |
| лимиты | тело > 20 КБ → `413`; текст > 600 симв. → `413`; пустой текст/неизвестный голос → `400` |
| методы | `PUT/DELETE/PATCH` и POST не на synthesize → `405` + заголовок `Allow` |
| `sanitize_text` | управляющие символы (кроме `\t\n\r`) вырезаются |
| приватность | текст запроса не логируется/не пишется (в логе — длина и время); warmup предпочитает DEFAULT_VOICE |

CORS-allowlist 0.3.0 сохранён (nub36.github.io + localhost + `AVEN_TTS_ORIGINS`).

### 19.2 Frontend: Natural = только сервер владельца

`checkServer` понимает minimal health (голоса добираются с `/api/tts/voices`, сохраняется
`default_voice`); менеджер speak() предвыбирает default_voice, если сохранённый голос
