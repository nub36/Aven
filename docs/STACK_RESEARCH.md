> **Статус:** исследовательский документ (по образцу [TTS_RESEARCH.md](TTS_RESEARCH.md)).
> **Ни одна рекомендация здесь не является решением.** Все технологические решения находятся в

> **Последнее обновление:** 2026-09-26. Версии, лицензии и цены — на эту дату по внешним источникам

## 1. Зачем этот документ

Stage 1 («полезный самостоятельный веб-сайт») по плану начинается **после** утверждения стека и способов
реализации: ADR из `Proposed` → `Accepted` ([PROJECT_PLAN.md](PROJECT_PLAN.md), раздел 4).
ADR-101…108 существуют, но в них нет сравнения альтернатив — ADR-101 сам помечает это открытым вопросом
(«обоснование framework против альтернативы «лёгкий собственный сервер»»). Открытые вопросы №3 (очередь
задач), №4 (обоснование кэширования) и №5 (стеки) в [PROJECT_PLAN.md](PROJECT_PLAN.md) — про то же самое.

Документ делает одну вещь: собирает **ограничения из наших же спецификаций → варианты по каждой области →
честные tradeoffs → рекомендацию → что проверить → конкретный список вопросов владельцу** (раздел 13),
чтобы решение можно было принять за один проход, а не исследовать с нуля.

Формат ответа владельца может быть простым: «R1 — вариант Б; фреймворк — Fastify; ORM — Drizzle; …» —
после чего ADR переводятся в `Accepted` и начинается Stage 1.

## 2. Требования к стеку, вытекающие из документов проекта

Это не пожелания, а уже зафиксированные принципы и спецификации — стек обязан им удовлетворять.

| Требование (источник) | Что это значит для стека |
|---|---|
| Web-first: сайт полноценно полезен мышью/клавиатурой/формами, без голоса ([ADR-013](DECISIONS.md), PROJECT_PLAN §6.2) | Нужен обычный веб с формами и навигацией. SEO/публичный контент не является целью → «SSR любой ценой» не обязателен |
| Один **Action Core** для UI, текста, голоса, автоматизаций, API; бизнес-логика не дублируется (ARCHITECTURE §4) | Доменная логика живёт в **backend-модулях**, а не в UI-фреймворке; клиент тонкий. Это главный аргумент в развилке R1 (раздел 3) |
| Основные функции без обязательного платного AI ([ADR-002](DECISIONS.md)) | Никаких внешних AI-сервисов в критическом пути; AI — опциональный слой |
| Опасные действия — подтверждение, история действий и Undo ([ADR-005](DECISIONS.md), COMMAND_ENGINE) | Транзакционность, журнал действий в БД, идемпотентность операций |
| Запрет произвольного пользовательского JavaScript на production-сервере ([ADR-006](DECISIONS.md), AUTOMATION) | Автоматизации = данные/ограниченный DSL, **не** `eval`/`vm` с пользовательским кодом |
| Пользователь контролирует данные; privacy/security by design ([ADR-008](DECISIONS.md), SECURITY §1–2) | Self-host или контролируемый хостинг; экспорт/удаление данных; шифрование secrets интеграций; регион хранения — решение владельца |
| Authentication + authorization **на каждом объекте**, audit админ-действий, 2FA там где нужно, управление сессиями (SECURITY §1) | Библиотека auth с сессиями в БД, TOTP, rate limits, принудительным завершением сессий; RBAC — своя (ADMIN §3) |
| Отдельные admin-сессии, 2FA по роли, rate limits, мониторинг подозрительной активности (SECURITY §10, ADMIN §13) | Админка — отдельный контур приложения, не отдельный продукт |
| Критический audit trail нельзя позволить незаметно удалить (SECURITY §11 — **механизм не выбран**) | Append-only таблица + отдельные права в БД; механизм — отдельный ADR (открытый вопрос №14) |
| Миграции, бэкап/восстановление, feature flags, health, emergency controls (ADMIN §5, 16–18, 21) | Миграции как код в репозитории + раздел админки; бэкап и **проверенное восстановление** — часть деплоя, а не дополнение |
| Пользовательские типы сущностей в будущем (DATA_MODEL §3.2) | Гибкая схема (JSONB) + версионирование определений сущностей |
| Финансовые данные: точность, история изменений, никакого «примерно» (SECURITY §5, FEATURES §7) | `numeric`/целые в минимальных единицах (копейки), никакой арифметики с float; аудит изменений суммы |
| Offline — желаемое будущее, **не** условие запуска веб-версии ([ADR-007](DECISIONS.md), OFFLINE_SYNC) | Local-first стек сейчас не выбираем; но API должен быть версионируемым и идемпотентным, чтобы синхронизация была возможна позже |
| Stage 5–6: мобильные приложения и desktop-agent ([FUTURE.md](FUTURE.md)) | Нужен **отдельный контракт API** (OpenAPI/схемы), а не «внутренности» веб-фреймворка; общие схемы валидации переиспользуются |
| Документация на русском, идентификаторы intents/actions на английском ([AGENT_GUIDE.md](AGENT_GUIDE.md) §6) | На стек не влияет |
| Бюджет и железо в документации не заданы | Стоимость владения — явный критерий выбора (раздел 8); вопрос владельцу |

## 3. Три развилки, которые определяют всё остальное

### R1. Где живёт backend: отдельный API + веб-клиент **или** full-stack фреймворк

| Вариант | Суть | Плюсы для Aven | Минусы для Aven |
|---|---|---|---|
| **Б. Отдельный API-бэкенд + веб-клиент** (рекомендуется) | Модули Action Core и вся доменная логика — в backend-приложении с REST/OpenAPI; веб — клиент (SPA или лёгкий SSR) | Action Core один для UI/Stage 2/Stage 3/Stage 5–6 «по построению»; контракт API существует независимо от веба; нет привязки к вендору веб-фреймворка; проще тестировать домен без браузера | Два деплой-артефакта; авторизация/CORS/типы между клиентом и сервером надо делать аккуратно (общие схемы решают); нет «бесплатного» SSR |
| **А. Full-stack Next.js** (App Router, server actions) | Один проект: страницы + серверная логика | Один деплой, SSR/кэширование/`next/image` из коробки, самая большая экосистема React | Доменная логика тяготеет к «внутренностям» фреймворка (server actions), что конфликтует с требованием единого Action Core для будущих клиентов; глубже всего интегрирован с Vercel (self-host поддерживается, но это отдельная работа: standalone output, image optimization, ISR); быстрая смена мажорных версий |
| **В. Full-stack на React Router v7 (framework mode, бывший Remix) или TanStack Start** | Один проект, SSR опционален, loader/action | Меньше вендор-специфики, чем у Next.js; SSR можно включить или выключить (`ssr: false`) | Экосистема моложе; те же вопросы «где граница доменной логики», что и в варианте А |

**Рекомендация (не решение):** вариант **Б**. Причина — не мода, а наши же требования: один Action Core
(ARCHITECTURE §4) и будущие клиенты Stage 5–6 ([FUTURE.md](FUTURE.md)). При варианте Б веб-клиент
заменяем без переписывания домена.

### R2. Где хостим

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| **A. Свой VPS + Docker Compose + reverse proxy** (рекомендуется на Stage 1) | Одна машина: приложение, Postgres, бэкапы | Полный контроль данных (приватность — [ADR-008](DECISIONS.md)); дёшево: Hetzner CX22 ≈ €3.29/мес (2 vCPU, 4 ГБ, 40 ГБ NVMe), CPX11 ≈ €4.15, CX32 ≈ $7.49 (4 vCPU, 8 ГБ, 80 ГБ NVMe), регионы Германия/**Финляндия**/США, бэкапы +20% ([источники](#15-источники-с-датами)) | Всё администрирование на нас: обновления, TLS, бэкап, мониторинг, восстановление |
| **B. PaaS** (Railway/Fly.io/Render и подобные) | Платформа деплоит контейнеры | Меньше операций, быстрый старт | Дороже на объёме; данные и конфигурация у третьей стороны; приватность/юрисдикция требует отдельной проверки |
| **C. Гибрид**: VPS для приложения + managed PostgreSQL + managed object storage | Часть ответственности провайдеру | Меньше риск потери данных (бэкапы провайдера), меньше операций | Дороже (managed Postgres ≈ €5–25/мес); зависимость от провайдера; экспорт данных надо держать рабочим |
| **D. Kubernetes** | Оркестрация контейнеров | Масштабирование, декларативность | **Не рекомендуется** на Stage 1: операционные расходы несоразмерны одному приложению для одного-нескольких пользователей |

**Рекомендация:** A на Stage 1, с заранее написанными `docker-compose.yml`, бэкапом и **проверенным**
восстановлением (ADMIN §17). Переход на C — если администрирование начнет съедать время или вырастет нагрузка.

### R3. Сколько компонентов вводим сразу

Принцип: **каждый новый инфраструктурный компонент требует обоснования** (это же правило уже записано для
кэширования: «Redis или совместимое — **если обосновано**», PROJECT_PLAN §8, ADR-107).
Минимальный набор на Stage 1: приложение + PostgreSQL + очередь задач **в том же PostgreSQL** + файловое
хранилище за абстракцией. Откладываются: Redis/Valkey, отдельный IdP, полный observability-стек, Kubernetes,
offline-sync, AI Router, собственный TTS-сервер (GPU — [TTS_RESEARCH.md](TTS_RESEARCH.md) §12–13).

### R4. Модульный монолит, а не микросервисы

Один деплой-артефакт backend с внутренними модулями (день, задачи, заметки, финансы, авто, память,
автоматизации, admin) и одним Action Core. Причины: один разработчик/агент на старте, общая транзакционность
(Undo, аудит, подтверждение опасных действий), отсутствие требования к независимому масштабированию модулей.
Границы модулей при этом соблюдаем так, чтобы позже можно было вынести — это требование ARCHITECTURE §4,
а не опция.

## 4. Backend

### 4.1 Runtime и язык

- **Node.js 24 LTS** («Krypton») — текущая production-линия: Active LTS, maintenance с 2026-10-20,
  EOL 2028-04-30. Node 22 — maintenance до 2027-04-30; Node 20 — EOL 2026-04-30; Node 26 станет Active LTS
  2026-10-28 (EOL 2029-04-30) → плановый переход на 26 LTS после его выхода.
- **TypeScript 6.0.x** — стабильная «мостовая» линия; **TypeScript 7.0** (компилятор переписан на Go,
  заявлено ≈10× быстрее) вышел 2026-07-08 и ставится как обычный пакет `typescript` (`tsc`).
  Рекомендация: стартовать на 6.x, 7.x включить после пилота в CI — источники отмечают, что два компилятора
  могут сообщать **разные** диагностические сообщения.
- Bun/Deno как основной runtime **не** рекомендуются на Stage 1 (зрелость корпоративных модулей и драйверов
  под наш набор), но допустимы для локальных инструментов/скриптов.

### 4.2 Фреймворк сервера (ADR-101)

| Вариант | Версия на дату исследования | Лицензия | Сильные стороны | Слабые стороны для Aven |
|---|---|---|---|---|
| **NestJS** | 11.1.x | MIT | Модули, DI, декораторы, единая структура проекта, встроенные интеграции (WS, GraphQL, microservices, CQRS) — удобно, когда доменов много (день/задачи/финансы/авто/admin) | «Стоимость абстракции» реальна для небольших сервисов; больше концепций и «магии»; тяжелее на старте |
| **Fastify** | 5.8.x | MIT | Производительность, валидация по JSON Schema из коробки, структурные логи (Pino), зрелая система плагинов, Node-first | Структуру приложения (модули/DI) проектируем сами |
| **Hono** | 4.12.x | MIT | Очень лёгкий, работает на Node/Bun/Deno/edge, встроенные middleware (JWT, CORS, кэш, Zod) | Архитектурные решения полностью на нас; экосистема «приложений» меньше |
| **Express** | 5.x | MIT | Максимально знакомый, минимум мнений | Минимум структуры — всё то, что нам нужно (модули, валидация, аудит), пишем сами |

**Рекомендация:** **NestJS** — если владелец хочет готовую модульную структуру и готов платить абстракцией;
**Fastify + собственная модульная структура** — если хочется меньше «магии» и больше контроля.
Обе рекомендации совместимы с R1-Б. Честно о цифрах: в источниках есть сравнения throughput
(например, «Fastify ~65K rps, NestJS на Express-адаптере ~18K rps»), но это данные сторонних статей,
мы их **не измеряли**; для личного ассистента (десятки запросов в минуту) throughput **не** является
критерием — критерии: структура, тестируемость, валидация, аудит, долгосрочная поддержка.

### 4.3 Контракт API и валидация (новый ADR-111)

| Вариант | Плюсы | Минусы |
|---|---|---|
| **REST + OpenAPI + общие схемы валидации** (рекомендуется) | Открытый контракт для Stage 5–6 и для API-источника команд (ARCHITECTURE §3); документация генерируется; не зависит от клиента | Контракт нужно поддерживать в актуальном состоянии (решается общими схемами + тестом) |
| **tRPC** | Максимальная типобезопасность без кодогенерации, очень быстро разрабатывать | Контракт «только для TypeScript-клиентов» — для мобильных (Flutter, ADR-104) и desktop (Rust, ADR-105) придётся делать второй |
| **GraphQL** | Гибкие выборки для клиента | Оверкилл для нашего набора разделов; authorization на каждом объекте (SECURITY §1) сложнее; кэширование/версионирование тяжелее |

Схемы валидации: **Zod** (MIT) или valibot — один набор схем в `packages/shared`, используется и сервером
(валидация входа Action Core), и клиентом (формы), и для генерации OpenAPI. Для NestJS альтернатива —
`class-validator` + `class-transformer`; тогда общие схемы с фронтом сложнее (это минус, а не плюс).

### 4.4 Доступ к данным и миграции (новый ADR-109)

| Вариант | Лицензия | Версия | Плюсы | Минусы |
|---|---|---|---|---|
| **Drizzle** | Apache-2.0 | `drizzle-orm` 0.45.x, `drizzle-kit` 0.31.x | Схема на TypeScript без кодогенерации, SQL-близкий синтаксис, первоклассный raw SQL, миграции из коробки, лёгкий | Меньше «магии» = больше явного кода для связей/вложенных записей |
| **Prisma** | Apache-2.0 | 7.x | Зрелый DX, своя схема `.prisma`, Prisma Studio (GUI), миграции; в 7.x убрали Rust-движок (меньше бинарников, лучше edge) | Кодогенерация; свой DSL; вложенные записи «как удобно» могут прятать неэффективные запросы |
| **Kysely + SQL-миграции** | MIT | — | Максимальный контроль, чистый SQL, минимум зависимостей | Всё (типы таблиц, миграции, отношения) собираем сами |
| TypeORM / MikroORM | MIT | — | Зрелые, декораторы | Исторически больше жалоб на типобезопасность/миграции; не рекомендуется для нового проекта |

**Рекомендация:** **Drizzle** — нам нужны контроль над SQL (JSONB для пользовательских сущностей,
агрегаты по финансам, append-only аудит) и отсутствие шага кодогенерации. **Prisma** — если владелец
ценит Studio и «всё включено» выше контроля над SQL.

## 5. Web-клиент (ADR-103)

### 5.1 Фреймворк/сборка

| Вариант | Версия на дату | Комментарий для Aven |
|---|---|---|
| **Vite + React + TanStack Router/Query** (рекомендуется при R1-Б) | Vite (актуальная мажорная), React 19.x | Чистый SPA: личный кабинет не требует SEO; типобезопасная маршрутизация и search-параметры; TanStack Query закрывает серверное состояние, кэш, мутации, optimistic updates (нужно для Undo/подтверждений) |
| **React Router v7** (library mode / framework mode) | 7.x | library mode = SPA без «налога» full-stack-фреймворка; framework mode (бывший Remix) — если позже понадобится SSR |
| **TanStack Start** | 1.0 (2026) | SSR + типобезопасность; моложе экосистема; RSC — позже |
| **Next.js** | 16.3.x (Active LTS 16.3.3, Maintenance LTS 15.5.x) | Самая большая экосистема; self-host возможен (standalone output, image optimization, ISR), но глубже всего интегрирован с Vercel; требует Node 20+; **в сентябре 2026 закрыты две критические уязвимости** в 16.3.3/15.5.24 → дисциплина патчей обязательна |

**Рекомендация:** при R1-Б — **Vite + React + TanStack Router/Query**. При R1-А — Next.js 16 (LTS-линия,
standalone output, pinned-версии).

### 5.2 UI-слой

Прототип (`/prototype`) уже задаёт структуру страниц, карточки, формы и CSS — это источник UX-требований,
но **не** production-код (prototype/README.md).

| Подход | Плюсы | Минусы |
|---|---|---|
| **Headless-компоненты + свой CSS из прототипа** (Radix UI / React Aria) | Доступность (клавиатура, ARIA, фокус) из коробки — у нас «Доступность» в настройках и требование полноценной работы с клавиатуры (PROJECT_PLAN §6.2); внешний вид полностью наш | Больше работы над стилями, чем у «готовой» библиотеки |
| Готовая компонентная библиотека (Mantine/MUI и подобные) | Быстрый старт, много готового | Чужой визуальный язык, переопределение стилей, лишний вес |
| Всё с нуля | Полный контроль | Риск регрессий доступности; дольше |

**Рекомендация:** headless + наш CSS. Доступность не должна доделываться потом.

## 6. Данные

### 6.1 СУБД (ADR-102)

- **PostgreSQL** — текущая стабильная мажорная **18.x** (18.4 на июнь 2026; релиз 18 — сентябрь 2025:
  асинхронный I/O, skip scan по мультиколоночным индексам, сохранение статистики планировщика при
  мажорном апгрейде). Поддерживаемые линии: 17.10, 16.14, 15.18, 14.23 (14 — EOL ноябрь 2026).
- Рекомендация: **PostgreSQL 17 или 18** — фиксируем на старте по доступности у выбранного хостинга;
  апгрейд мажорной версии — плановая операция с прогоном миграций на копии.
- Почему Postgres, а не альтернативы: реляционная модель под наши сущности и связи (DATA_MODEL §3),
  JSONB под будущие пользовательские типы сущностей (§3.2), транзакции под Undo/аудит/подтверждения
  ([ADR-005](DECISIONS.md)), зрелые бэкап/PITR, `numeric` под деньги (SECURITY §5).
- SQLite остаётся кандидатом для **локальной** БД мобильных клиентов (ADR-104), не для сервера.

### 6.2 Очередь задач / background jobs (ADR-106, открытый вопрос №3)

| Вариант | Backend | Сильные стороны | Слабые стороны |
|---|---|---|---|
| **pg-boss** (рекомендуется) | PostgreSQL | Отдельный компонент **не нужен**; `SKIP LOCKED` для безопасной конкурентности; ACID — задача ставится **в той же транзакции**, что и бизнес-запись (нет окна «БД записали, а задача потерялась»); отложенные/cron-задачи, singleton, dead-letter-queue, retry с backoff | Готовых дашбордов мало (свой раздел в админке — ADMIN §18 уже его предусматривает); задержка подхвата задачи — десятки мс, не суб-миллисекунды |
| **BullMQ** | Redis/Valkey | Самый функциональный: приоритеты, rate limiting, repeatable/cron, потоки зависимых задач (flows), Bull Board (UI), ≈500K загрузок/неделю | Требует ещё один сервис (Redis/Valkey) → деплой, мониторинг, бэкап, лицензия (раздел 6.3); нет ACID-постановки вместе с бизнес-транзакцией |
| **Temporal** (и подобные workflow-движки) | свой кластер | Мощные долгосрочные workflow, гарантии, версионирование | Отдельная инфраструктура и эксплуатация — несоразмерно Stage 1 |
| **node-cron / OS cron** | — | Проще некуда | Только для одной инстанции; нет retry/DLQ/видимости; при нескольких инстанциях — дублирование срабатываний |

**Рекомендация:** **pg-boss** на Stage 1. Что у нас реально работает в фоне: напоминания и события
(FEATURES §4), «утро/вечер» (FEATURES §3.7), уведомления и email (ADMIN §10–11), бэкапы, пересчёт
агрегатов финансов, миграции/импорты. Это единицы-десятки задач в минуту, а не тысячи.

**Явный критерий перехода на BullMQ + Valkey** (чтобы решение не было «навсегда»): устойчивая нагрузка
> ~1000 задач/мин, **или** нужен жёсткий rate limiting внешних API, **или** нужны потоки зависимых задач
(fan-out DAG), **или** очередь начинает заметно влиять на Postgres. Переход документируется новым ADR.

### 6.3 Кэш и in-memory хранилище (ADR-107, открытый вопрос №4)

**Обоснование (которого не хватало):** на Stage 1 отдельный Redis/Valkey **не вводим**.

- Потребности, которые обычно закрывает Redis, у нас закрыты иначе: очередь — pg-boss (6.2); сессии —
  в PostgreSQL (SECURITY §1 требует **управления** сессиями, а не их исчезновения при перезапуске);
  кэш справочников — in-process LRU + HTTP-кэширование; realtime-обновления — SSE/WebSocket из приложения.
- Каждый лишний сервис = деплой, обновления, мониторинг, бэкап, поверхность атаки. Для одного приложения
  это неоправданно до появления **измеренной** необходимости.
- **Критерии введения** (любой из): измеренная нагрузка на кэш/очередь, превышающая возможности Postgres;
  жёсткий distributed rate limiting нескольких инстанций; pub/sub между несколькими сервисами;
  требование горизонтального масштабирования приложения (несколько инстанций без sticky-сессий).

Лицензии — если компонент всё же понадобится:

| Продукт | Версия/дата | Лицензия | Комментарий |
|---|---|---|---|
| **Valkey** | 9.1 (май 2026) | BSD-3 (пермиссивная) | Форк Redis 7.2.4 под Linux Foundation (AWS/Google/Oracle/Snap); wire-совместим с Redis; дефолт в AWS ElastiCache/MemoryDB |
| Redis | 8.x (8.2 — февраль 2026) | **AGPLv3** (с мая 2025) + RSALv2/SSPLv1 | Снова open source, но AGPL — copyleft: при распространении модификаций возникают обязательства; для внутреннего использования обычно приемлемо, но требует юридической оценки |

**Рекомендация:** если/когда понадобится — **Valkey** (пермиссивная лицензия, совместимость).

### 6.4 Файлы и object storage (ADR-108)

Что храним на Stage 1: чеки и вложения финансов, документы, фото авто/покупок, экспорт данных
пользователя (SECURITY §2), бэкапы. Объёмы на старте небольшие.

**Решение, которое принимается сейчас:** абстракция `StorageProvider` (put/get/delete/signed URL +
версионирование ключей) и **S3-совместимый API как целевой контракт** — это и есть смысл ADR-108.
Конкретная реализация может меняться без изменения кода приложения.

| Реализация | Лицензия | Статус на дату исследования | Комментарий |
|---|---|---|---|
| Локальный диск/том за абстракцией | — | — | Достаточно для старта; бэкап тома обязателен; миграция на S3-реализацию — смена конфигурации |
| Managed object storage (S3/R2/GCS и подобные) | проприетарная | — | Меньше операций; данные у провайдера (приватность/юрисдикция — вопрос владельцу) |
| **SeaweedFS** | Apache-2.0 | активен (34K+ звёзд, коммиты в августе 2026) | Зрелый self-hosted S3-совместимый (через S3 gateway/filer); хорошо с большим числом мелких файлов |
| RustFS | Apache-2.0 | активен, но молодой | Ближайший «заменитель MinIO» с веб-интерфейсом; зрелость ниже |
| Garage | **AGPL-3.0** | активен | Лёгкий, гео-распределённый; single-tenant; без lifecycle; copyleft-лицензия |
| **MinIO** | **AGPLv3** | **публичный репозиторий архивирован** (последний push 2026-04-24) | **Не выбирать для нового self-hosted**: проект в публичном репозитории не развивается |
| Ceph | LGPL | активен | Полноценная распределённая система хранения; для одного приложения избыточна |

**Рекомендация:** Stage 1 — локальный том за абстракцией + бэкап; при росте объёмов или требовании
«хранить отдельно от приложения» — managed S3-совместимое **или** SeaweedFS (Apache-2.0).

### 6.5 Аутентификация, сессии, 2FA (новый ADR-110)

Требования (SECURITY §1, §10; ADMIN §13): сессии в БД с управлением и принудительным завершением,
TOTP-2FA (в т.ч. обязательная по роли — политика открыта, SECURITY §11), rate limits, отдельные
admin-сессии, повторная аутентификация для чувствительных настроек ([ADR-011](DECISIONS.md)).

| Вариант | Лицензия | Что это | Плюсы | Минусы |
|---|---|---|---|---|
| **Better Auth** (рекомендуется) | MIT | Встроенная TypeScript-библиотека: email/пароль, сессии, OAuth; плагины — TOTP/MFA, passkeys, организации, rate limiting, API keys; адаптеры Drizzle/Prisma/Kysely | Auth живёт в нашем приложении и нашей БД (контроль данных, аудит); MFA и rate limiting из коробки; не нужен отдельный сервис | Это **не** IdP: SSO между несколькими приложениями не даст (у нас одно приложение) |
| Auth.js v6 | — | Встроенная библиотека, «Next-first» | Зрелая экосистема | MFA/passkeys — плагинами; сильнее связан с Next.js |
| Zitadel | Apache-2.0 | Отдельный IdP: OIDC/OAuth2/SAML, мульти-тенантность, passkeys, TOTP | Правильный выбор, если приложений станет несколько | Отдельный сервис: деплой, обновления, эксплуатация |
| Keycloak | open source (Red Hat) | Зрелый отдельный IdP: OIDC/OAuth2/SAML/LDAP, броkering, MFA | Максимальная протокольная полнота | Тяжёлая эксплуатация (кластеризация через Infinispan); для одного приложения избыточен |
| Своя реализация (argon2id + сессии в БД) | — | Пишем сами | Полный контроль | **Не рекомендуется**: риск ошибок в криптографии, сессиях, reset-потоках, rate limiting — именно там, где ошибка стоит приватности |

**Рекомендация:** Better Auth (встроенная библиотека) + свой RBAC (ADMIN §3) + свой аудит.
Отдельный IdP — только когда появится второе приложение/SSO.

- **Качество в CI:** GitHub Actions (уже используется в репозитории для исследования TTS):
  typecheck → lint → unit/integration → e2e (на PR) → build → deploy (после merge в `main`),
  миграции применяются в деплое с rollback-планом.
- **Логи/наблюдаемость:** структурные логи (Pino) с запретом логирования секретов и лишних приватных данных
  (SECURITY §7 — правило уже зафиксировано); health endpoint (ADMIN §16); минимум на старте:
  health + uptime-мониторинг + ротация логов. Sentry/метрики-стек — отдельное решение (вопрос №12 раздела 13).
