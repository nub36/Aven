# COMMAND_ENGINE — Движок команд Aven

> **Статус:** проектная документация. Владелец утвердил дискретную модель разрешения и правила подтверждений; числовые confidence-пороги не используются.
> **Первая…пятая итерации реализованы в UX-прототипе 2026-09-28** — фактический контракт и охват см. разделы 9–13 (это прототип, не production-реализация).
> **Последнее обновление:** 2026-09-28

## 1. Назначение

Command Engine — ядро понимания команд. **Основные функции Aven должны работать без генеративного AI** ([ADR-002](DECISIONS.md)). Внутри используются intents/actions ([ADR-004](DECISIONS.md)).

Вся внутренняя система работает с **текстовым представлением команды** — голос лишь превращается в текст до входа в движок ([ADR-003](DECISIONS.md)).

**Место в порядке развития — Stage 2** ([ADR-013](DECISIONS.md)): Command Engine подключается к **уже существующим функциям сайта** (Stage 1 — полезный самостоятельный веб-сайт) и даёт возможность выполнять их одной строкой. Команды — дополнительный путь к тем же Actions: **те же действия остаются доступными через обычный UI** (формы, кнопки, навигация). Отдельная бизнес-логика для UI, текста и голоса не создаётся.

### Примеры intents

```
expense.add
expense.stats
car.fuel.add
car.mileage.set
note.create
note.search
event.create
event.list
timer.start
task.create
automation.run
memory.add
memory.search
```

### Примеры settings-intents (управление настройками командой)

Пользователь может менять подходящие настройки текстом/голосом ([PROJECT_PLAN.md](PROJECT_PLAN.md), раздел 12; [ADR-011](DECISIONS.md)). Примеры действий:

```
settings.voice.rate.set          ← «Говори медленнее.»
settings.quiet_hours.set         ← «Не разговаривай после 23:00.»
settings.day_period.set          ← «Вечер для меня начинается в 18:30.»
dictionary.alias.create          ← «Называй BMW бэхой.»
settings.voice.enabled.set       ← «Отключи голосовые ответы.»
settings.confirmation_policy.set ← «Всегда спрашивай перед удалением.»
```

Полный набор `settings.*` actions и охват «подходящих» настроек — открытый вопрос.

### Примеры команд (Stage 2)

- «Добавь задачу купить фильтр.»
- «Запиши 850 рублей продукты.»
- «Покажи расходы за неделю.»
- «Добавь заправку 42 литра на 3000.»
- «Создай заметку...»
- «Что у меня завтра?»

Те же действия доступны через обычный UI соответствующих разделов.

**Прототипная подготовка (2026-09-27, не полноценный NLP):** `/prototype/js/actions.js` уже даёт DOM-free действия для задач/событий (`createTask`, `completeTask`, `createEvent`, `getEventsForDate`, `getOverdueTasks` и др.). Текущий Assistant использует только простые demo-routes/state-machine, но путь для Stage 2 проверен: `text → intent (будет позже) → parameters → Common Action → state/history → UI/response`. Голос в Stage 3 должен идти тем же путём через STT-текст, а не через отдельные `voiceCreateTask()`/`voiceCreateEvent()`.

Фраза: **«Потратил сегодня 1250 рублей на бензин»**

```

amount    = 1250
```

## 2. Конвейер обработки

Command Engine состоит из отдельных компонентов:

1. нормализация текста;
2. определение намерения (intent detection);
3. извлечение параметров;
4. разбор дат;
5. разбор времени;
6. разбор денежных значений;
7. разбор чисел;
8. Entity Resolver (связывание упоминаний с объектами пользователя);
9. временный контекст незавершённого flow;
10. дискретный уровень разрешения (`EXACT / INFERRED / AMBIGUOUS / UNSUPPORTED`);
11. запрос недостающих параметров (уточнения);
12. подтверждение (для опасных/существенных);
13. выполнение Action (через Action Core, [ARCHITECTURE.md](ARCHITECTURE.md));
14. генерация шаблонного ответа.

Если информации недостаточно, Aven задаёт уточнение.

Пример:

> **Пользователь:** «Напомни завтра позвонить.»
> **Aven:** «В какое время?»
> **Пользователь:** «В десять.»
> **Aven:** завершает создание напоминания.

Не угадывать потенциально опасные или существенные данные. Для опасных операций всегда использовать подтверждение.

## 6. Разрешение и безопасность команд — решение владельца

Вместо некалиброванных процентов используются только дискретные уровни:

| Уровень | Значение | Поведение |
|---|---|---|
| `EXACT` | Полное детерминированное совпадение | безопасное действие можно выполнить сразу |
| `INFERRED` | Однозначный вывод по явно описанному правилу | read-only запрос можно выполнить; mutation требует подтверждения |
| `AMBIGUOUS` | Подходят несколько вариантов | мутации нет; показать варианты и уточнить |
| `UNSUPPORTED` | Команда/цель не поддержана или не найдена | мутации нет; честно объяснить ограничение |

Числа вроде `0.91`, `83%` или пороги confidence не используются: у прототипа нет статистически
калиброванной модели, поэтому такая точность была бы выдуманной.

Политика действий:

- `EXACT` создание обычной Task/Event и `EXACT` complete/reopen однозначной Task выполняются сразу;
- `INFERRED` mutation сначала показывает конкретное действие и ждёт подтверждения;
- read-only `EXACT`/`INFERRED` выполняются без подтверждения, если неоднозначность не влияет на ответ;
- delete/destructive/bulk, financial mutation и update существующего Event всегда требуют подтверждения;
- неподдержанные сейчас текстовые команды не добавляются только ради демонстрации подтверждения.

До подтверждения нет мутации и записи History. «Нет», «Отмена», кнопка отмены или Escape закрывают
flow с нулём изменений. Подтверждение выполняется максимум один раз; непосредственно перед ним цель
повторно читается через Common Query, поэтому исчезнувшая/изменившаяся запись безопасно отклоняется.
History создаёт только Common Action после выполнения; Undo остаётся общим.

## 7. Шаблонные ответы

Для базовых функций AI не требуется: ответы строятся из шаблонов и данных.

Примеры:

- «В сентябре вы потратили на {car} {amount}.»
- «Готово. Напомню {time}.»
- «У вас несколько автомобилей. Какой выбрать?»

Правила:

- Можно иметь несколько вариантов формулировок, но ответ **не должен искажать фактические данные**.
- Ответ отражает реальный статус выполнения ([ADR-010](DECISIONS.md)).

## 9. Первая итерация в прототипе (2026-09-28, фактическое состояние)

> Это **фактический** отчёт о том, что реализовано в `/prototype`, а не план. Всё, чего нет в
> списке «Поддерживается», считается не поддержанным. Production-реализации по-прежнему нет.

### 9.1. Контракт

Модуль `prototype/js/command.js` (`window.AvenCommand`) — DOM-free ядро:

```
normalize(text)              → нормализованная строка
parse(text, context)         → intent | { ok:false, error:{ code, message, examples } }   (без side effects)
resolve(intent, context)     → resolved | ambiguous | not_found + discrete resolution
execute(intent, context)     → result (вызывает только существующие Common Actions/Queries)
respond(result)              → человеческий текст
respondToParseError(parsed)  → человеческий текст
run(text, context)           → { ok, intent, result, response, context }
supported() / examples()     → перечень возможностей для UI, справки и тестов
```

Структурированное намерение:

```
{ ok: true, kind: 'query' | 'mutation', domain, action, params,
  match: { rule, resolution: 'EXACT' | 'INFERRED' }, requiresConfirmation,
  input: { text, normalized }, context: { todayISO } }
```

Структурированный результат:

```
{ ok, status: 'done' | 'info' | 'ambiguous' | 'confirmation_required' |
              'not_found' | 'stale' | 'invalid',
  action, resolution?, intent, entity?, target?, data?, historyId?, candidates?, code?, message? }
```

Правила слоя: ядро не меняет состояние напрямую, не пишет собственную историю, не дублирует
бизнес-логику задач/событий/финансов, не использует системные часы (только `AvenActions.dates`),
не использует AI/LLM/сеть/STT. Экран помощника — тонкий адаптер над `run()`.

### 9.2. Поддерживается сейчас

| Команда (примеры) | Действие | Через что выполняется |
|---|---|---|
| «Что у меня сегодня?», «что сегодня», «покажи дела на сегодня», «Что у меня завтра?», «какой план на послезавтра» | `day.plan` | `tasks.getTasksForDate`, `events.getEventsForDate`, `tasks.getOverdueTasks` |
| «Покажи просроченные задачи» | `tasks.overdue` | `tasks.getOverdueTasks` |
| «Какие есть предложения?» | `suggestions.list` | `AvenSuggestions.getSuggestions` |
| «Сколько я потратил?» | `finance.summary` | `finance.summary`, `finance.getOperations` (только чтение) |
| «Какой пробег?» | `auto.status` | `auto.car/stats`, `finance.totals` (только чтение) |
| «Что ты умеешь?» | `help.capabilities` | перечень `supported()` |
| «Создай/добавь/запиши задачу … [на завтра] [в 10:30]» | `task.create` | `tasks.createTask` |
| «Добавь завтра в 10 встречу с Сергеем» | `event.create` | `events.createEvent` |
| «Отметь/заверши/выполни … выполненной» | `task.complete` | `tasks.completeTask` |
| «Перенеси задачу … на пятницу» | `task.reschedule` | `tasks.updateTask` |

Даты: «сегодня», «завтра», «послезавтра», «вчера», дни недели (ближайший будущий),
`дд.мм[.гггг]`, `гггг-мм-дд`. Дата без года трактуется как ближайшая будущая.
Время: «в 10», «в 10 часов», «в 10:30», «10:30». Форма «10.30» намеренно не поддерживается
(неотличима от даты). Несуществующие дата/время — ошибка, а не «почти правильно».

Нормализация: регистр, `ё → е`, повторные и неразрывные пробелы, кавычки, завершающая пунктуация.
Морфологического анализатора, fuzzy-подбора и персонального словаря в первой итерации **нет**.

### 9.3. Явно НЕ поддерживается в первой итерации

- удаление и любые массовые/разрушительные операции текстом (нет подтверждения для текстового
  пути — по разделу 6 и [ADR-005](DECISIONS.md) такие команды в итерацию не включены);
- расходы/доходы, заметки, покупки, заправки и обслуживание, напоминания — текстом;
- перенос и изменение событий (создание есть, изменение — только в «Календаре»);
- уточняющие вопросы в несколько шагов (раздел 2, п. 11) и диалоговый контекст;
- пользовательские команды, персональный словарь, `settings.*`-команды (разделы 4–5);
- голос/STT (Stage 3) и любой LLM/AI.

### 9.4. Безопасность в первой итерации

- Разбор текста не меняет данные; изменения возможны только после успешного разбора и проверки.
- Несколько подходящих задач → структурированная неоднозначность со списком вариантов, мутации нет.
- Ничего не найдено / ошибка проверки общего слоя → причина словами, мутации нет.
- Неизвестная команда → отказ с примерами; данные и история не меняются.
- История и Undo — только существующие, созданные общим слоем действий.

Проверка: `prototype/tests/command-engine-check.js` — **152 проверки, 0 провалов** (в том числе
негативные: неизвестный текст, неоднозначность, неверные дата/время, отказ общего действия,
отсутствие подтверждения для разрушительных команд).

## 10. Вторая итерация: multi-step resolution и confirmations (2026-09-28)

### 10.1. Граница этапа

В итерацию входят разрешение Task для уже существующих `task.complete`/`task.reschedule`, выбор
кандидата, подтверждение `INFERRED` mutation и UI этих шагов. Delete, finance mutation и update Event
остаются неподдержанными: раздел 9 относил их к более поздним блокам, поэтому они не добавлены ради
демонстрации. Инфраструктура подтверждения готова применить обязательную политику, когда команды войдут
в документированный scope.

### 10.2. Контракты

`AvenCommand.resolve(intent, context)` возвращает `resolved | ambiguous | not_found` и один из уровней
`EXACT | INFERRED | AMBIGUOUS | UNSUPPORTED`. Для Task полное нормализованное название — `EXACT`,
единственное совпадение по целому слову/фразе с хотя бы одним содержательным словом длиной 3+ символа —
детерминированное `INFERRED`; произвольные внутрисловные и слишком короткие подстроки не матчятся,
fuzzy matching нет. Кандидат содержит id только для внутреннего продолжения, а UI показывает
title/date/time/status.

`AvenCommandSession` (`prototype/js/command-session.js`) — DOM-free transient orchestrator:

```
submit(text) → clarification_required | confirmation_required | done/info/error
choose(index) / confirm() / cancel() / reset()
pending() → минимальный сериализуемый snapshot текущего незавершённого flow
```

Session не содержит бизнес-логики и не пишет History. Pending хранит исходный intent, фиксированный
контекст общих часов и ссылки на кандидатов/цель; функций/closures нет. Он живёт только в JS memory,
не попадает в `AvenState` или localStorage и очищается после успеха, отказа, отмены, ухода из Assistant,
новой распознанной команды или stale failure.

### 10.3. Продолжение и безопасность

- ответы `1`/`2`, «первая/первую», «вторая/вторую» и точное повторение названия выбирают вариант;
- неверный выбор повторяет варианты без мутации;
- новая распознанная независимая команда сбрасывает старый flow и выполняется как новая;
- неизвестный текст не становится случайным выбором/подтверждением;
- перед continuation/confirm цель повторно читается через `tasks.getTask`;
- pending очищается **до** вызова mutation, поэтому double confirm не может выполнить её дважды;
- parse остаётся pure; конечное выполнение идёт через `AvenActions.tasks.*`.

Assistant показывает semantic buttons кандидатов и настоящие Confirm/Cancel controls; текстовые ответы
работают тем же session. Escape отменяет flow и возвращает focus в поле. Home передаёт команду в тот же
Assistant/session, отдельного home-state нет.

Проверка второй итерации: `command-session-check.js` — **73/73**, расширенный
`command-engine-check.js` — **161/161**; полный regression — **14 suite, 1155/1155**.

## 11. Третья итерация: заметки текстом (2026-09-28)

### 11.1. Граница этапа

Раздел 9.3 явно относил заметки (наравне с расходами, покупками, заправками и напоминаниями) к
неподдержанному первой итерацией. Эта итерация закрывает ровно заметки — единственный домен из того
списка, добавленный сейчас: **создание** заметки текстом и **поиск/показ** уже созданных заметок.
Изменение, архивирование и удаление уже существующей заметки текстом по-прежнему не входят в scope
и остаются честно неподдержанными (раздел 11.4) — как и раньше, ради демонстрации ничего не добавлено.
Расходы, покупки, заправки/обслуживание и напоминания текстом остаются в более поздних, ещё не начатых
блоках. Отдельного Notes Command Engine, Notes-парсера или второй Notes command session не создавалось:
заметки — ещё один домен уже существующего `AvenCommand`/`AvenCommandSession`.

### 11.2. Грамматика и контракт

```
note.create  — «Создай/добавь/запиши [новую] заметку <текст>»
note.search  — «Покажи/найди/поищи [мои] заметки [про|о|об|на тему <текст>]»
```

Слово «заметку/заметки/…» сразу после глагола создания — единственный признак домена: как только оно
распознано, **весь остаток фразы становится содержимым заметки целиком**, без повторного поиска в нём
дат, времени или слов других доменов («встреча», «задача», «расход», «заправка» и т. п. внутри текста
не переключают команду на другой домен — это прямой урок из production-review дефекта PR #27, когда
«добавь заметку про встречу» создавала событие). Заголовок заметки движок строит из этого же текста
(обрезка только у заголовка — 120 символов у общего действия; текст заметки не обрезается) и передаёт
оба поля в единственный существующий `AvenActions.notes.createNote({ title, body })`: второй схемы полей
заметки в командном слое нет. Пустой остаток после слова «заметку» (`«создай заметку»` без текста) —
явная ошибка `NOTE_CONTENT_REQUIRED`, а не создание пустой заметки с выдуманным текстом.

Поиск — read-only через существующий `AvenActions.notes.getNotes({ status: 'active', q })`; пустой
запрос («покажи заметки») означает «показать все активные», а не ошибку. Ответ — человеческий текст с
заголовком и коротким превью текста (для одного результата) либо списком заголовков (для нескольких);
внутренние id, домен действия и JSON не показываются. Ноль результатов — честное «не нашла», без
мутации. Поиск никогда не мутирует состояние и не пишет History, поэтому не входит в ambiguity/
confirmation flow: несколько результатов — это просто список, а не выбор цели.

### 11.3. Разрешение и безопасность

Создание заметки не требует entity resolution (нет цели для поиска) — как и `task.create`/
`event.create`, это `EXACT` safe mutation и выполняется сразу, без подтверждения. Существующий
`AvenCommandSession` подхватывает заметки автоматически: новая распознанная команда о заметке сбрасывает
любой pending flow другого домена (ambiguity/confirmation задачи), как и любая другая независимая
команда (раздел 10.3) — второго pending context для заметок не появилось.

### 11.4. Явно неподдержано в этой итерации

- изменение текста уже существующей заметки текстом (`измени/переименуй/отредактируй/обнови заметку …`)
  — `UNSUPPORTED_NOTE_UPDATE`, без мутации;
- архивирование/возврат из архива текстом (`заархивируй/разархивируй заметку …`, «в архив»/«из архива»)
  — `UNSUPPORTED_NOTE_ARCHIVE`, без мутации;
- удаление заметки текстом остаётся под общим `UNSUPPORTED_DELETE` (раздел 9.3) — без изменений;
- открытие конкретной заметки («открой заметку …») текстом не добавлялось: документированного scope
  на это нет, а поиск уже покрывает «посмотреть заметку».

Во всех случаях: ноль мутаций, ноль записей History, понятное объяснение вместо общего «не поняла».

Проверка третьей итерации: расширенный `command-engine-check.js` — **203/203** (+42 новых поведенческих
проверки заметок, включая обязательные regression-кейсы «встреча»/«билет»/«расход»/«машина» внутри
текста заметки), расширенный `command-session-check.js` — **77/77** (+4: сброс pending Task-флоу новой
командой о заметке); полный regression — **14 suite, 1201/1201**.

## 12. Четвёртая итерация: напоминания текстом (2026-09-28)

### 12.1. Граница этапа

Раздел 9.3 относил напоминания (наравне с расходами, покупками и заправками) к неподдержанному в
первой итерации; раздел 11.1 подтвердил это для третьей итерации заметок. Эта итерация закрывает ровно
напоминания — единственный домен из того списка, добавленный сейчас: **создание** напоминания текстом и
**поиск/показ** уже созданных напоминаний. Изменение, «отложить», «скрыть» и удаление уже существующего
напоминания текстом по-прежнему не входят в scope и остаются честно неподдержанными (раздел 12.4).
Расходы, покупки и заправки/обслуживание текстом остаются в более поздних, ещё не начатых блоках. Не
создавался ни второй движок напоминаний/уведомлений, ни Reminders-парсер, ни вторая command session:
напоминания — ещё один домен уже существующего `AvenCommand`/`AvenCommandSession`, использующий тот же
`AvenNotify` (через `AvenActions.reminders`), что и раздел «Уведомления».

### 12.2. Грамматика и контракт

```
reminder.create  — «Напомни <текст с датой[/временем]>» | «Создай/добавь напоминание <текст>»
reminder.search  — «Покажи/найди/поищи [мои] напоминания [про|о|об|на тему <текст>]»
```

Глагол «напомни(те)/напомнить» или существительное «напоминание/напоминания/…» сразу после глагола
создания — признак домена: как только он распознан, **весь остаток фразы становится содержимым
напоминания целиком**, без повторного поиска в нём слов других доменов («встреча», «задача», «расход»,
«заправка», «заметка» внутри текста не переключают команду на другой домен — тот же принцип, что закрыл
production-дефект PR #27 для заметок в третьей итерации). Обратное тоже верно: слова «напомни»/
«напоминание» внутри текста настоящей команды о задаче/событии/заметке не превращают её в напоминание.

Дата и время ищутся тем же общим парсером (`findDate`/`findTime`/`extractWhen`), что и у `event.create` —
никакого отдельного разбора дат для напоминаний не появилось. Ключевое отличие от `event.create`:
**дата обязательна**. `event.create` при отсутствии даты по умолчанию подставляет сегодня; для
напоминания это было бы выдуманным поведением — реальный контракт `AvenNotify.createReminder(entity)`
требует `dateISO`, а тихая подстановка «сегодня» без запроса пользователя недопустима по правилу
честности. Поэтому отсутствие даты — явная ошибка `REMINDER_DATE_REQUIRED`, а не создание с угаданной
датой. Время, как и у событий, необязательно. Пустой остаток после слова «напоминание» (`«создай
напоминание»` без текста) — явная ошибка `REMINDER_CONTENT_REQUIRED`, а не создание пустой записи.
Заголовок напоминания движок строит из текста (с заглавной буквы) и передаёт его вместе с `dateISO`/
`time` в единственный существующий `AvenActions.reminders.create({ title, dateISO, time })`: второй
схемы полей напоминания в командном слое нет.

Поиск — read-only через существующий `AvenActions.reminders.list({ q })`. Ручные напоминания в данных
**не имеют собственного поля активности/статуса** — состояние живёт только на уровне уведомления
(`notifState['manual:'+id]`: прочитано/отложено/скрыто), поэтому `reminders.list()` возвращает все
записи без фильтрации по статусу, и команда честно следует этому — придуманного «только активные»
фильтра, которого нет в реальном API, не добавлялось. Пустой запрос («покажи напоминания») означает
«показать все», а не ошибку. Ответ — человеческий текст с заголовком и датой (для одного результата)
либо списком (для нескольких); внутренние id, домен действия и JSON не показываются. Ноль результатов —
честное «не нашла», без мутации. Ни при каких условиях ответ не обещает фоновую доставку (push/email/
service worker) — прототип этого не делает.

### 12.3. Разрешение и безопасность

Создание напоминания не требует entity resolution (нет цели для поиска) — как и `task.create`/
`event.create`/`note.create`, это `EXACT` safe mutation и выполняется сразу, без подтверждения, с одной
записью в «Историю» и обычным Undo. Существующий `AvenCommandSession` подхватывает напоминания
автоматически: новая распознанная команда о напоминании сбрасывает любой pending flow другого домена
(ambiguity/confirmation задачи), как и любая другая независимая команда (раздел 10.3) и как заметки
(раздел 11.3) — второго pending context для напоминаний не появилось (проверено регрессией в
`command-session-check.js`).

### 12.4. Явно неподдержано в этой итерации

- изменение содержания/даты/времени уже существующего напоминания текстом (`измени/перенеси напоминание
  …`) — `UNSUPPORTED_REMINDER`, без мутации;
- «отложить»/«скрыть»/«вернуть» напоминание текстом (`отложи/скрой напоминание …`) — `UNSUPPORTED_REMINDER`,
  без мутации; эти действия остаются доступны только в разделе «Уведомления»;
- удаление напоминания текстом остаётся под общим `UNSUPPORTED_DELETE` (раздел 9.3) — без изменений;
- фоновая доставка (push/email/service worker) не добавлялась и не обещается нигде в ответах, Help или
  обучении — прототип показывает напоминания только внутри открытого приложения, как и раньше.

Во всех случаях: ноль мутаций, ноль записей History, понятное объяснение вместо общего «не поняла».

Проверка четвёртой итерации: расширенный `command-engine-check.js` — **268/268** (+65 новых поведенческих
проверок напоминаний, включая обязательные regression-кейсы «встреча»/«задача»/«расход»/«машина» внутри
текста напоминания и обратные регрессии для настоящих команд задач/событий/заметок), расширенный
`command-session-check.js` — **84/84** (+7: сброс pending Task-флоу новой командой о напоминании, включая
read-only поиск и honest-rejection без даты); полный regression — **14 suite, 1273/1273**.

## 13. Пятая итерация: расходы текстом (Stage 2, 2026-09-28)

### 13.1. Граница этапа

Раздел 9.3 относил расходы (наравне с покупками и заправками) к неподдержанному в первой итерации;
итерации 3 и 4 закрыли заметки и напоминания и подтвердили, что расходы остаются следующим
документированным блоком. Эта итерация закрывает ровно **расход**: создание расхода текстом и
read-only просмотр расходов. **Доходы** текстом в scope не входят (расход-first блок — так же, как
заметки закрывались отдельно от напоминаний): попытка записать доход получает честный отказ
`UNSUPPORTED_FINANCE_INCOME`, ноль мутаций. Изменение и удаление уже записанной операции, создание
счетов и категорий, пересчёт валют, заправки/покупки текстом — не входят и остаются честно
неподдержанными. Второго денежного движка, Finance-парсера, `FinanceCommandSession` или второй системы
подтверждений не создавалось: финансы — ещё один домен уже существующего `AvenCommand`/
`AvenCommandSession`, исполняемый единственным существующим `AvenActions.finance.createOperation`.

### 13.2. Политика владельца (обязательна)

**Любая финансовая мутация всегда проходит подтверждение** — даже `EXACT`. Это сильнее общей политики
§6 (где `EXACT` safe mutation выполняется сразу) и применяется намеренно: деньги считаются
существенным действием. Полный текст решения — [DECISIONS.md](DECISIONS.md), «Product Decision —
Finance text commands policy».

### 13.3. Грамматика и контракт

```
finance.expense.create — «Запиши/добавь/создай/внеси расход <сумма> [₽|руб|рублей] на <категория>
                          [со счёта <счёт>] [<дата>]»
                       | «Потратил(а)/заплатил(а)/оплатил(а) <сумма> … на <категория> …»
                       | «Расход <сумма> на <категория>»
finance.list           — «Покажи/найди расходы [за сегодня|за неделю|за месяц] [на <категория>]»
                       | «Какие расходы сегодня?»
finance.summary        — «Сколько я потратил?» (без изменений, из первой итерации)
```

**Сумма.** Поддерживаются `500`, `500 ₽`, `500 руб`, `500 рублей`, `500,50`, `500.50`, `1 250,50 ₽`
и эквивалентные записи с обычными/неразрывными пробелами. Сумма сразу переводится в **целые
минимальные единицы (копейки)** тем же правилом, что и общий слой (`AvenActions.money.minor`), и
передаётся в единственное существующее общее действие, которое её ещё раз проверяет. Float-накопления
в бизнес-арифметике нет. Ноль и отрицательные значения отклоняются. Сокращения (`5к`, `1.2к`, `1,2к`,
`тыс`), суммы словами, `$`/`€`/«долларов»/«евро» и неоднозначные строки вида `1.250,50` **не
интерпретируются наугад** — это честный отказ (`AMOUNT_UNSUPPORTED`/`CURRENCY_UNSUPPORTED`/
`AMOUNT_INVALID`/`AMOUNT_REQUIRED`) с примером поддерживаемого формата, ноль мутаций и ноль History.
Валюта — только валюта профиля; конвертации нет.

**Категория.** Только уже существующая: точное название — `EXACT`, единственное вхождение целым словом —
`INFERRED`, несколько — `AMBIGUOUS` (уточнение), отсутствие — честный отказ со списком существующих
категорий. Новая категория командой **не создаётся никогда**. Документированного default-значения в
модели нет, поэтому при отсутствии категории в тексте Aven спрашивает, а не подставляет молча.

**Счёт.** Указывается явной конструкцией «со счёта …»/«с карты …» (чтобы обычное «на продукты» никогда
не было понято как счёт). Правила разрешения и запрет на создание — те же, что у категории; при
отсутствии в тексте Aven спрашивает счёт. Внутренние id счетов пользователю не показываются.

**Описание/назначение.** Отдельного поля описания командная грамматика не вводит: «на продукты» — это
**категория**, а не комментарий. Название операции формирует существующее общее действие (по умолчанию
= категория), комментарий остаётся пустым. Никакого silent guessing.

**Дата.** Ищется тем же общим парсером дат на часах приложения (`AvenActions.dates`). Если даты нет,
используется документированный default самого общего действия (`finance.createOperation` → app today,
PR #26), но **сводка подтверждения всегда показывает конкретную разрешённую дату** — скрытого
умолчания пользователь не видит. Невалидная дата (`31.02`) — ошибка без pending, без мутации, без History.

### 13.4. Поток выполнения

```
parse (чистый)
  → [уточнение категории]        ← при отсутствии/неоднозначности, 0 мутаций
  → [уточнение счёта]            ← при отсутствии/неоднозначности, 0 мутаций
  → сводка подтверждения         ← тип «Расход», сумма, категория, счёт, дата
  → Confirm                      ← единственный шаг, после которого возможна мутация
  → AvenActions.finance.createOperation  → History (одна запись) → Undo
```

Уточнение и подтверждение живут в уже существующем `AvenCommandSession`: добавлен только один
generic-механизм — **slots** (значения недостающих параметров), которые заполняются выбором
пользователя и возвращаются в тот же intent. Перескочить подтверждение после выбора кандидата нельзя.
Перед выполнением счёт и категория перечитываются: если они исчезли между уточнением и Confirm —
безопасный отказ (`stale`), без фиктивного успеха. Pending очищается до вызова mutation, поэтому
double confirm не может создать вторую операцию. Cancel/«нет»/«отмена»/Escape — ноль мутаций и ноль
History. Pending живёт только в JS-памяти: ни в `AvenState`, ни в localStorage.

### 13.5. Read-only запросы

`finance.list` использует существующие `AvenActions.finance.getOperations` и `finance.totals`
(периоды `today`/`week`/`month`, фильтр по существующей категории) — второго аналитического движка в
Command Engine нет, суммы не пересчитываются отдельно. `finance.summary` («Сколько я потратил?»)
не менялся. Просмотр не требует подтверждения, ничего не мутирует и не пишет History; ответ —
человеческий текст с обычным денежным форматом, без id, без JSON и без float-артефактов.

### 13.6. Доменный приоритет

Финансовые правила стоят после правил задач/заметок/напоминаний и перед `event.create`, поэтому:
«Запиши расход 500 ₽ на заметки/на встречу» и «Расход 500 ₽ на напоминание» остаются финансовой
командой, а «Создай заметку расход 500 рублей», «Напомни записать расход 500 рублей завтра» и
«Создай задачу записать расход …» остаются заметкой/напоминанием/задачей. Все regex построены на явных
кириллических границах (`NOT_BEFORE`/`NOT_AFTER`), без ASCII `\b`/`\w`.

### 13.7. Явно неподдержано в этой итерации

- доходы текстом — `UNSUPPORTED_FINANCE_INCOME`, без мутации;
- изменение и удаление уже записанной операции текстом (удаление — под общим `UNSUPPORTED_DELETE`);
- создание счетов и категорий текстом (никогда — это политика, а не временный пробел);
- пересчёт валют и сокращения сумм;
- заправки/обслуживание авто и покупки текстом (отдельный следующий блок);
- морфология, fuzzy-подбор, пользовательские команды и персональный словарь.

Проверка пятой итерации: расширенный `command-engine-check.js` — **387/387** (+112 поведенческих
проверок расходов, включая суммы, отказы, подтверждение, отмену, Escape, double confirm, уточнение →
подтверждение, stale, Undo, согласованность «Финансов»/«Главной»/помощника/«Истории», доменные
регрессии, Help/Tutorial и ширины 320–1280), расширенный `command-session-check.js` — **105/105**
(+21: slots, всегда-подтверждение, отмена, double confirm, сброс pending в обе стороны, read-only);
полный regression — **14 suite, 1413/1413**.

### 13.8. Правки после независимого ревью (2026-09-28)

Ревью перед мержем показало пять мест, где разбор отвечал правдоподобно, но неверно. Все исправлены
в сторону честности, без ослабления существующих проверок:

| Фраза | Было | Стало |
| --- | --- | --- |
| «Удали расход 500», «Удали последний расход» | `finance.summary` | `UNSUPPORTED_DELETE` |
| «Измени расход 500» | `finance.summary` | `UNSUPPORTED_FINANCE_UPDATE` (новый ключ) |

## 14. Шестая итерация: Auto text commands (Stage 2, 2026-09-29)

Итерация закрывает только создание **заправки** и **обслуживания** через существующий
`AvenActions.auto.createRecord`. Документы, страховки, изменение/удаление Auto-записей, Shopping,
Event update, destructive/bulk, morphology/fuzzy и голос не входят.

Грамматика детерминирована:

```
auto.fuel.create    — «Запиши заправку <литры> л [на <стоимость> рублей]
                       [пробег <км> км] [<дата>] [и добавь в расходы [со счёта <счёт>]]»
auto.service.create — «Запиши обслуживание <работа> [на <стоимость> рублей]
                       [пробег <км> км] [<дата>] [и учти в финансах [со счёта <счёт>]]»
```

Литры обязательны и больше нуля; название обслуживания обязательно. Стоимость, пробег и дата
передаются в существующую Auto-модель (`sum/cost`, `km`, `dateISO`), дата по умолчанию — app today,
пробег по умолчанию — текущий пробег автомобиля согласно Common Action. Деньги извлекаются тем же
`findAmount`, что расходы, и передаются в Common Action без второго money engine. Parse чист.

**Стоимость Auto сама по себе не является Finance mutation.** EXACT Auto-only команда выполняется
сразу по общей policy и создаёт только Auto record. Finance link включается только явной фразой
«добавь в расходы / учти в финансах». Linked flow разрешает только существующую категорию «Авто» и
существующий счёт, затем всегда показывает общую сводку Auto + Finance. До Confirm, при Cancel/«нет»/
Escape — ноль Auto, Finance и History. Confirm один раз вызывает `auto.createRecord(...,
linkFinance: true)`: Common Action сначала безопасно создаёт связанную обычную Finance operation и
только после успеха добавляет Auto record; одна History entry содержит batch Undo обеих сущностей,
баланса и изменившегося mileage. Исчезнувший счёт/категория перед Confirm даёт stale failure.

Проверка итерации 6: `command-engine-check.js` — **448/448** (+49),
`command-session-check.js` — **116/116** (+11), `stage13-entities-check.js` — **119/119** (+3);
полный regression — **14 suites, 1489/1489, 0 failures**.

## 15. Седьмая итерация: Shopping text commands (Stage 2, 2026-09-29)

Итерация закрывает четыре сознательных действия над покупками: создание покупки, read-only
список/поиск и вопросы о гарантии — через существующие `AvenActions.shopping.createPurchase` и
`getPurchases`. Изменение/статус, ремонты, удаление, чеки/файлы/OCR не входят (честные отказы
`UNSUPPORTED_PURCHASE_UPDATE/REPAIR/FILE`, `UNSUPPORTED_DELETE`).

Грамматика детерминирована:

```
shopping.purchase.create   — «Добавь/Запиши покупку <название> [за <цена> рублей]
                              [в магазине <магазин>] [<дата>] [гарантия до <дата>]
                              [и добавь в расходы | и учти в финансах [со счёта <счёт>]]»
shopping.purchase.search   — «Покажи покупки» / «Найди покупку <текст>»
shopping.purchase.warranty — «Какие гарантии скоро закончатся?», «Покажи покупки
                              с гарантией», «Когда закончится гарантия на <вещь>?»
```

Название обязательно (`PURCHASE_NAME_REQUIRED без мутаций`), цена необязательна и извлекается общим
`findAmount` (форматы ровно как у расхода, `5к` — `AMOUNT_UNSUPPORTED`); магазин и гарантия — только
в явных конструкциях «в магазине …» / «гарантия до <дата>», даты — общий парсер (`DATE_INVALID`,
`WARRANTY_DATE_UNSUPPORTED` без догадок). Parse чист: ноль Shopping/Finance/History.

**Цена покупки сама по себе не создаёт Finance operation.** EXACT Shopping-only выполняется сразу,
ответ честно говорит «расход не создавался», действие пишет одну History entry с Undo типа remove.
Явный Finance qualifier всегда показывает сводку ОБЕИХ частей (покупка + расход с категорией «Другое»
и существующим счётом) и ждёт Confirm — даже при EXACT; до Confirm и после Cancel/«нет»/Escape —
0 покупок, 0 операций, 0 History. Confirm один раз вызывает атомарный
`shopping.createPurchase(..., linkFinance: true)`: Common Action сначала создаёт Finance operation,
затем покупку, при сбое компенсирует расход/баланс и не пишет History (код `PURCHASE_CREATE_FAILED`);
одна batch History entry отменяет обе сущности и поправляет счёт. Без счёта — уточнение account-слота,
неизвестный счёт — честный отказ без мутаций, счёт перечитывается перед execute (stale — безопасный
отказ). linked без цены — `AMOUNT_REQUIRED` без мутаций.

Read-only ответы не пишут History, не выбирают наугад: пустой поиск честно говорит «не нашла»,
несколько совпадений показываются списком. Гарантийные статусы и цвета считаются общей логикой
Shopping; вопрос про конкретную вещь при полном промахе прямого поиска пробует один мягкий
suffix-strip финали кириллицы одного слова (документированная read-only деградация, не морфология).

Проверка итерации 7: `command-engine-check.js` — **527/527** (+79), `command-session-check.js` —
**125/125** (+9), `stage13-entities-check.js` — **124/124** (+5, включая поведенческую инъекцию
сбоя вставки покупки после успешного Finance шага с проверкой компенсации); полный regression —
**14 suites, 1582/1582, 0 failures**. `node --check` и `git diff --check` чисты.

## 16. Восьмая итерация: перенос события текстом (Stage 2, 2026-09-29)

### 16.1. Граница этапа

Раздел 9.3 относил «перенос и изменение событий» к явно неподдержанному (создание было, изменение —
только в «Календаре»); разделы 10.1 и 13.7 подтверждали это для итераций 2–7. Эта итерация закрывает
ровно одно: **перенос уже существующего события на другую дату и/или время**. Ни второго Event
Command Engine, ни `EventCommandSession`, ни отдельного `EventResolutionEngine` не появилось —
события стали ещё одним доменом уже существующих `AvenCommand`/`AvenCommandSession` поверх
существующего Common Action `AvenActions.events.updateEvent`. Event schema не менялась.

### 16.2. Грамматика и контракт

```
event.reschedule — «Перенеси|Передвинь|Сдвинь|Измени <слово события> <название> на <дата и/или время>»
```

Домен определяется тем же явным словом, что и у `event.create` (`встреч*`, `событи*`, «созвон»,
«звонок», «приём», «визит»), и это слово должно стоять в начале названия. Название цели строится тем
же правилом «метка + остаток», которым `event.create` строит заголовок, поэтому «перенеси встречу с
Сергеем» ищет событие «Встреча с Сергеем» без морфологического анализатора. Слово «задачу» отдаёт
фразу правилу `task.reschedule`; «заметку», «напоминание», «покупку», «расход» — своим доменам.
Все шаблоны построены на явных кириллических границах (`NOT_BEFORE`/`NOT_AFTER`), без ASCII `\b`/`\w`.

«Куда» разбирается общим парсером (`extractWhen`/`findDate`/`findTime`) плюс одна документированная
форма «на 12» = 12:00 (для голых чисел после «на»; даты пишутся «12.05»). Непонятый хвост («на
следующую пятницу», «на утро») — честная ошибка `EVENT_WHEN_REQUIRED`, а не тихое отбрасывание.
Несуществующие дата/время (`31.02`, `25:00`, `10:75`) — `DATE_INVALID`/`TIME_INVALID`. Относительные
даты берутся только из общих часов `AvenActions.dates`. `parse` остаётся чистым: ни событие, ни
«История» не меняются.

### 16.3. Разрешение, подтверждение и безопасность

Разрешение события — те же дискретные правила, что у задач: полное нормализованное название —
`EXACT`, единственное вхождение целым словом/фразой с содержательным словом 3+ символа — `INFERRED`,
несколько — `AMBIGUOUS` (кандидаты с названием, датой и временем; ноль мутаций), ничего —
`EVENT_NOT_FOUND`. При отсутствии события новое **не создаётся** — это отдельно проверяется тестами.

Подтверждение — **ВСЕГДА**, даже при `EXACT` и простой смене времени (Product Decision «Event update
text commands», DECISIONS.md). Выбор кандидата не заменяет подтверждение. Сводка показывает событие
и «было → станет» целиком («Перенести «Стоматолог»: сегодня, 28.09.2026, 10:00–11:00 → завтра,
29.09.2026, 10:00–11:00?») — без id, JSON и имён действий. До Confirm состояние события,
«Календаря», «Дня», «Главной» и «Истории» не меняется; Cancel/«нет»/«отмена»/Escape — ноль изменений;
новая распознанная команда сбрасывает pending flow.

Перед выполнением цель перечитывается через `events.getEvent`, и минимальный ожидаемый слепок
(название, дата, начало, окончание, «весь день») сравнивается с фактическим: изменённое или удалённое
снаружи событие даёт безопасный `stale`-отказ вместо применения устаревшего переноса. Pending
очищается до вызова mutation, поэтому double confirm не может перенести событие дважды.

### 16.4. Семантика времени

- перенос **даты** сохраняет начало и окончание;
- перенос **времени** сохраняет длительность: окончание сдвигается на ту же величину; обе границы
  показываются в подтверждении;
- у события без окончания меняется только начало;
- перенос «в то же самое» — честное `info` без мутации и без записи «Истории» (фиктивная запись
  «изменений нет» не создаётся);
- выход окончания за полночь — честный отказ (`EVENT_TIME_OVERFLOW`).

### 16.5. Явно неподдержано в этой итерации

- удаление события текстом — общий `UNSUPPORTED_DELETE`;
- повторяющиеся события — `UNSUPPORTED_EVENT_REPEAT` (перенос одного повторения и всей серии —
  разные действия, модель такого выбора не хранит);
- время для события «весь день» — `UNSUPPORTED_EVENT_ALLDAY_TIME`;
- название, место, описание, участники, повторение — `UNSUPPORTED_EVENT_FIELD`;
- timezone-миграция, массовые операции, морфология/fuzzy.

### 16.6. Микро-правка Shopping (регресс после PR #33)

Форма «покупки с истекшей/истёкшей гарантией» не попадала в существующий read-only запрос об
истёкшей гарантии: шаблон знал только «истекла»/«просроченные». Добавлена ровно одна словоформа
(`истек(?:л|ш)[а-яе]*`; «ё» приводится к «е» общей нормализацией). Это точечное перечисление
словоформ, а не начало морфологии: «истекающая» по-прежнему означает «скоро закончится». Запрос
остаётся read-only: ноль мутаций, ноль «Истории».

Проверка итерации 8: `command-engine-check.js` — **613/613** (+86: разбор, доменные приоритеты,
обязательное подтверждение, старт/окончание, no-op, overflow, stale, «весь день», повторяющиеся,
сквозной путь Assistant → «Календарь»/«День»/«Главная»/«История»/Undo, cancel/Escape/double confirm,
кандидаты, ширина 320, Help/Tutorial, Shopping F1), `command-session-check.js` — **140/140** (+15);
полный regression — **14 suites, 1683/1683, 0 failures**.

## 17. Окончательная валидация остаётся в Common Actions (Data Integrity, 2026-09-29)

Этап Data Integrity Hardening **не расширял** Command Engine и не добавлял в него новых доменов,
правил и валидаторов. Зафиксирована граница ответственности, которая и так подразумевалась:

- **Разбор текста** может иметь собственную синтаксическую защиту (например, `31.02` и `25:00`
  отклоняются ещё на разборе, сокращения сумм вроде «5к» и чужая валюта честно не поддержаны).
  Это удобство и ранняя понятная ошибка, а не гарантия целостности.
- **Source of truth — Common Action Layer.** Календарный контракт даты
  (`AvenActions.dates.isValid`) и инвариант безопасных денег
  (`AvenActions.money.safeMinor`/`rangeIssue`) живут там и являются **окончательной** защитой для
  всех входов сразу: UI-формы, текстовой команды и прямого вызова действия.
- Отдельных `commandSafeDate()` / `commandSafeMoney()` **не появилось и появляться не должно** —
  второй копии правил нет.

Практическое следствие, закреплённое тестом: команда со слишком большой суммой, прошедшая уточнение
счёта **и** подтверждение пользователя, всё равно отклоняется общим действием
(`AMOUNT_OUT_OF_RANGE`), операция не создаётся и «История» не пишется. Обойти проверку через
командный слой нельзя. Аналогично для невозможной даты в задаче, напоминании и переносе события:
состояние события не меняется.

Проверки — `prototype/tests/data-integrity-check.js`, часть E (Command Engine как не-обход общего
слоя) и часть H (форма «Финансов» как не-обход общего слоя).
