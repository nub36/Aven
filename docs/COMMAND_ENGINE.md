# COMMAND_ENGINE — Движок команд Aven

> **Статус:** проектная документация. Владелец утвердил дискретную модель разрешения и правила подтверждений; числовые confidence-пороги не используются.
> **Первая, вторая и третья итерации реализованы в UX-прототипе 2026-09-28** — фактический контракт и охват см. разделы 9–11 (это прототип, не production-реализация).
> **Последнее обновление:** 2026-09-28

---

## 1. Назначение

Command Engine — ядро понимания команд. **Основные функции Aven должны работать без генеративного AI** ([ADR-002](DECISIONS.md)). Внутри используются intents/actions ([ADR-004](DECISIONS.md)).

Вся внутренняя система работает с **текстовым представлением команды** — голос лишь превращается в текст до входа в движок ([ADR-003](DECISIONS.md)).

**Место в порядке развития — Stage 2** ([ADR-013](DECISIONS.md)): Command Engine подключается к **уже существующим функциям сайта** (Stage 1 — полезный самостоятельный веб-сайт) и даёт возможность выполнять их одной строкой. Команды — дополнительный путь к тем же Actions: **те же действия остаются доступными через обычный UI** (формы, кнопки, навигация). Отдельная бизнес-логика для UI, текста и голоса не создаётся.

### Примеры intents

```
expense.add
expense.stats
car.fuel.add
car.mileage.set
note.create
note.search
event.create
event.list
timer.start
task.create
automation.run
memory.add
memory.search
```

### Примеры settings-intents (управление настройками командой)

Пользователь может менять подходящие настройки текстом/голосом ([PROJECT_PLAN.md](PROJECT_PLAN.md), раздел 12; [ADR-011](DECISIONS.md)). Примеры действий:

```
settings.voice.rate.set          ← «Говори медленнее.»
settings.quiet_hours.set         ← «Не разговаривай после 23:00.»
settings.day_period.set          ← «Вечер для меня начинается в 18:30.»
dictionary.alias.create          ← «Называй BMW бэхой.»
settings.voice.enabled.set       ← «Отключи голосовые ответы.»
settings.confirmation_policy.set ← «Всегда спрашивай перед удалением.»
```

Полный набор `settings.*` actions и охват «подходящих» настроек — открытый вопрос.

### Примеры команд (Stage 2)

- «Добавь задачу купить фильтр.»
- «Запиши 850 рублей продукты.»
- «Покажи расходы за неделю.»
- «Добавь заправку 42 литра на 3000.»
- «Создай заметку...»
- «Что у меня завтра?»

Те же действия доступны через обычный UI соответствующих разделов.

**Прототипная подготовка (2026-09-27, не полноценный NLP):** `/prototype/js/actions.js` уже даёт DOM-free действия для задач/событий (`createTask`, `completeTask`, `createEvent`, `getEventsForDate`, `getOverdueTasks` и др.). Текущий Assistant использует только простые demo-routes/state-machine, но путь для Stage 2 проверен: `text → intent (будет позже) → parameters → Common Action → state/history → UI/response`. Голос в Stage 3 должен идти тем же путём через STT-текст, а не через отдельные `voiceCreateTask()`/`voiceCreateEvent()`.

### Пример преобразования

Фраза: **«Потратил сегодня 1250 рублей на бензин»**

```

amount    = 1250
currency  = RUB

```

## 2. Конвейер обработки

Command Engine состоит из отдельных компонентов:

1. нормализация текста;
2. определение намерения (intent detection);
3. извлечение параметров;
4. разбор дат;
5. разбор времени;
6. разбор денежных значений;
7. разбор чисел;
8. Entity Resolver (связывание упоминаний с объектами пользователя);
9. временный контекст незавершённого flow;
10. дискретный уровень разрешения (`EXACT / INFERRED / AMBIGUOUS / UNSUPPORTED`);
11. запрос недостающих параметров (уточнения);
12. подтверждение (для опасных/существенных);
13. выполнение Action (через Action Core, [ARCHITECTURE.md](ARCHITECTURE.md));
14. генерация шаблонного ответа.

Если информации недостаточно, Aven задаёт уточнение.

Пример:

> **Пользователь:** «Напомни завтра позвонить.»
> **Aven:** «В какое время?»
> **Пользователь:** «В десять.»
> **Aven:** завершает создание напоминания.

Не угадывать потенциально опасные или существенные данные. Для опасных операций всегда использовать подтверждение.

## 6. Разрешение и безопасность команд — решение владельца

Вместо некалиброванных процентов используются только дискретные уровни:

| Уровень | Значение | Поведение |
|---|---|---|
| `EXACT` | Полное детерминированное совпадение | безопасное действие можно выполнить сразу |
| `INFERRED` | Однозначный вывод по явно описанному правилу | read-only запрос можно выполнить; mutation требует подтверждения |
| `AMBIGUOUS` | Подходят несколько вариантов | мутации нет; показать варианты и уточнить |
| `UNSUPPORTED` | Команда/цель не поддержана или не найдена | мутации нет; честно объяснить ограничение |

Числа вроде `0.91`, `83%` или пороги confidence не используются: у прототипа нет статистически
калиброванной модели, поэтому такая точность была бы выдуманной.

Политика действий:

- `EXACT` создание обычной Task/Event и `EXACT` complete/reopen однозначной Task выполняются сразу;
- `INFERRED` mutation сначала показывает конкретное действие и ждёт подтверждения;
- read-only `EXACT`/`INFERRED` выполняются без подтверждения, если неоднозначность не влияет на ответ;
- delete/destructive/bulk, financial mutation и update существующего Event всегда требуют подтверждения;
- неподдержанные сейчас текстовые команды не добавляются только ради демонстрации подтверждения.

До подтверждения нет мутации и записи History. «Нет», «Отмена», кнопка отмены или Escape закрывают
flow с нулём изменений. Подтверждение выполняется максимум один раз; непосредственно перед ним цель
повторно читается через Common Query, поэтому исчезнувшая/изменившаяся запись безопасно отклоняется.
History создаёт только Common Action после выполнения; Undo остаётся общим.

## 7. Шаблонные ответы

Для базовых функций AI не требуется: ответы строятся из шаблонов и данных.

Примеры:

- «В сентябре вы потратили на {car} {amount}.»
- «Готово. Напомню {time}.»
- «У вас несколько автомобилей. Какой выбрать?»

Правила:

- Можно иметь несколько вариантов формулировок, но ответ **не должен искажать фактические данные**.
- Ответ отражает реальный статус выполнения ([ADR-010](DECISIONS.md)).

## 9. Первая итерация в прототипе (2026-09-28, фактическое состояние)

> Это **фактический** отчёт о том, что реализовано в `/prototype`, а не план. Всё, чего нет в
> списке «Поддерживается», считается не поддержанным. Production-реализации по-прежнему нет.

### 9.1. Контракт

Модуль `prototype/js/command.js` (`window.AvenCommand`) — DOM-free ядро:

```
normalize(text)              → нормализованная строка
parse(text, context)         → intent | { ok:false, error:{ code, message, examples } }   (без side effects)
resolve(intent, context)     → resolved | ambiguous | not_found + discrete resolution
execute(intent, context)     → result (вызывает только существующие Common Actions/Queries)
respond(result)              → человеческий текст
respondToParseError(parsed)  → человеческий текст
run(text, context)           → { ok, intent, result, response, context }
supported() / examples()     → перечень возможностей для UI, справки и тестов
```

Структурированное намерение:

```
{ ok: true, kind: 'query' | 'mutation', domain, action, params,
  match: { rule, resolution: 'EXACT' | 'INFERRED' }, requiresConfirmation,
  input: { text, normalized }, context: { todayISO } }
```

Структурированный результат:

```
{ ok, status: 'done' | 'info' | 'ambiguous' | 'confirmation_required' |
              'not_found' | 'stale' | 'invalid',
  action, resolution?, intent, entity?, target?, data?, historyId?, candidates?, code?, message? }
```

Правила слоя: ядро не меняет состояние напрямую, не пишет собственную историю, не дублирует
бизнес-логику задач/событий/финансов, не использует системные часы (только `AvenActions.dates`),
не использует AI/LLM/сеть/STT. Экран помощника — тонкий адаптер над `run()`.

### 9.2. Поддерживается сейчас

| Команда (примеры) | Действие | Через что выполняется |
|---|---|---|
| «Что у меня сегодня?», «что сегодня», «покажи дела на сегодня», «Что у меня завтра?», «какой план на послезавтра» | `day.plan` | `tasks.getTasksForDate`, `events.getEventsForDate`, `tasks.getOverdueTasks` |
| «Покажи просроченные задачи» | `tasks.overdue` | `tasks.getOverdueTasks` |
| «Какие есть предложения?» | `suggestions.list` | `AvenSuggestions.getSuggestions` |
| «Сколько я потратил?» | `finance.summary` | `finance.summary`, `finance.getOperations` (только чтение) |
| «Какой пробег?» | `auto.status` | `auto.car/stats`, `finance.totals` (только чтение) |
| «Что ты умеешь?» | `help.capabilities` | перечень `supported()` |
| «Создай/добавь/запиши задачу … [на завтра] [в 10:30]» | `task.create` | `tasks.createTask` |
| «Добавь завтра в 10 встречу с Сергеем» | `event.create` | `events.createEvent` |
| «Отметь/заверши/выполни … выполненной» | `task.complete` | `tasks.completeTask` |
| «Перенеси задачу … на пятницу» | `task.reschedule` | `tasks.updateTask` |

Даты: «сегодня», «завтра», «послезавтра», «вчера», дни недели (ближайший будущий),
`дд.мм[.гггг]`, `гггг-мм-дд`. Дата без года трактуется как ближайшая будущая.
Время: «в 10», «в 10 часов», «в 10:30», «10:30». Форма «10.30» намеренно не поддерживается
(неотличима от даты). Несуществующие дата/время — ошибка, а не «почти правильно».

Нормализация: регистр, `ё → е`, повторные и неразрывные пробелы, кавычки, завершающая пунктуация.
Морфологического анализатора, fuzzy-подбора и персонального словаря в первой итерации **нет**.

### 9.3. Явно НЕ поддерживается в первой итерации

- удаление и любые массовые/разрушительные операции текстом (нет подтверждения для текстового
  пути — по разделу 6 и [ADR-005](DECISIONS.md) такие команды в итерацию не включены);
- расходы/доходы, заметки, покупки, заправки и обслуживание, напоминания — текстом;
- перенос и изменение событий (создание есть, изменение — только в «Календаре»);
- уточняющие вопросы в несколько шагов (раздел 2, п. 11) и диалоговый контекст;
- пользовательские команды, персональный словарь, `settings.*`-команды (разделы 4–5);
- голос/STT (Stage 3) и любой LLM/AI.

### 9.4. Безопасность в первой итерации

- Разбор текста не меняет данные; изменения возможны только после успешного разбора и проверки.
- Несколько подходящих задач → структурированная неоднозначность со списком вариантов, мутации нет.
- Ничего не найдено / ошибка проверки общего слоя → причина словами, мутации нет.
- Неизвестная команда → отказ с примерами; данные и история не меняются.
- История и Undo — только существующие, созданные общим слоем действий.

Проверка: `prototype/tests/command-engine-check.js` — **152 проверки, 0 провалов** (в том числе
негативные: неизвестный текст, неоднозначность, неверные дата/время, отказ общего действия,
отсутствие подтверждения для разрушительных команд).

## 10. Вторая итерация: multi-step resolution и confirmations (2026-09-28)

### 10.1. Граница этапа

В итерацию входят разрешение Task для уже существующих `task.complete`/`task.reschedule`, выбор
кандидата, подтверждение `INFERRED` mutation и UI этих шагов. Delete, finance mutation и update Event
остаются неподдержанными: раздел 9 относил их к более поздним блокам, поэтому они не добавлены ради
демонстрации. Инфраструктура подтверждения готова применить обязательную политику, когда команды войдут
в документированный scope.

### 10.2. Контракты

`AvenCommand.resolve(intent, context)` возвращает `resolved | ambiguous | not_found` и один из уровней
`EXACT | INFERRED | AMBIGUOUS | UNSUPPORTED`. Для Task полное нормализованное название — `EXACT`,
единственное совпадение по целому слову/фразе с хотя бы одним содержательным словом длиной 3+ символа —
детерминированное `INFERRED`; произвольные внутрисловные и слишком короткие подстроки не матчятся,
fuzzy matching нет. Кандидат содержит id только для внутреннего продолжения, а UI показывает
title/date/time/status.

`AvenCommandSession` (`prototype/js/command-session.js`) — DOM-free transient orchestrator:

```
submit(text) → clarification_required | confirmation_required | done/info/error
choose(index) / confirm() / cancel() / reset()
pending() → минимальный сериализуемый snapshot текущего незавершённого flow
```

Session не содержит бизнес-логики и не пишет History. Pending хранит исходный intent, фиксированный
контекст общих часов и ссылки на кандидатов/цель; функций/closures нет. Он живёт только в JS memory,
не попадает в `AvenState` или localStorage и очищается после успеха, отказа, отмены, ухода из Assistant,
новой распознанной команды или stale failure.

### 10.3. Продолжение и безопасность

- ответы `1`/`2`, «первая/первую», «вторая/вторую» и точное повторение названия выбирают вариант;
- неверный выбор повторяет варианты без мутации;
- новая распознанная независимая команда сбрасывает старый flow и выполняется как новая;
- неизвестный текст не становится случайным выбором/подтверждением;
- перед continuation/confirm цель повторно читается через `tasks.getTask`;
- pending очищается **до** вызова mutation, поэтому double confirm не может выполнить её дважды;
- parse остаётся pure; конечное выполнение идёт через `AvenActions.tasks.*`.

Assistant показывает semantic buttons кандидатов и настоящие Confirm/Cancel controls; текстовые ответы
работают тем же session. Escape отменяет flow и возвращает focus в поле. Home передаёт команду в тот же
Assistant/session, отдельного home-state нет.

Проверка второй итерации: `command-session-check.js` — **73/73**, расширенный
`command-engine-check.js` — **161/161**; полный regression — **14 suite, 1155/1155**.

## 11. Третья итерация: заметки текстом (2026-09-28)

### 11.1. Граница этапа

Раздел 9.3 явно относил заметки (наравне с расходами, покупками, заправками и напоминаниями) к
неподдержанному первой итерацией. Эта итерация закрывает ровно заметки — единственный домен из того
списка, добавленный сейчас: **создание** заметки текстом и **поиск/показ** уже созданных заметок.
Изменение, архивирование и удаление уже существующей заметки текстом по-прежнему не входят в scope
и остаются честно неподдержанными (раздел 11.4) — как и раньше, ради демонстрации ничего не добавлено.
Расходы, покупки, заправки/обслуживание и напоминания текстом остаются в более поздних, ещё не начатых
блоках. Отдельного Notes Command Engine, Notes-парсера или второй Notes command session не создавалось:
заметки — ещё один домен уже существующего `AvenCommand`/`AvenCommandSession`.

### 11.2. Грамматика и контракт

```
note.create  — «Создай/добавь/запиши [новую] заметку <текст>»
note.search  — «Покажи/найди/поищи [мои] заметки [про|о|об|на тему <текст>]»
```

Слово «заметку/заметки/…» сразу после глагола создания — единственный признак домена: как только оно
распознано, **весь остаток фразы становится содержимым заметки целиком**, без повторного поиска в нём
дат, времени или слов других доменов («встреча», «задача», «расход», «заправка» и т. п. внутри текста
не переключают команду на другой домен — это прямой урок из production-review дефекта PR #27, когда
«добавь заметку про встречу» создавала событие). Заголовок заметки движок строит из этого же текста
(обрезка только у заголовка — 120 символов у общего действия; текст заметки не обрезается) и передаёт
оба поля в единственный существующий `AvenActions.notes.createNote({ title, body })`: второй схемы полей
заметки в командном слое нет. Пустой остаток после слова «заметку» (`«создай заметку»` без текста) —
явная ошибка `NOTE_CONTENT_REQUIRED`, а не создание пустой заметки с выдуманным текстом.

Поиск — read-only через существующий `AvenActions.notes.getNotes({ status: 'active', q })`; пустой
запрос («покажи заметки») означает «показать все активные», а не ошибку. Ответ — человеческий текст с
заголовком и коротким превью текста (для одного результата) либо списком заголовков (для нескольких);
внутренние id, домен действия и JSON не показываются. Ноль результатов — честное «не нашла», без
мутации. Поиск никогда не мутирует состояние и не пишет History, поэтому не входит в ambiguity/
confirmation flow: несколько результатов — это просто список, а не выбор цели.

### 11.3. Разрешение и безопасность

Создание заметки не требует entity resolution (нет цели для поиска) — как и `task.create`/
`event.create`, это `EXACT` safe mutation и выполняется сразу, без подтверждения. Существующий
`AvenCommandSession` подхватывает заметки автоматически: новая распознанная команда о заметке сбрасывает
любой pending flow другого домена (ambiguity/confirmation задачи), как и любая другая независимая
команда (раздел 10.3) — второго pending context для заметок не появилось.

### 11.4. Явно неподдержано в этой итерации

- изменение текста уже существующей заметки текстом (`измени/переименуй/отредактируй/обнови заметку …`)
  — `UNSUPPORTED_NOTE_UPDATE`, без мутации;
- архивирование/возврат из архива текстом (`заархивируй/разархивируй заметку …`, «в архив»/«из архива»)
  — `UNSUPPORTED_NOTE_ARCHIVE`, без мутации;
- удаление заметки текстом остаётся под общим `UNSUPPORTED_DELETE` (раздел 9.3) — без изменений;
- открытие конкретной заметки («открой заметку …») текстом не добавлялось: документированного scope
  на это нет, а поиск уже покрывает «посмотреть заметку».

Во всех случаях: ноль мутаций, ноль записей History, понятное объяснение вместо общего «не поняла».
