# SECURITY — Безопасность и приватность

> **Статус:** проектная документация. Security проектируется с самого начала ([ADR-008](DECISIONS.md)).
> **Последнее обновление:** 2026-09-26 — экраны аккаунта (вход, шаг 2FA/TOTP, регистрация, восстановление доступа,
> сессии, выход) представлены в **прототипе** как UX-макет (`prototype/js/auth.js`, `#/login`): настоящей
> аутентификации, хэширования и токенов там нет и не будет до перевода стековых ADR в `Accepted`.

---

## 1. Обязательные концепции безопасности

Security должна проектироваться **с самого начала**. Обязательные концепции:

- password hashing современным алгоритмом;
- secure sessions / tokens;
- CSRF / XSS / SQL injection protections;
- validation (входных данных everywhere);
- authorization **на каждом объекте**;
- rate limiting;
- encryption для подходящих secrets;
- separation of user data (строгое разделение данных пользователей);
- audit административных действий;
- device / session management;
- optional/required 2FA там, где нужно;
- backup;
- restore testing (проверка восстанавливаемости);
- export account;
- delete account;
- least privilege;
- explicit permissions для device agents и integrations;
- confirmation для destructive actions.

**Принцип:** не хранить чувствительные данные просто потому, что это технически возможно.

## 2. Приватность (контроль пользователя)

Пользователь контролирует свои данные. Предусмотреть:

- просмотр;
- изменение;
- экспорт;
- удаление;
- управление сессиями;
- управление устройствами;
- управление интеграциями;
- управление памятью Aven («Память Aven» — [DATA_MODEL.md](DATA_MODEL.md)).

**Минимизировать доступ администрации к пользовательскому содержимому.** Администратор по умолчанию **не** получает содержимое приватных пользовательских заметок и файлов ([ADMIN.md](ADMIN.md)).

## 3. Безопасность команд и действий

- Опасные/разрушительные действия — подтверждение независимо от confidence ([ADR-005](DECISIONS.md), [COMMAND_ENGINE.md](COMMAND_ENGINE.md)).
- Потенциально опасные/существенные данные не угадываются.
- История действий + Undo для подходящих действий.
- На production-сервере запрещено выполнение произвольного пользовательского JavaScript; блоки автоматизаций — только зарегистрированные операции с permissions и лимитами ([ADR-006](DECISIONS.md), [AUTOMATION.md](AUTOMATION.md)).
- AI не имеет неконтролируемого прямого доступа к БД или системным операциям; схема `AI Router → Action + parameters → permission validation → execution` ([ARCHITECTURE.md](ARCHITECTURE.md)).

## 4. Настройки и разделение /settings vs /admin

- **`/settings`** — настройки конкретного пользователя; **`/admin`** — управление системой Aven. Интерфейсы разделены ([ADR-012](DECISIONS.md), [PROJECT_PLAN.md](PROJECT_PLAN.md), раздел 13).
- **Администратор не должен автоматически получать возможность действовать от имени пользователя.**
- Если в будущем появится **support impersonation**, функция должна: проектироваться отдельно (отдельный ADR); иметь строгие permissions; быть явно заметной; журналироваться; иметь причину входа (reason); по возможности ограничивать доступ к чувствительным данным.
- **Команды изменения настроек (в т.ч. голосовые) не обходят security requirements** ([ADR-011](DECISIONS.md)): для чувствительных настроек — подтверждение и/или повторная аутентификация. Перечень чувствительных настроек — открытый вопрос.
- Настройки приватности пользователя (экспорт, удаление данных, диагностические данные, история действий, управление постоянной памятью) — дополняют контроль пользователя из раздела 2 ([PROJECT_PLAN.md](PROJECT_PLAN.md), раздел «Настройки Aven»).

## 5. Финансовые данные

- Не проектировать систему как банковское приложение.
- **Не хранить платёжные секреты** без отдельной проработки безопасности ([FEATURES.md](FEATURES.md), раздел 7).

## 6. Device-агенты и интеграции

- Desktop-agent запускается **только с явного согласия** пользователя.
- Контролируемые permissions; явно разрешённые системные действия.
- Интеграции — явные permissions, шифрование secrets, здоровье и лимиты ([INTEGRATIONS.md](INTEGRATIONS.md)).

## 7. Логирование

- Не логировать секреты, passwords, raw auth tokens и лишние приватные данные.
- Аудит админ-действий: admin, action, timestamp, target, old/new где безопасно, IP/session metadata.
- **Критический audit trail нельзя позволять обычному администратору незаметно удалять** (механизм защиты — открытое решение, [PROJECT_PLAN.md](PROJECT_PLAN.md)).

## 8. Backup и восстановление

- Регулярный backup; состояние и последний успешный backup видны в админке.
- Обязательный **restore verification** (проверка, что backup реально восстанавливается).

## 9. Безопасность офлайн-данных

Локальные данные клиентов защищаются средствами платформы; будущее состояние «Local/private data» — данные не покидают устройство ([OFFLINE_SYNC.md](OFFLINE_SYNC.md)).

## 10. Admin-безопасность

- Отдельные admin sessions; обязательная/доступная 2FA по роли; rate limits; мониторинг подозрительной активности и security events — [ADMIN.md](ADMIN.md), раздел Security.

## 11. Открытые вопросы

1. Конкретные алгоритмы/библиотеки (hashing, токены) — фиксируются вместе со стеком (этап 1).
2. Механизм защиты критического audit trail (append-only / WORM / мультиподпись) — не выбран.
3. Политика обязательности 2FA по ролям (admin — обязательна? superadmin?) — детализировать.
4. Модель квот и лимитов — не определена.
5. Шифрование локальных офлайн-данных на устройствах — детализировать при проектировании клиентов.
6. Перечень «чувствительных настроек», требующих подтверждения/повторной аутентификации при изменении командой — не определён.
7. Механизм повторной аутентификации и окно доверия после неё — не спроектированы.
8. Support impersonation — отдельный ADR, если появится; детали — PROJECT_PLAN, раздел 12.
