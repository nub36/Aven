> **Статус:** реестр архитектурных решений проекта. Источник истины по тому, что утверждено.
> **Последнее обновление:** 2026-09-25
>
> Формат каждой записи: **ID, дата, статус, решение, причина, последствия**.
> Статусы: `Предложено` (draft, требует утверждения) · `Принято` · `Отклонено` · `Заменено` (с указанием замещающего ID).

> **Правило:** нельзя тихо менять ранее утверждённое решение. Если решение меняется — фиксируется новое решение, старое отмечается как «Заменено».

## Утверждённые решения (зафиксированы концепцией проекта)

### ADR-001

- **ID:** ADR-001
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** Документация в репозитории является source of truth. Вводится docs-first процесс: перед существенной работой читать PROJECT_PLAN → AGENT_GUIDE → профильные документы → DECISIONS; после каждой задачи обновлять WORK_LOG и профильные документы.
- **Причина:** Проект стартует с документационной основы; фиксация концепции до кода предотвращает хаотичные решения и потерю контекста между сессиями агентов/разработчиков.
- **Последствия:** Любые изменения проекта сопровождаются обновлением документов; накладные расходы на ведение документации; обязательный журнал работ и реестр решений.

### ADR-002

- **ID:** ADR-002
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** Основные возможности Aven работают **без** генеративного AI. AI в будущем — дополнительный слой (language parser, intent router, помощник по сложным запросам), необязательный для базовой работы. При отсутствии AI или интернета основные функции продолжают работать. AI не имеет неконтролируемого прямого доступа к БД и системным операциям: схема `Human input → AI Router (опционально) → строго определённый Action + parameters → permission validation → execution`.
- **Причина:** Зависимость ядра от платного LLM API делает систему дорогой, ломкой и зависимой от внешних провайдеров; концепция явно требует обратного.
- **Последствия:** Command Engine должен полноценно работать на детерминированных методах (шаблоны, словари, морфология, entity resolution); AI-слой проектируется как подключаемая надстройка со строгим контрактом.

### ADR-003

- **ID:** ADR-003
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** Внутренняя система работает с **текстовым представлением команды**. Голос — слой ввода/вывода: `Микрофон → STT → текст → Command Engine → Action → Result → текст → TTS`. Голосовой слой **заменяем** (провайдеры/движки STT/TTS сменяемы). Текстовый ввод доступен всегда; микрофон не обязателен. Ответ может одновременно показываться текстом и озвучиваться.
- **Причина:** Один внутренний формат упрощает движок, тестирование и переносимость между платформами; поддержка STT/TTS браузерами не гарантирована, поэтому голос не может быть обязательным.
- **Последствия:** Все intents/actions/парсеры определяются над текстом; голосовые провайдеры изолируются за интерфейсами; в UI всегда есть текстовый ввод и текстовый ответ.

### ADR-004

- **ID:** ADR-004
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** Ядро обработки — **Command Engine на intents/actions** + **Action Core**: любой источник команды (UI, текст, голос, Automation, API, в будущем AI) превращается в стандартное действие (например, `ADD_EXPENSE`, `CREATE_REMINDER`). Бизнес-логика не дублируется отдельно для голоса и UI.
- **Причина:** Единый контракт действий исключает расхождение поведения между интерфейсами и упрощает автоматизации, API и будущий AI-слой.
- **Последствия:** Каждая возможность выражается как action с параметрами и правами; UI/голос/автоматизации — только источники команд.

### ADR-005

- **ID:** ADR-005
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** **Опасные/разрушительные действия требуют подтверждения независимо от confidence.** Вводится оценка уверенности распознавания (конкретные числовые пороги НЕ утверждены): высокая уверенность + безопасное действие → выполнить; средняя → уточнить/подтвердить; низкая → попросить переформулировать. Ведётся история действий; для подходящих действий предусмотрен Undo. Недостающие параметры запрашиваются уточнением (state machine), потенциально опасные/существенные данные не угадываются.
- **Причина:** Защита пользовательских данных от ошибок распознавания и дорогостоящих ошибок; пример: «Удали все расходы» → «Будет удалено 1428 записей. Подтвердить?»
- **Последствия:** Каждый action имеет класс опасности и требования к подтверждению; хранится журнал действий с возможностью отмены для подходящих действий; пороги confidence — отдельное будущее решение.

### ADR-006

- **ID:** ADR-006
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** На production-сервере **запрещено** выполнение произвольного пользовательского JavaScript (в т.ч. в Automation Canvas). Каждый серверный блок автоматизации — заранее зарегистрированная операция с определёнными входами, выходами, permissions, validation и resource limits.
- **Причина:** Произвольный код = RCE-риск, невозможность лимитирования и аудита.
- **Последствия:** Реестр разрешённых блоков; sandbox-модель не требуется для пользовательского JS, т.к. он не исполняется; расширяемость через зарегистрированные операции.

### ADR-007

- **ID:** ADR-007
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** Долгосрочная архитектура учитывает **offline-first / local-first**: частичная работа без интернета, при восстановлении — безопасная синхронизация, разрешение конфликтов, статус pending sync. Состояния: Online / Offline / Sync pending / Local-private data (будущее).
- **Причина:** Концепция требует работы без интернета (заметки, задачи, локальные события, часть календаря, расходы, авто, калькуляторы, локальный поиск, часть Command Engine, TTS/STT где позволяет устройство).
- **Последствия:** Клиенты проектируются с локальным хранилищем; серверная модель должна поддерживать синхронизацию; стратегия разрешения конфликтов — отдельное открытое решение (см. PROJECT_PLAN, открытые вопросы).

### ADR-008

- **ID:** ADR-008
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** **Privacy & security by design.** Пользователь контролирует свою память, данные, команды и автоматизации: просмотр, изменение, экспорт, удаление, управление сессиями/устройствами/интеграциями/памятью. Доступ администрации к пользовательскому содержимому минимизирован (админ по умолчанию не видит приватные заметки и файлы). Обязательны: современный password hashing, безопасные сессии/tokens, CSRF/XSS/SQLi-защиты, валидация, authorization на каждом объекте, rate limiting, шифрование secrets, аудит админ-действий, 2FA где нужно, backup + restore testing, export/delete account, least privilege, явные permissions для device-агентов и интеграций. Чувствительные данные не хранятся «просто потому, что технически возможно»; платёжные секреты не хранятся без отдельной проработки безопасности.
- **Причина:** Aven — центр личных данных; доверие возможно только при контроле пользователя над данными.
- **Последствия:** Подробности в [SECURITY.md](SECURITY.md); каждый модуль проектируется с учётом прав доступа; интерфейс «Память Aven» обязателен.

### ADR-009

- **ID:** ADR-009
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** Функциональность **расширяется модулями**. Предусмотрены универсальные пользовательские сущности: в будущем пользователь сможет создавать собственные разделы/типы (Аквариум, Мотоцикл, Домашнее животное, Сервер, Коллекция) с расширяемыми типами полей (text, long text, number, money, date, datetime, boolean, file, image, URL, select, relation, ...). Сущности связываются между собой (пример: BMW → Ремонт → Расход → Чек → Автосервис → Дата); дублирование одних данных в разных модулях без необходимости не допускается.
- **Причина:** Широкий перечень направлений (авто, финансы, дом, поездки, ...) невозможно и не нужно реализовывать монолитно; пользовательские типы дают покрываемость нишевых сценариев.
- **Последствия:** Модель данных строится вокруг расширяемых сущностей и связей (см. [DATA_MODEL.md](DATA_MODEL.md)); модули включаются/выключаются (feature flags в админке).

### ADR-010

- **ID:** ADR-010
- **Дата:** 2026-09-25
- **Статус:** Принято
- **Решение:** **Честность статусов**: Aven не изображает выполненное действие, если оно не выполнено. Различаются статусы: успешно; ожидает синхронизации; запланировано; требует подтверждения; ошибка; недоступно офлайн; платформа не поддерживает. Особенно важно для voice, notifications, integrations и desktop/mobile операций. Не обещать, что закрытый браузер сам произнесёт голосовое сообщение; Web Push и возможности браузера/ОС имеют ограничения.
- **Причина:** Доверие к помощнику строится на честной обратной связи.
- **Последствия:** У каждой операции — машиночитаемый статус; UI и шаблонные ответы отражают реальный статус; возможности платформ декларируются явно (см. [VOICE.md](VOICE.md), [OFFLINE_SYNC.md](OFFLINE_SYNC.md), [FUTURE.md](FUTURE.md)).

## Предложенные решения (требуют утверждения, реализация запрещена до «Принято»)

### ADR-101

- **ID:** ADR-101
- **Дата:** 2026-09-25
- **Статус:** Предложено
- **Решение:** Backend — TypeScript + Node.js; возможный framework — NestJS.
- **Причина:** Единый язык с веб-фронтендом, типизация, зрелая экосистема; NestJS даёт модульность, DI, структуру для крупных систем.
- **Последствия:** Требуется утверждение (в т.ч. сравнение альтернатив); до утверждения код не пишется. Открытый вопрос: обоснование выбора framework против альтернативы «лёгкий собственный сервер».

### ADR-102

- **ID:** ADR-102
- **Дата:** 2026-09-25
- **Статус:** Предложено
- **Решение:** Серверная БД — PostgreSQL.
- **Причина:** Реляционная модель соответствует структурированным данным (расходы, заправки, события), связям сущностей и требованиям целостности; JSONB покрывает гибкие пользовательские типы.
- **Последствия:** Схема данных проектируется в [DATA_MODEL.md](DATA_MODEL.md) после утверждения; миграции — обязательная часть админки (раздел Migrations в [ADMIN.md](ADMIN.md)).

### ADR-103

- **ID:** ADR-103
- **Дата:** 2026-09-25
- **Статус:** Предложено
- **Решение:** Веб-клиент — React + TypeScript; возможный framework — Next.js.
- **Причина:** Экосистема, типизация, SSR/SSG-возможности Next.js.
- **Последствия:** Требуется утверждение; вопрос: действительно ли нужен SSR для личного помощника или достаточно SPA + PWA (см. открытые вопросы в [PROJECT_PLAN.md](PROJECT_PLAN.md)).

### ADR-104

- **ID:** ADR-104
- **Дата:** 2026-09-25
- **Статус:** Предложено
- **Решение:** Мобильные приложения (будущее) — Flutter/Dart как один из кандидатов; локальная БД — SQLite.
- **Причина:** Кроссплатформенность Android/iOS из одной кодовой базы; SQLite — проверенное локальное хранилище для offline-first.
- **Последствия:** Решение принимается перед этапом мобильных приложений; альтернативы (Kotlin Multiplatform, React Native) должны быть рассмотрены в ADR.

### ADR-105

- **ID:** ADR-105
- **Дата:** 2026-09-25
- **Статус:** Предложено
- **Решение:** Desktop-agent (будущее) — Rust + Tauri как кандидат.
- **Причина:** Компактный бинарник, системный доступ для разрешённых действий («Открой Steam», «Покажи свободное место»), безопасность Rust.
- **Последствия:** Desktop-agent запускается только с явного согласия пользователя, имеет контролируемые permissions и явно разрешённые системные действия; не входит в MVP.

### ADR-106

- **ID:** ADR-106
- **Дата:** 2026-09-25
- **Статус:** Открыто (кандидаты не определены)
- **Решение:** Требуется выбрать production-ready систему очередей/воркеров для фоновых задач (напоминания, автоматизации, уведомления, синхронизация).
- **Причина:** Плана по job-инфраструктуре в концепции нет — сказано только «нужно выбрать production-ready очередь/worker систему».
- **Последствия:** Кандидаты (BullMQ, RabbitMQ, Temporal и др.) подлежат сравнению в отдельном ADR; влияет на [AUTOMATION.md](AUTOMATION.md) и админку (очереди, retry, failed runs).

### ADR-107

- **ID:** ADR-107
- **Дата:** 2026-09-25
- **Статус:** Открыто
- **Решение:** Кэширование — Redis или совместимое решение **только если обосновано**.
- **Причина:** В концепции кэш упомянут условно; на старте нагрузка может не требовать кэша.
- **Последствия:** Обоснование (или отказ) готовится к этапу 1; не блокирует MVP-проектирование.

### ADR-108

- **ID:** ADR-108
- **Дата:** 2026-09-25
- **Статус:** Предложено
- **Решение:** Объектное хранилище файлов — S3-compatible abstraction (интерфейс поверх совместимых бэкендов).
- **Причина:** Файлы (чеки, фото, документы) — часть модели данных; абстракция позволяет менять провайдера и/self-hosted варианты.
- **Последствия:** Интерфейс хранилища фиксируется в [INTEGRATIONS.md](INTEGRATIONS.md)/[DATA_MODEL.md](DATA_MODEL.md); конкретный провайдер и лимиты — отдельно (админка: Storage, quotas).
