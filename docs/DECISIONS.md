# DECISIONS — Решения проекта: продуктовые принципы и ADR

> **Статус:** реестр решений проекта. Источник истины по тому, что зафиксировано и в каком статусе.
> **Последнее обновление:** 2026-09-25
>
> **Важно:** владелец проекта **не** утверждал ADR-001…010 как неизменяемые архитектурные решения (и не утверждал их автоматически). Часть из них — продуктовые принципы, заданные владельцем (статус `Product Principle`); они фиксируют **цель/ограничение продукта**, но **не** способ реализации. Никакое архитектурное или технологическое решение сейчас не является необратимым.
>
> **Разграничение понятий:** `Product Principle` / `Product Direction` ≠ `Proposed Architecture Decision`. Принцип/направление фиксирует цель; **способ реализации** фиксируется только ADR со статусом `Accepted`. Все не утверждённые владельцем технические решения имеют статус `Proposed` или `Under Discussion`.

---

## Статусы

| Статус | Смысл |
|---|---|
| `Product Principle` | Продуктовый принцип, явно заданный владельцем. **НЕ** окончательное архитектурное решение: способ реализации требует отдельного ADR со статусом `Accepted` до production-разработки |
| `Product Direction` | Текущее продуктовое направление, заданное владельцем. **НЕ** архитектурное решение; **может быть пересмотрено владельцем проекта** |
| `Proposed` | Предложено; требует утверждения владельцем |
| `Under Discussion` | Активно обсуждается; решения нет |
| `Accepted` | Утверждено владельцем (пока нет ни одного) |
| `Rejected` | Отклонено |
| `Superseded` | Заменено другим ADR (указан замещающий ID) |

## Правила изменяемости архитектуры

> **«До начала production-разработки архитектура Aven находится в стадии проектирования. Любое Proposed/Under Discussion решение может быть изменено владельцем проекта без необходимости сохранять обратную совместимость с ещё не существующей production-реализацией.»**

- После начала разработки архитектура также может изменяться, но изменение должно документироваться **новым ADR с причиной и последствиями**.
- ADR **не трактуется** как запрет на изменение архитектуры.
- Старое решение **не удаляется бесследно**: при реальной замене получает статус `Superseded`/`Rejected` со ссылкой на новое.
- При конфликте **нового прямого решения владельца** со старым ADR **приоритет имеет решение владельца**; конфликт документируется (порядок приоритетов источников требований — [AGENT_GUIDE.md](AGENT_GUIDE.md)).
- Реализация соответствующей части системы не начинается, пока **способ реализации** не зафиксирован ADR со статусом `Accepted`.

## Продуктовые принципы (Product Principle)

> Принципы явно заданы владельцем в концепции/инструкциях. Они **не являются окончательными архитектурными решениями**; механизмы реализации требуют отдельных ADR (`Accepted`) до production-разработки.

### ADR-001

- **ID:** ADR-001
- **Дата:** 2026-09-25 (уточнён 2026-09-25)
- **Статус:** Product Principle
- **Решение:** Документация в репозитории — **source of truth текущего состояния проекта**; при этом документация **не является неизменяемой**: владелец может менять требования, архитектуру, MVP, технологии и приоритеты. Вводится docs-first процесс: перед существенной работой читать PROJECT_PLAN → AGENT_GUIDE → профильные документы → DECISIONS; после задачи обновлять WORK_LOG и профильные документы. Приоритет источников требований — см. [AGENT_GUIDE.md](AGENT_GUIDE.md).
- **Причина:** Владелец явно объявил документацию источником истины; при этом проект в стадии проектирования, и документы должны отражать актуальные решения владельца, а не «замораживать» старые.
- **Последствия:** Любые изменения проекта сопровождаются обновлением документов; накладные расходы на ведение документации; обязательный журнал работ и реестр решений; устаревшие решения помечаются `Superseded`/`Rejected`, а не удаляются.

### ADR-002

- **ID:** ADR-002
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** Основные возможности Aven работают **без** обязательного генеративного AI. AI в будущем — дополнительный слой (language parser, intent router, помощник по сложным запросам), необязательный для базовой работы. При отсутствии AI или интернета основные функции продолжают работать. AI не имеет неконтролируемого прямого доступа к БД и системным операциям: `Human input → AI Router (опционально) → строго определённый Action + parameters → permission validation → execution`.
- **Причина:** Принцип явно задан владельцем: Aven должен уметь работать без платного LLM API; зависимость ядра от внешнего платного провайдера недопустима.
- **Последствия:** Command Engine проектируется на детерминированных методах (шаблоны, словари, морфология, entity resolution); AI-слой — подключаемая надстройка со строгим контрактом. Конкретный AI-провайдер/модель — будущее отдельное решение.

### ADR-003

- **ID:** ADR-003
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** **Текстовый ввод всегда доступен** наряду с голосовым; микрофон не обязателен. Внутренняя система работает с **текстовым представлением команды** (голос превращается в текст до входа в движок). Ответы могут одновременно показываться текстом и озвучиваться.
- **Причина:** Принцип явно задан владельцем.
- **Последствия:** Intents/actions/парсеры определяются над текстом; в UI всегда есть текстовый ввод и текстовый ответ. Заменяемость голосового слоя (STT/TTS за интерфейсами) — **архитектурное направление в статусе Proposed**, реализация требует отдельного ADR.

### ADR-004

- **ID:** ADR-004
- **Дата:** 2026-09-25 (пересмотрен 2026-09-25: понижен до Proposed)
- **Статус:** Proposed
- **Решение:** Архитектурный подход: ядро обработки — **Command Engine на intents/actions** + **Action Core**: любой источник команды (UI, текст, голос, Automation, API, в будущем AI) превращается в стандартное действие (например, `ADD_EXPENSE`, `CREATE_REMINDER`); бизнес-логика не дублируется для голоса и UI.
- **Причина:** Концепция задаёт направление («внутренне использовать intents/actions»), но конкретная архитектура ядра — проектное решение, не утверждённое владельцем как окончательное.
- **Последствия:** Требуется утверждение владельцем (возможны альтернативы/уточнения контракта действий); до `Accepted` реализация ядра не начинается.

### ADR-005

- **ID:** ADR-005
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** **Опасные/разрушительные действия требуют подтверждения** независимо от confidence. Вводится оценка уверенности распознавания (числовые пороги НЕ утверждены): высокая + безопасное → выполнить; средняя → уточнить/подтвердить; низкая → переформулировать. Ведётся история действий; для подходящих действий — Undo. Недостающие параметры запрашиваются уточнением; опасные/существенные данные не угадываются.
- **Причина:** Принцип явно задан владельцем.
- **Последствия:** Классификация действий по опасности и конкретные пороги confidence — отдельные будущие решения; хранится журнал действий с Undo для подходящих действий.

### ADR-006

- **ID:** ADR-006
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** **На production-сервере запрещено выполнять произвольный пользовательский JavaScript** (в т.ч. в Automation Canvas). Направление реализации: каждый серверный блок автоматизации — заранее зарегистрированная операция с входами, выходами, permissions, validation, resource limits.
- **Причина:** Принцип безопасности, явно заданный владельцем («НЕЛЬЗЯ по умолчанию»).
- **Последствия:** Конкретный механизм реестра блоков, модель permissions и resource limits — **Proposed**, требуют отдельного ADR; произвольный пользовательский JS на сервере не исполняется независимо от выбора механизма.

### ADR-007

- **ID:** ADR-007
- **Дата:** 2026-09-25 (пересмотрен 2026-09-25)
- **Статус:** Product Principle
- **Решение:** **Продуктовое требование (явно задано владельцем): система должна иметь возможность работать частично без интернета.** Архитектурная стратегия обеспечения этого требования (offline-first/local-first, выбор локальных хранилищ, синхронизация, разрешение конфликтов, статусы Online/Offline/Sync pending/Local-private data) — **Under Discussion** (см. [OFFLINE_SYNC.md](OFFLINE_SYNC.md)).
- **Причина:** Требование зафиксировано в концепции; способ его архитектурной реализации владельцем не утверждён.
- **Последствия:** Клиенты проектируются с учётом офлайн-требования; стратегия синхронизации и хранилищ — отдельные решения. **Уточнение приоритета (2026-09-25, владельцем):** при направлении Web-first сложная offline-синхронизация **не** является обязательным условием запуска первой web-версии; для Web допустимы локальные возможности браузера там, где это даёт практическую пользу; части [OFFLINE_SYNC.md](OFFLINE_SYNC.md) имеют статус Future/Under Design.

### ADR-008

- **ID:** ADR-008
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** **Пользователь контролирует свою память, данные, команды и автоматизации** (просмотр, изменение, экспорт, удаление, управление сессиями/устройствами/интеграциями/памятью). **Приватность и безопасность закладываются с самого начала.** Доступ администрации к пользовательскому содержимому минимизирован (по умолчанию админ не видит приватные заметки и файлы). Направления: современный password hashing, безопасные сессии, CSRF/XSS/SQLi-защиты, authorization на каждом объекте, rate limiting, шифрование secrets, аудит, 2FA где нужно, backup + restore testing, export/delete account, least privilege. Чувствительные данные не хранятся «просто потому, что технически возможно»; платёжные секреты — без отдельной проработки безопасности не хранятся.
- **Причина:** Принципы явно заданы владельцем; Aven — центр личных данных.
- **Последствия:** Конкретные алгоритмы и механизмы — отдельные решения (Proposed/Under Discussion) вместе со стеком; интерфейс «Память Aven» обязателен; подробности — [SECURITY.md](SECURITY.md).

### ADR-009

- **ID:** ADR-009
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** Функциональность **расширяется модулями**; в будущем пользователь сможет создавать **собственные разделы/типы сущностей** (Аквариум, Мотоцикл, Домашнее животное, Сервер, Коллекция) с расширяемыми типами полей (text, long text, number, money, date, datetime, boolean, file, image, URL, select, relation, ...). Сущности связываются (пример: BMW → Ремонт → Расход → Чек → Автосервис → Дата); без дублирования одних данных в разных модулях без необходимости.
- **Причина:** Принцип явно задан владельцем в концепции.
- **Последствия:** Модель данных строится вокруг расширяемых сущностей и связей ([DATA_MODEL.md](DATA_MODEL.md)); конкретный механизм пользовательских типов (EAV/JSONB/гибрид) — **Under Discussion**; модули включаются/выключаются.

### ADR-010

- **ID:** ADR-010
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** **Aven не должен сообщать об успешном выполнении невыполненного действия.** Различаются статусы: успешно; ожидает синхронизации; запланировано; требует подтверждения; ошибка; недоступно офлайн; платформа не поддерживает. Особенно важно для voice, notifications, integrations, desktop/mobile операций. Не обещать, что закрытый браузер сам произнесёт голосовое сообщение; Web Push и возможности браузера/ОС имеют ограничения.
- **Причина:** Принцип явно задан владельцем; доверие к помощнику строится на честной обратной связи.
- **Последствия:** У операций — машиночитаемые честные статусы; UI и шаблонные ответы отражают реальность; возможности платформ декларируются явно.

### ADR-011

- **ID:** ADR-011
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** Пользователь должен иметь возможность менять **подходящие настройки не только через UI, но и текстовой/голосовой командой**. Команды преобразуются в **стандартные Actions** (примеры: `settings.voice.rate.set`, `settings.quiet_hours.set`, `settings.day_period.set`, `dictionary.alias.create`, `settings.voice.enabled.set`, `settings.confirmation_policy.set`). **Голосовая команда не обходит security requirements**; для чувствительных настроек — подтверждение и/или повторная аутентификация.
- **Причина:** Принцип явно задан владельцем; соответствует духу продукта («скажи Aven, что сделать»).
- **Последствия:** Полный набор `settings.*` actions и перечень «подходящих»/«чувствительных» настроек — отдельные решения ([COMMAND_ENGINE.md](COMMAND_ENGINE.md), [SECURITY.md](SECURITY.md)); подробности — [PROJECT_PLAN.md](PROJECT_PLAN.md), раздел «Управление настройками через Aven».

### ADR-012

- **ID:** ADR-012
- **Дата:** 2026-09-25
- **Статус:** Product Principle
- **Решение:** **Разделение пользовательских и административных возможностей:** `/settings` — настройки конкретного пользователя; `/admin` — управление системой Aven. **Администратор не должен автоматически получать возможность действовать от имени пользователя.** Если в будущем появится support impersonation, функция должна проектироваться отдельно, иметь строгие permissions, быть явно заметной, журналироваться, иметь причину входа и по возможности ограничивать доступ к чувствительным данным.
- **Причина:** Принцип явно задан владельцем; минимизация доступа администрации к пользовательскому содержимому (см. ADR-008).
- **Последствия:** Механика разделения прав и будущий impersonation-ADR — отдельные решения ([SECURITY.md](SECURITY.md), [ADMIN.md](ADMIN.md)).

### ADR-013

- **ID:** ADR-013
- **Дата:** 2026-09-25
- **Статус:** Product Direction — **может быть пересмотрено владельцем проекта** (не необратимое архитектурное решение)
- **Решение:** Текущий приоритет разработки — **WEB-FIRST**. Первая полноценная реализация Aven — **самостоятельный полезный веб-сайт**. Первую версию **не** проектировать как: оболочку будущего мобильного приложения; только голосового ассистента; только чат; пустой dashboard; демонстрацию технологий. Пользователь полноценно пользуется основными функциями сайта мышью, клавиатурой, обычными формами, навигацией. **Голос и текстовые команды — дополнительные способы управления уже существующими функциями.** Единый путь действия:

  ```
  UI / Forms
          \
  Text command → Action Core → Business Logic → Data
          /
  Voice → STT → Text command

  Result → UI
         → Text response
         → TTS (если включено)
  ```

  Отдельная бизнес-логика для UI, текста и голоса **не создаётся**. Ориентировочный порядок развития: **Stage 1** — полезный самостоятельный веб-сайт → **Stage 2** — Command Engine и управление функциями сайта текстовыми командами → **Stage 3** — голосовой ввод/ответы поверх Command Engine → **Stage 4** — расширение автоматизаций и Automation Canvas → **Stage 5** — после появления полезного и проверенного веб-продукта определить, какие функции переносить в мобильные → **Stage 6** — Android/iOS и другие клиенты (отдельное будущее направление). Порядок отражает **продуктовый приоритет**, а не обязательную строгую последовательность реализации. **Web-first ≠ Web-only:** архитектура должна позволять дальнейшее развитие в PWA, Android, iOS, desktop, integrations, но эти платформы не являются текущей целью разработки.
- **Причина:** Направление задано владельцем 2026-09-25: сначала полезный и проверенный веб-продукт, затем перенос на другие платформы по подтверждённой необходимости.
- **Последствия:** UI/Forms — первоклассный источник команд наравне с текстом/голосом через единый Action Core; ни одна базовая функция не зависит от микрофона/STT/TTS; mobile и desktop остаются в [FUTURE.md](FUTURE.md) (Stage 5–6); сложная offline-синхронизация не является условием web-запуска (см. ADR-007, [OFFLINE_SYNC.md](OFFLINE_SYNC.md)); backend/API и бизнес-логика проектируются так, чтобы позже их могли использовать другие доверенные клиенты, без искусственных препятствий.

## Предложенные решения (Proposed — требуют утверждения, реализация до `Accepted` запрещена)

### ADR-101

- **ID:** ADR-101
- **Дата:** 2026-09-25
- **Статус:** Proposed
- **Решение:** Backend — TypeScript + Node.js; возможный framework — NestJS.
- **Причина:** Единый язык с веб-фронтендом, типизация, зрелая экосистема; NestJS даёт модульность, DI, структуру.
- **Последствия:** Требуется утверждение (в т.ч. сравнение альтернатив); до утверждения код не пишется. Открытый вопрос: обоснование framework против альтернативы «лёгкий собственный сервер».

### ADR-102

- **ID:** ADR-102
- **Дата:** 2026-09-25
- **Статус:** Proposed
- **Решение:** Серверная БД — PostgreSQL.
- **Причина:** Реляционная модель соответствует структурированным данным, связям сущностей и целостности; JSONB покрывает гибкие пользовательские типы.
- **Последствия:** Схема проектируется в [DATA_MODEL.md](DATA_MODEL.md) после утверждения; миграции — обязательная часть админки.

### ADR-103

- **ID:** ADR-103
- **Дата:** 2026-09-25
- **Статус:** Proposed
- **Решение:** Веб-клиент — React + TypeScript; возможный framework — Next.js.
- **Причина:** Экосистема, типизация, SSR/SSG-возможности Next.js.
- **Последствия:** Требуется утверждение; вопрос: нужен ли SSR для личного помощника или достаточно SPA + PWA.

### ADR-104

- **ID:** ADR-104
- **Дата:** 2026-09-25
- **Статус:** Proposed
- **Решение:** Мобильные приложения (будущее) — Flutter/Dart как один из кандидатов; локальная БД — SQLite.
- **Причина:** Кроссплатформенность Android/iOS из одной кодовой базы; SQLite — проверенное локальное хранилище.
- **Последствия:** Решение принимается перед этапом мобильных приложений; альтернативы (Kotlin Multiplatform, React Native) должны быть рассмотрены в ADR.

### ADR-105

- **ID:** ADR-105
- **Дата:** 2026-09-25
- **Статус:** Proposed
- **Решение:** Desktop-agent (будущее) — Rust + Tauri как кандидат.
- **Причина:** Компактный бинарник, системный доступ для разрешённых действий, безопасность Rust.
- **Последствия:** Desktop-agent запускается только с явного согласия, контролируемые permissions; не входит в MVP.

### ADR-108

- **ID:** ADR-108
- **Дата:** 2026-09-25
- **Статус:** Proposed
- **Решение:** Объектное хранилище файлов — S3-compatible abstraction.
- **Причина:** Файлы (чеки, фото, документы) — часть модели данных; абстракция позволяет менять провайдера и self-hosted варианты.
- **Последствия:** Интерфейс хранилища фиксируется после утверждения; конкретный провайдер и лимиты — отдельно ([ADMIN.md](ADMIN.md), Storage).

## Under Discussion

### ADR-106

- **ID:** ADR-106
- **Дата:** 2026-09-25
- **Статус:** Under Discussion
- **Решение:** Требуется выбрать production-ready систему очередей/воркеров для фоновых задач (напоминания, автоматизации, уведомления, синхронизация).
- **Причина:** В концепции сказано только «нужно выбрать production-ready очередь/worker систему»; кандидаты не определены.
- **Последствия:** Кандидаты (BullMQ, RabbitMQ, Temporal и др.) подлежат сравнению в отдельном ADR; влияет на [AUTOMATION.md](AUTOMATION.md) и админку (очереди, retry, failed runs).

### ADR-107

- **ID:** ADR-107
- **Дата:** 2026-09-25
- **Статус:** Under Discussion
- **Решение:** Кэширование — Redis или совместимое решение **только если обосновано**.
- **Причина:** Кэш упомянут условно; на старте нагрузка может не требовать кэша.
- **Последствия:** Обоснование (или отказ) готовится к этапу 1; не блокирует MVP-проектирование.
